## この手順書の言葉

- **手順書**: この文書のように、plan が作り、人が承認し、implement が実行する文書。
- **指紋**: ファイルの内容から計算した SHA-256 の値（`sha256:` で始まる文字列）。承認したときから
  変わっていないことを機械的に確かめるために使う。
- **review の記録**: review が `.agents/artifacts/executions/<手順書 ID>/<実行 ID>/review/` に
  1 件 1 ファイルで追記する出来事の列。指摘の集合の固定、往復ごとの判定、人の判断がここに残る。
- **指摘（finding）と状態**: review が見つけた問題 1 件。状態は `open`（未解決）、`closed`（解決した、
  または人が直さないと決めた）、`stale`（前提が古くなった）、`deferred`（後回しの候補へ送った）。
- **人が決める指摘**: 機械で確かめる方法が書けないと理由つきで記録された指摘。人の判断を記録した
  ときだけ閉じる。この手順書は、これ以外の（機械で確かめる）指摘にも人の判断で閉じる道を足す。
- **判断の記録（decision）**: 人の判断を残す review の出来事。いまは指摘の ID と結果
  （受け入れ / 却下）だけを持ち、理由の欄が無い。
- **正本と複製**: review の補助スクリプトの正本は `tools/workflow-runtime/review/` にあり、skill
  ディレクトリ `skills/ba0918-review/scripts/` には配布用の複製が置かれる。複製は
  `bunx agentic-skill-vendor gen` が正本から作り、`verify` が一致を検査する。手で複製を直さない。

## 目的

Phase 4 の実走で、review skill 自身のレビュー往復を人が手書きの引き継ぎ文書で次のセッションへ
渡す羽目になった。原因を辿ると、review の記録には「完了した」ことと「人がどう決めたか」の
2 つが無く、記録だけからは現在地を導けなかった。

- 全指摘が閉じた review でも、次に `bind`（review を始める補助コマンド）を実行すると「進行中の
  review がある」と誤認する。完了を表す情報が記録に無いため
- 機械で確かめる指摘を人が「直さない」と決めても、それを記録に残す道が無い。何度も失敗させて
  人が決める指摘に格上げする抜け道しかなかった

仕様書はこの 2 点を決め直した（完了は全指摘の状態から導く、固定後の開いている指摘は人が理由つきで
却下できる）。この手順書はそれを review の補助スクリプトと文書に反映する。

## 利用者が得る結果

- 全指摘が `closed`、`stale`、`deferred` のどれかになった review に対して `bind` を実行すると、
  「進行中」ではなく「完了済み」と答え、記録の事実（review ID、出来事の数）を示す
- 集合を固定したあと、人は `decide --finding <ID> --result rejected --reason <理由>` で、機械で
  確かめる指摘も閉じられる。理由は判断の記録に残り、次のセッションが記録だけから「なぜ直さないと
  決めたか」を読める
- 却下した指摘は、そのあと確かめ方が通っても状態が変わらない。人の判断を機械が上書きしない

## 何を変えて、何を変えないか

変えるもの:

- `tools/workflow-runtime/review/review_model.py`（純粋な検証と遷移）: 判断の記録に理由の欄を
  足し、機械で確かめる指摘を人の却下で閉じる遷移を許す
- `tools/workflow-runtime/review/review_runtime.py`（記録と実行）: `decide` を開いている全指摘に
  広げ、完了を全指摘の状態から導く
- それぞれのテスト `tools/workflow-runtime/tests/review_model_test.py`、
  `tools/workflow-runtime/tests/review_runtime_test.py`
- skill の文書 `skills/ba0918-review/SKILL.md`、`references/review.md`、`references/evidence.md`
- 配布の複製 `skills/ba0918-review/scripts/` と、複製の指紋を記録する `vendor-lock.json`
  （`gen` が更新する）

変えないもの:

- 指摘の ID の導き方、集合の固定の仕方、再レビューの判定（確かめ方が通ったら閉じる）。
  すでに固定された集合や過去の記録は書き換えない
- 完了を表す新しい出来事の種類。仕様書が「完了を表す出来事は書かない」と決めている
- brainstorm、plan、implement の skill とスクリプト。現在地を横断して導く道具（Phase 5.2）
- review の記録の置き場所と 1 件 1 ファイルの方式

## 外部への影響と、主なリスク

- 外部サービスとの入出力は無い。ネットワークにも触れない
- **過去の判断の記録には理由の欄が無い**（Phase 4 の実走で書かれた `decision` 出来事）。読む側は
  理由の欄が無い記録も受け付ける必要がある。受け付けないと、Phase 4 の review 記録が読めなくなり、
  その実行の現在地を導けない。手順 1 のテストで確かめる
- **完了は毎回導く値であって、鍵ではない**。仕上げのレビューの結果を `merge` で合流させると
  開いた指摘が増え、review は再び「進行中」になる。これは仕様書の「完了を表す出来事は書かない」
  から導かれる振る舞いで、この手順書が新しく決める意味ではない。文書にその旨を書く
- **却下が集合の固定前に使えると、レビュアーが不都合な指摘を消せる**。`decide` は固定後にしか
  動かないことを手順 2 のテストで確かめる
- 正本を直したあと複製の同期を忘れると、配布される skill が古い振る舞いのままになる。手順 5 で
  `gen` と `verify` を通す

## Steps

### 1. 判断の記録に理由を持たせ、機械で確かめる指摘も人の却下で閉じられる遷移にする

**目的:** 仕様書 `review.md` の「指摘（finding）」「人が決める指摘」「収束の仕組み」に合わせる。
`review_model.py` の、ファイルにも git にも触らない部分だけを変える。

- 判断の記録（`decision` 出来事）に理由の欄を足す。結果が却下のときは理由が必須で、空や上限超えは
  拒否する。結果が受け入れのときは理由が無くてもよい
- 理由の欄が無い古い判断の記録を読んでも、指摘の状態の導出が壊れない
- 状態の遷移: 機械で確かめる指摘も、人の却下（理由つき）によって `open` → `closed` にできる。
  人が決める指摘の従来の閉じ方（受け入れ / 却下の記録）はそのまま。`closed` から戻す遷移は
  引き続き拒否する
- 機械で確かめる指摘に「受け入れ」の判断を記録することは拒否する。仕様書が人に許しているのは
  「直さない」と決めることだけで、確かめ方を通さずに「直った」と記録する道は作らない

**前提:** なし。

**変更してよいファイル:** `tools/workflow-runtime/review/review_model.py`、
`tools/workflow-runtime/tests/review_model_test.py`。

**Completion:** test

確かめること:

- 却下の判断の記録は理由が無いと拒否され、理由があれば受け付けられる
- 機械で確かめる指摘が人の却下で `closed` になり、その後 `open` へ戻す遷移は拒否される
- 機械で確かめる指摘への「受け入れ」の判断は拒否される
- 人が決める指摘の従来の閉じ方（受け入れ / 却下）は変わらず動く
- 理由の欄を持たない判断の記録が混ざった出来事の列からも、指摘の状態が導ける

**実装側に任せてよい選択:** 遷移の原因を表す語の名前（例: 人の却下を従来の「人の判断」と別の
語にするか）。理由の欄が無いときの内部表現（`null` か欄の省略か）。

**止まる条件:** 仕様書に無い判断の結果（受け入れ・却下以外）を足したくなったら止まる。

### 2. `decide` を開いている全指摘に広げる

**目的:** 仕様書 `review.md` の「人が決める指摘」「人が判断する場面」「失敗したときの動き」、
`workflow.md` の「人の判断の置き場」に合わせる。補助コマンド `decide` が、機械で確かめる指摘も
受け付けるようにする。

- `decide --finding <ID> --result rejected --reason <理由>` で、固定した集合の開いている指摘を
  閉じ、理由つきの判断の記録を書く
- 集合を固定する前は、従来どおり拒否する（固定前に指摘を消す抜け道にしない）
- `closed`、`stale`、`deferred` の指摘、集合に無い ID は拒否する
- 却下した指摘は、その後の再レビューで確かめ方を走らせず、状態も変えない。確かめ方が通るように
  なっていても `closed` のまま

**前提:** 手順 1。

**変更してよいファイル:** `tools/workflow-runtime/review/review_runtime.py`、
`tools/workflow-runtime/tests/review_runtime_test.py`。

**Completion:** test

確かめること:

- 固定後、機械で確かめる指摘を理由つきで却下すると `closed` になり、判断の記録に理由が残る
- 理由の無い却下、機械で確かめる指摘への受け入れ、固定前の却下、集合に無い ID、すでに閉じた指摘
  への判断は、それぞれ拒否され、記録は増えない
- 却下のあと、確かめ方が通る状態にして再レビューを実行しても、その指摘は判定の対象に現れず
  `closed` のまま

**実装側に任せてよい選択:** 引数の名前（`--reason`）と、拒否の理由コードの語。

**止まる条件:** 却下した指摘を再び開く操作が必要に見えたら止まる（仕様書は再開を決めていない）。

### 3. review の完了を全指摘の状態から導く

**目的:** 仕様書 `review.md` の「記録の置き場所」と、`workflow.md` の「止まったところから戻る」
「横断の状態は持たない」に合わせる。完了を表す出来事を足さずに、`bind` が完了を答えられるように
する。

- review が完了しているとは、固定した集合（合流した指摘を含む）の全指摘が `closed`、`stale`、
  `deferred` のどれかであること。仕様の改訂で止まった（`findings_stale`）review も終わっている
- `bind` は、完了した review がある実行に対しては「完了済み」として拒否し、記録の事実（review ID、
  出来事の数、最後の出来事、記録の場所）を示す。開いた指摘が 1 つでも残っていれば従来どおり
  「進行中」として、人の確認（`--continue`）を待つ
- 集合を固定する前の review は、指摘が 0 件でも完了ではない（まだ何も固定していない）
- 完了は毎回導く。合流で開いた指摘が増えれば、再び進行中になる

**前提:** 手順 1、2。

**変更してよいファイル:** `tools/workflow-runtime/review/review_runtime.py`、
`tools/workflow-runtime/tests/review_runtime_test.py`。

**Completion:** test

確かめること:

- 全指摘を閉じた review に `bind` を実行すると「完了済み」の理由で拒否され、答えに記録の事実が
  含まれる
- 開いた指摘が 1 つ残る review では「進行中」のまま、`--continue` で続けられる
- 人の却下だけで全指摘が閉じた review も完了と判定される
- 集合を固定する前の review は完了と判定されない
- 完了した review に仕上げのレビューの指摘を `merge` で合流させると、再び進行中と判定される

**実装側に任せてよい選択:** 「完了済み」を表す理由コードの語（従来の「終了済み」の語を流用するか
分けるか）と、答えに含める事実の欄の名前。

**止まる条件:** 完了を記録する出来事を書きたくなったら止まる（仕様書が禁じている）。

## 失敗したらどこで止まるか

- テストで示す手順で、失敗するテストが書けないなら、その手順が既存の振る舞いを確かめようとしている。
  テストを直す
- 手順書に無い振る舞いを決めたくなったら止まり、brainstorm に戻す
- 過去の review 記録が新しい検証で読めなくなったら、記録を書き換えずに止まる（記録は上書きしない）
- 手順 6 で失敗が見つかったら、どの手順の範囲かを特定して戻る。特定できなければ人に伝える
