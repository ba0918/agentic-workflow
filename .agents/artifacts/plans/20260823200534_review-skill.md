三つの仕様書の役割: `review.md` は、この手順書で作る skill の振る舞いのすべて（入力の検証、
指摘の形、モデルの決め方、最初のレビュー、差分の再レビュー、記録、やらないこと）を定める。
`workflow.md` は、implement が review に何を渡すか、review が修正する側に何を渡すか、
記録をどこに置くかを定める。`implement.md` は、review が読む証拠（`binding.json` と出来事の
ファイル、`implementation_green` の出来事）の形を定める。review は implement の証拠を読む
だけで、書き足さない。

## この手順書の言葉

- **手順書**: この文書のように、plan が作り、人が承認し、implement が実行する文書。
- **指紋**: ファイルの内容から計算した SHA-256 の値（`sha256:` で始まる文字列）。内容が
  1 文字でも変わると別の値になるので、「承認したときから変わっていない」ことを機械的に
  確かめるために使う。
- **実行と証拠**: implement は手順書を 1 回実行するたびに実行 ID を振り、起きたことを
  `.agents/artifacts/executions/<手順書 ID>/<実行 ID>/` に 1 件 1 ファイルで残す。これを証拠と
  呼ぶ。最後の出来事が `implementation_green`（全手順完了）なら、review に渡せる状態。
- **指摘（finding）**: review が見つけた問題 1 件。仕様書の「指摘（finding）」の表にある項目を
  持つ。
- **確かめ方（oracle）**: 指摘が直ったかを機械的に判定する手段（テスト名やコマンド）。指摘の
  ID はこの確かめ方から導く。
- **観点の一覧（profile）**: レビューで何を見るかを書いた文章ファイル。skill 本体から切り離して
  `references/profile/` に置く。
- **trailer**: コミットメッセージの末尾に置く `Key: value` 形式の行。修正コミットは、直した
  指摘の ID をここに書く。

## 目的

brainstorm、plan、implement はすでに `main` にある。4 つ目の review が無いので、implement が
仕上げた実装を独立した目で確かめるステップを、人が会話の中で即興で行っている。この手順書で
review skill を作り、4 ステップの仕組みを一周させる。

review の設計の核は、仕様書の「何をするステップか」にある経験（観点ごとに別の AI を並列に
走らせ、修正のたびに指摘が増え続け、無人のまま 22 往復した）への対策で、次の 2 つ。

1. 最初のレビューで指摘の集合を 1 回で作って固定し、以後は足さない
2. 指摘の ID を確かめ方から導き、再レビューでは「その確かめ方が通ったか」だけを見る

## 利用者が得る結果

implement が「全手順完了」で引き渡した実行に対して、review を起動すると、証拠から入力を
機械的に確かめ、観点の一覧に沿って 1 回レビューし、確かめ方つきの指摘の集合を記録して
固定する。修正のあとにもう一度起動すると、未解決の指摘と、その指摘の ID を trailer に持つ
修正コミットの差分だけを見て、確かめ方を走らせ、通った指摘を閉じる。往復は指摘の数で
必ず終わる。

## 外部への影響と、主なリスク

- 外部サービスとの入出力は、2 人目のレビュアー（`--second-reviewer` で明示されたときだけ）に
  限られる。渡す物は手順書の内容と差分だけで、渡す前に秘密情報を走査する。この手順書では、
  渡す物を組み立てて走査する部分までを作り、実際に外部へ送る部分は実行先ごとの差し替え
  可能な口（コマンド 1 つを呼ぶ形）にとどめる。この手順書の実行中に外部のレビュアーを
  呼ぶことはない
- 確かめ方のコマンドは作業ディレクトリの中で実行する。絶対パス、作業ディレクトリの外への
  書き込み、認証情報を含むコマンドは拒否する。拒否の検査が甘いと、レビュー対象の作業
  ディレクトリの外を壊す恐れがあるので、手順 4 のテストで拒否を確かめる
- review の記録は implement の証拠と同じディレクトリの下（`review/`）に置く。implement の
  出来事の連番に書き足してしまうと implement の証拠の整合が壊れるので、review は自分の連番を
  持ち、implement のファイルには触らない。手順 2 のテストで確かめる
- レビューそのもの（コードを読んで指摘を考える部分）は LLM が `SKILL.md` を読んで行う。この
  手順書で作るのは、その周りの機械的な部分（入力の検証、指摘の登録、確かめ方の実行、記録）と、
  LLM に読ませる文章。LLM を実際に走らせる確認（実測）は、人が名前を挙げて頼んでいないので
  この手順書には入れない

## 仕様書にあって、この手順書が値を決めないこと

仕様書が「運用で決める」「ここでは決めない」としている事柄は、この手順書でも決めない。
実装は、値を外から受け取れる形にし、無いときの振る舞いを次のとおりにする。

- **入力が大きすぎるときの閾値**（仕様書「読む範囲は重さの候補で変える」）: 起動時の引数で
  受け取る。指定が無ければ大きさでは止まらない
- **何度直しても通らない指摘を、人が決める指摘に格上げする回数**（仕様書「収束の仕組み」）:
  仕様書は回数を決めていない。この手順書では、再レビューで確かめ方を走らせて失敗した回数を
  指摘ごとに記録し、格上げは起動時の引数で受け取った回数に達したときに行う。引数が無ければ
  格上げせず、失敗の回数を報告に含めるだけにする
- **プロジェクトの指示や利用者の規則に書かれた「レビューに使うモデル」の読み取り方**
  （仕様書「自走時にモデルを決める順序」）: 文書のどの行をモデルの指定とみなすかは決まって
  いない。skill を動かす AI が文書を読んで判断し、補助スクリプトには「どの段階で決まったか」と
  「モデル ID」を引数で渡す。スクリプトは渡された段階と ID を記録するだけで、文書を解釈しない

## 手順の進め方の共通事項

- `test` の手順は、先に失敗するテストを書き、`python3 -m unittest tests.review_model_test`
  （または `tests.review_runtime_test`）で失敗を確かめてから実装し、通るのを確かめる
- テスト名は振る舞いを書く。手順ごとに 1 コミット。本文には「なぜ」を書く
- 手順書に無い振る舞いが必要になったら、止まって brainstorm に戻す
- この手順書は、改修後の implement skill（`skills/ba0918-implement/SKILL.md`）で実行する。
  implement の本文や補助コマンドの不足に気づいたら、その場で直さず記録だけ残し、この
  手順書の Scope の外として扱う
- implement の補助スクリプト（`execution_model.py`、`implement_runtime.py`）の関数を review から
  import して使ってよい。読むのは implement の証拠の形の検証に限る

## Steps

### 1. 指摘の形、ID の導出、状態の遷移、review の出来事を純粋な関数で作る

**目的:** 仕様書「指摘（finding）」「重さと対応は別」「確かめ方を先に書く」「人が決める指摘」
「同じ原因はまとめる」「指摘の集合を固定する」「記録の置き場所」に合わせる。`review_model.py` に、
ファイルや git に触らない検証と計算だけを置く。

- 指摘 1 件の検証: 仕様書の表にある項目（ID、重さ、対応、根拠となる仕様、証拠、確かめ方、
  根本原因のキー、状態、依拠した仕様の指紋、観点）をすべて持ち、値が決められた語のどれかで
  ある。`info` の対応は `record_only` だけ。`human_judgment` の指摘は、機械で確かめられない
  理由を持つ。それ以外の指摘は確かめ方（コマンドかテスト名）を持つ
- 指摘の ID の導出: 確かめ方の内容から機械的に導く。行番号や証拠の文言が変わっても、確かめ方が
  同じなら同じ ID になる
- 状態の遷移: `open` → `closed`（確かめ方が通った、または人が決める指摘に人の判断が記録された）、
  `open` → `stale`、`open` → `deferred`。`closed` から戻さない。`human_judgment` の指摘は
  確かめ方の結果では閉じない
- 同じ根本原因のキーを持つ指摘を 1 つの修正単位にまとめる見せ方の計算（ID と確かめ方は
  個別のまま）
- review の出来事の種類と必須の欄の定義。最初の出来事は implement の最後の出来事の指紋を
  持つ。固定した指摘の集合の出来事は、その集合の指紋と、レビューしたモデル ID と、モデルが
  決まった段階と、強さ（`light` / `standard`）と、使った観点の一覧の指紋を持つ。再レビューの
  出来事は、見た修正コミットの SHA と、指摘ごとの判定を持つ。出来事に全出力、ログ、認証情報、
  環境変数の値を入れられない

### 2. implement の証拠から入力を確かめ、review の記録を始める

**目的:** 仕様書「受け取るもの」「記録の置き場所」「失敗したときの動き」と、`workflow.md` の
「implement → review: 作業ブランチと証拠」、`implement.md` の「証拠の残し方」「完了と引き渡し」に
合わせる。補助コマンド `bind --plan-id <手順書 ID> --attempt-id <実行 ID>` が、証拠を読んで
次を確かめ、通ったら `review/` の最初の出来事を書く。

- 証拠の最後の出来事が `implementation_green` である
- `binding.json` の手順書（パス、版、指紋）が、いまの手順書のファイルと一致する
- `binding.json` の仕様書（パス、指紋）が、いまの仕様書のファイルと一致する
- 作業ディレクトリが存在し、`binding.json` のブランチを指している
- `review/` がすでにあって終わっていないなら、その事実（いつ、どこまで）を見せて止まり、人の
  確認を待つ。リポジトリ全体の「使用中」の印は置かない

あわせて、レビューのモデルの記録: `--model <モデル ID> --model-source <決まった段階>` を
受け取り、段階は「起動時の指定 / プロジェクトの指示 / 利用者の規則 / いまの会話」の 4 つの
どれかに限る。モデル ID は `claude-fable-5` のような完全な ID だけを受け付け、`opus` のような
別名は拒否する。

### 3. 最初のレビューの入力を組み立て、指摘の集合を固定する

**目的:** 仕様書「最初のレビュー」「読む範囲は重さの候補で変える」「安全上の確認は必須」
「強さは 2 段階、人が選ぶ」「指摘の集合を固定する」「観点の一覧（profile）」「仕上げのレビューと
2 人目のレビュアー」に合わせる。レビューそのものは LLM が行うので、ここで作るのは、LLM に
渡す物を決める部分と、LLM が出した指摘を受け取って固定する部分。

- `inputs --level light|standard [--profile <名前>] [--max-diff-lines <n>]`: 作業ブランチの
  差分（implement の `binding.json` の起点コミットから先端まで）を取り、差分のファイルの種類から
  観点の一覧を選ぶ（skill の文書なら `skill.md`、それ以外は `default.md`。混ざっていれば
  ファイルの集合ごとに当てる）。`--profile` があればそれで上書きする。閾値があって差分が
  超えていれば止まる。差分が触った関数を直接呼んでいる場所（1 段）は、候補が立ってから
  LLM が読むので、ここでは先読みしない
- `register --findings <JSON>`: LLM が出した指摘の一覧を受け取り、手順 1 の検証にかけ、
  `human_judgment` 以外の指摘は確かめ方を作業ディレクトリで走らせて「いま失敗する」ことを
  確認する。最初から通る指摘は集合に入れず、その旨を出力する。`light` のときは `warn` と
  `info` を受け付けない。安全上の確認の項目が終わっていない（観点の一覧の必須項目に対する
  結果が無い）なら、集合を固定せず「未完了で再開できる」状態で止まる
- 固定: 通った指摘の集合を 1 つの出来事として書き、集合の指紋を出力する
- 2 人目のレビュアーへの受け渡し物: `--second-reviewer` と `--second-model` が両方あるときだけ、
  手順書の内容と差分だけを 1 つのファイルに組み立て、秘密情報を走査し、実行先のコマンドを
  1 回だけ呼ぶ。自分のレビュー結果は渡さない。呼べなければ警告を記録して続ける。結果は
  LLM が読んで、指摘として `register` に渡す（同じ集合に入る）

確かめること:

- 閾値を超える差分では止まり、閾値が無ければ止まらない

- 確かめ方の実行で、絶対パス、作業ディレクトリの外への書き込み、認証情報を含むコマンドが
  拒否される

**実装側に任せてよい選択:** 差分のファイルの種類の判定方法（パスが `skills/` 以下か、など）。
確かめ方の実行の仕組み（手順 4 と共用する）。2 人目のレビュアーの実行先の呼び方（コマンドと
引数を設定で受け取る形）。

**止まる条件:** 観点の一覧の「必須項目」をスクリプトがどう知るか（手順 5 の文章ファイルから

### 4. 差分の再レビューの機械部分を作る

**目的:** 仕様書「差分の再レビューと収束」「収束の仕組み」「直す側との約束」「人が決める指摘」に
合わせる。補助コマンド `reverify` が、固定した集合と修正コミットから、見直す範囲を計算し、
確かめ方を走らせて開閉を記録する。

- 固定した集合を読み、依拠した仕様書の指紋がいまのファイルと違えば `findings_stale` の
  出来事を書いて止まる
- 固定したあとのコミットを列挙し、各コミットの trailer から指摘の ID を読む。trailer に
  指摘の ID を持たないコミットが混ざっていれば、範囲外として止まる（推測で補わない）
- 未解決（`open`）の指摘ごとに確かめ方を作業ディレクトリで走らせ、通れば `closed`、失敗なら
  `open` のままにして、失敗の回数を 1 増やす。`human_judgment` の指摘は走らせず、人の判断を
  まとめて求める一覧に入れる
- 修正コミットが、最初のレビューで見たファイルの外を触っていれば、全体レビューのやり直しの
  候補として出力する。自動では再実行しない
- 失敗の回数が引数の回数に達した指摘は `human_judgment` に格上げし、人の判断の一覧に入れる
- LLM が再レビュー中に見つけた別の問題は、`defer --findings <JSON>` で `deferred` として別に
  記録し、集合には足さない。修正が新たに持ち込んだリスクだけは `--introduced` を付けて集合に
  足せる（手順 3 と同じ検証と「いま失敗する」の確認を通す）
- 人の判断の記録: `decide --finding <ID> --result accepted|rejected` で、`human_judgment` の
  指摘を `closed` にする。1 往復分をまとめて示す出力を持つ

**前提:** 手順 3。

**変更してよいファイル:** `skills/ba0918-review/scripts/review_runtime.py`、
`tests/review_runtime_test.py`。

**Completion:** test

確かめること:

- 仕様書が改訂されていれば `findings_stale` で止まり、指摘は閉じられない
- trailer の無いコミットが混ざっていれば止まる。trailer があるコミットだけなら、その差分だけが
  見直す範囲として出力される
- 確かめ方が通った指摘だけ `closed` になり、通らない指摘は `open` のまま失敗の回数が増える。
  「直しました」という文言は入力にならない
- `human_judgment` の指摘は確かめ方の結果で閉じず、`decide` で閉じる
- 固定した集合に無い指摘を `reverify` で足そうとすると拒否される。`defer` は集合を変えない。
  `--introduced` の指摘だけが足され、最初から通るものは足されない
- 最初のレビューで見たファイルの外を触る修正コミットがあると、やり直しの候補が出力され、
  固定した集合は変わらない
- 失敗の回数が引数に達した指摘が格上げされる。引数が無ければ格上げされず回数が出力される
- 固定した集合のファイルは、再レビューの前後で 1 バイトも変わらない（開閉は追記）

**実装側に任せてよい選択:** trailer のキーの名前（`Finding:` など）。再レビューの出来事の
分け方（1 往復 1 ファイルか、指摘ごとか）。

**止まる条件:** 「最初のレビューで見たファイル」をどう記録しておくかで迷ったら、手順 3 の
固定の出来事に差分のファイル一覧を含める。それ以上の判断が要れば止まる。

## 人が判断する場面

| 場面 | 人が決めること |
|---|---|
| この手順書の承認 | このファイルを、この指紋のまま正本にしてよいか。同時に、いま「対象」の手順書 `20260823190251`（implement 改修 2/2、完了済み）を「保留」にしてよいか |

| 手順 6 の本文 | 3 ファイルを読んで、仕様書と食い違いが無いか |
| 手順 7 の結果 | 報告を読んで、review skill の実装を完了とするか |

## 失敗したらどこで止まるか

- テストで示す手順で、失敗するテストが書けないなら、その手順が既存の振る舞いを確かめようと
  している。テストを直す
- 手順書に無い振る舞いを決めたくなったら止まり、brainstorm に戻す
- implement の証拠の形が仕様書と食い違っていたら、review 側で吸収せずに止まる（implement の
  問題として別に直す）
- 手順 7 で失敗が見つかったら、どの手順の範囲かを特定して戻る。特定できなければ人に伝える
