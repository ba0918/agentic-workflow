## この手順書の言葉

- **手順書**: plan が作り、implement が実行する 1 つの Markdown ファイル。この文書自身も手順書。
- **指紋**: ファイルの内容から計算した SHA-256 のハッシュ値。人が読んだファイルと正本になったファイルが同じだと機械的に確かめるためのもの。文中では `sha256:` で始まる文字列。
- **人が判断する場面（Human gates）**: 手順の途中で人の「はい / いいえ」を待つ箇所。手順書の中に JSON で宣言する。
- **補助スクリプト**: `skills/ba0918-plan/scripts/plan_artifact.py`。草稿の保存、正本への移動、索引の読み書きをする Python スクリプト。

## 目的

Phase 4 の試運転で、plan が作って人が承認した手順書を、実装 skill がそのまま読めなかった。
原因は、手順書の書式と、読む側が受け付ける書式の約束がどこにも書かれていなかったこと。
改訂した `docs/spec/plan.md` はその約束を書いた。この手順書は、plan skill をその約束に
合わせる。

## 利用者が得る結果

plan が作った手順書は、正本になる前に「implement が機械的に読む 6 箇所」の書式検査と、
参照する仕様書の指紋の一致確認を通っている。人が読んで承認した手順書が、実行の段になって
「読めない」と言われることが無くなる。

## 何を変えて、何を変えないか

変えるもの:

- 補助スクリプトが手順書から読む箇所を、新しい書式（`**対象仕様:**` にパス・指紋・該当する節、
  各手順に `**完了の示し方:**`、人が判断する場面の JSON は `clauses` ではなく `sections`）にする
- 補助スクリプトが、草稿の保存時と正本への移動時に、6 箇所の書式と指紋の一致を検査する
- plan skill の本文（`SKILL.md` と `references/` の 3 本）を新しい仕様書に合わせる
- 補助スクリプトのテスト（`tests/plan_artifact_test.py`）の手順書の見本を新しい書式にする

変えないもの:

- 未完了の手順書の索引 `open-plans.json` の形。登録済みの古い手順書は、古い仕様書の指紋を
  指したまま「保留」に残す。移行や書き換えはしない
- 草稿の置き場所（`.agents/tmp/plans/`）と正本の置き場所（`.agents/artifacts/plans/`）
- 「いま対象」の切り替え、未コミットの変更があるときの停止、草稿の指紋が変わっていたときの拒否
- implement skill（いまの `skills/ba0918-cycle/`）。これは次の手順書で直す

## 外部への影響と、主なリスク

- 外部サービスとの入出力は無い。ファイルの読み書きはすべてこのリポジトリの中
- **implement の改修が終わるまで、新しい書式の手順書を implement は完全には扱えない。**
  brainstorm で許容すると決めた（implement の改修は直後に予定している）
- **いまの implement（`skills/ba0918-cycle/scripts/cycle_runtime.py`）は、人が判断する場面の
  読み取り結果の `clauses` という欄を参照している。** 手順 1 でこの欄を `sections` に変えると、
  `tests/cycle_runtime_test.py` の人が判断する場面に関するテストが通らなくなる。この手順書の
  範囲では直さない（implement の改修で直す）。implement 改修までの間、cycle のテストの一部が
  赤のまま main に残る。これは承認済み（欄名の変更を implement 改修まで遅らせると、仕様書と
  最初の手順書の書き方がずれるため、そちらを退けた）
- この手順書は、新しい書式で書かれた最初の手順書。実行するのは改修前の implement ではなく、
  人（またはこの会話の AI）が手順書を読んで手順どおりに進める。理由は、改修前の implement は
  「作った物で示す」手順を完了にできないから（Phase 3.5 の動機そのもの）

## 手順の進め方の共通事項

- 「テストで示す」手順は、先に失敗するテストを `tests/plan_artifact_test.py` に書き、
  `python3 -m unittest tests.plan_artifact_test` で失敗を確かめてから実装し、通るのを確かめる
- テスト名は振る舞いを書く（「〜を拒否する」「〜を返す」）。内部の関数名を書かない
- 手順ごとに 1 つのコミットにする。コミットの本文には「なぜ」を書く
- 手順書に書いていない振る舞いが必要になったら、自分で決めずに止まって brainstorm に戻す

## 実装手順

### 1. 人が判断する場面の JSON を、条文 ID ではなく節の名前で受け付ける

**目的:** `docs/spec/plan.md` の「人が判断する場面の宣言」に合わせる。JSON の `clauses`
（`CY-050` のような条文 ID の配列）を `sections`（仕様書の節の名前の配列）に変える。
いまのスクリプトは、手順の `**対応仕様:**` 行の条文 ID と突き合わせているが、新しい
書式では手順書冒頭の `**対象仕様:**` に列挙した「該当する節」と突き合わせる。

**前提:** なし（最初の手順）。

**変更してよい範囲:** `skills/ba0918-plan/scripts/plan_artifact.py` の人が判断する場面の
読み取り（`read_plan_human_gates` と、その結果の型）、`tests/plan_artifact_test.py`。

**完了の示し方:** テストで示す

確かめること:

- `sections` の各名前が、`**対象仕様:**` のどれかの「該当する節」と一致すれば受け付ける
- 一致しない名前が 1 つでもあれば、どの名前が一致しないかを含む失敗で拒否する
- 比べるのは節の名前そのもの。`**対象仕様:**` 側の「 」は含めない
- `clauses` という欄を持つ古い JSON は「欄が違う」として拒否する
- `sections` が空の配列なら拒否する

**実装側に任せてよい選択:** 読み取り結果の型で `sections` をどう持つか（タプルか、
別の小さな型か）。どちらでも振る舞いは変わらない。

**止まる条件:** `**対象仕様:**` の読み取り（手順 2）が無いとこの手順の突き合わせが
書けない、と分かった場合は、手順 2 の読み取り部分を先にこの手順の中で最小限に作ってよい。
ただしその場合も、手順 2 で確かめる内容は手順 2 で別に確かめる。

### 2. 手順書の冒頭（ID、版、参照する仕様書）を読み、指紋の一致を確かめる

**目的:** `docs/spec/plan.md` の「implement が機械的に読む箇所」のうち、`**Plan ID:**`、
`**Plan revision:**`、`**対象仕様:**`（パス・内容identity・該当する節）を読む処理を作る。
さらに、書かれた指紋が、そのパスにいま置かれている仕様書の指紋と一致することを確かめる。

**前提:** 手順 1 が終わっている。

**変更してよい範囲:** `skills/ba0918-plan/scripts/plan_artifact.py`、`tests/plan_artifact_test.py`。

**完了の示し方:** テストで示す

確かめること:

- `**Plan ID:**` と `**Plan revision:**` が読めて、`draft` / `publish` に渡した ID と版に一致する。
  一致しなければ拒否する
- `**対象仕様:**` の各項目から、パス、`sha256:` で始まる指紋、「 」で囲まれた節の名前の一覧が
  読める
- 指紋が、リポジトリ内のそのパスのファイルの指紋と一致すれば通る。一致しない、または
  ファイルが無ければ、どのパスが一致しないかを含む失敗で拒否する
- パスはリポジトリの中の相対パスに限る。`..` や絶対パスは拒否する
- `**対象仕様:**` が無い、項目が 1 つも無い、指紋の形が違う、のどれでも拒否する

**実装側に任せてよい選択:** 読み取り結果をまとめる型の名前と構成。

**止まる条件:** 仕様書に書かれていない形（たとえば 1 つのパスに複数の指紋）をどう扱うか
決めたくなったら止まる。拒否するのが既定。

### 3. 変更してよい範囲の木と、手順ごとの「完了の示し方」を読む

**目的:** 残りの機械的に読む箇所を読む処理を作る。`## 変更するもの` の下の `text` の
コードブロックをファイルの木として読む。`## 実装手順` の下の `### 1.`、`### 2.` … を手順として
読み、各手順の `**完了の示し方:**` が 3 種類（テストで示す / 作った物で示す / 外で確かめる）の
どれかであることを確かめる。

**前提:** 手順 2 が終わっている。

**変更してよい範囲:** `skills/ba0918-plan/scripts/plan_artifact.py`、`tests/plan_artifact_test.py`。

**完了の示し方:** テストで示す

確かめること:

- ファイルの木は、字下げで階層、ディレクトリは末尾 `/`、パスはリポジトリ相対として読め、
  展開した相対パスの一覧が返る
- 木の中に注釈（`#` や空白以外の余分な文字）、絶対パス、`..` があれば拒否する
- `## 変更するもの` の下にコードブロックが無い、または空なら拒否する
- 手順見出しは `### 1.` から 1 ずつ増える。抜けや重複があれば拒否する
- 各手順に `**完了の示し方:**` がちょうど 1 つあり、3 種類のどれかである。無い、2 つある、
  別の言葉、のどれでも拒否する
- `## 実装手順` が無い、手順が 1 つも無い、のどちらでも拒否する

**実装側に任せてよい選択:** 木の字下げの幅（2 でも 4 でも、一貫していれば受け付ける）。

**止まる条件:** 仕様書の例と違う木の書き方（たとえば `├──` の罫線）を受け付けるか決めたく
なったら止まる。受け付けないのが既定。

### 4. 草稿の保存と正本への移動で、書式と指紋の検査を行う

**目的:** `docs/spec/plan.md` の「草稿と承認」の手順 1 と 4 に合わせる。`draft` は、手順 1〜3 の
読み取りがすべて通ってから草稿を保存する。`publish` は、草稿の指紋が提示したものと同じである
ことに加えて、同じ検査にいまも通ることを確かめてから移動する。どちらも、通らなければ何も
書かず、どの箇所がどう読めないかを返す。

**前提:** 手順 1〜3 が終わっている。

**変更してよい範囲:** `skills/ba0918-plan/scripts/plan_artifact.py`、`tests/plan_artifact_test.py`。

**完了の示し方:** テストで示す

確かめること:

- 検査に通る手順書は、これまでどおり保存・移動・登録される
- 6 箇所のどれかが読めない手順書は、`draft` で保存されない。コマンドの出力に、読めない箇所の
  説明が含まれる
- 参照する仕様書の指紋が一致しない手順書は、`draft` で保存されない
- `publish` の時点で仕様書が変わっていれば（草稿の指紋は同じでも）、移動も登録もされず、
  草稿は残る
- 既存のテスト（指紋の不一致、いま対象の切り替え、未コミットの変更での停止）は変わらず通る

**実装側に任せてよい選択:** 検査の失敗を 1 つの例外型にまとめるか、箇所ごとに分けるか。
出力に箇所の説明が含まれれば、どちらでもよい。

**止まる条件:** `identity` コマンド（保存せずに指紋だけ返す）にも検査を入れるか決めたく
なったら止まる。入れないのが既定（指紋を返すだけの役目のため）。

### 5. plan skill の本文を新しい仕様書に合わせる

**目的:** `skills/ba0918-plan/SKILL.md` と `references/` の 3 本を、改訂した `docs/spec/plan.md`
の内容に合わせる。具体的には次を反映する。

- 参照する仕様書の書き方（`**対象仕様:**` にパス・指紋・該当する節）と、条文 ID を使わないこと
- 各手順に `**完了の示し方:**` を 3 種類から 1 つ書くこと。選び方は `docs/spec/workflow.md` の
  「plan → implement」の節に従う
- 人が判断する場面の JSON の `sections` と、その突き合わせの規則
- 変更してよい範囲の木の書式
- `draft` と `publish` が書式と指紋を検査し、通らなければ AI が直して保存し直すこと
- 手順書の機械的な読み取りは `plan_artifact.py` が 1 か所で持ち、implement はそれを使うこと
- `references/readability.md` の確認項目を、利用者の読みやすさの規則（`ba0918-readability`。
  ROADMAP Phase 3.5 が「基準はこれで、新しい契約は作らない」と定めている）と矛盾しない形に
  直すこと。具体的には「すべての技術用語を初出で説明する」を「このプロジェクトの中でしか
  通じない言葉と参照は、名前を出す前に意味を言う。広く通じる技術用語はそのまま使い、
  1 つの文書で説明は 1 回」に改め、「根拠が足りないことは、足りないと書く」を足す。
  `readability.md` 自体は残す（この skill は単体で配布するので、利用者の環境にある規則を
  読める前提にしない）

書く言語は `PROJECT.md` の決まりどおり英語（AI が読む文書のため）。

**前提:** 手順 4 が終わっている（本文が説明するコマンドの振る舞いが先に存在している）。

**変更してよい範囲:** `skills/ba0918-plan/SKILL.md`、`skills/ba0918-plan/references/creation.md`、

**完了の示し方:** 作った物で示す

**実装側に任せてよい選択:** 文章の構成と分量。`docs/spec/plan.md` の節の並びに合わせる必要はない。

## 人が判断する場面

| 場面 | 人が決めること |
|---|---|
| この手順書の承認 | このファイルを、この指紋のまま正本にしてよいか |
| 手順 5 の本文の確認 | 4 つのファイルを読んで、仕様書と食い違いが無いか |
| 手順 6 の結果 | 報告を読んで、plan skill の改修を完了とするか |

手順の途中で人の「はい / いいえ」を機械的に待つ箇所（`**Human gates:**` の宣言）は、
この手順書には置かない。手順 5 と 6 の確認は「作った物で示す」の完了条件そのものであり、
別の宣言を重ねない。

## 失敗したらどこで止まるか

- テストで示す手順で、失敗するテストが書けない（既に通ってしまう）なら、その手順が既存の
  振る舞いを確かめようとしている。テストを直す
- 手順書に無い振る舞いを決めたくなったら止まり、brainstorm に戻す
- 手順 6 で自分の手順書が読めなければ、読み取りか手順書のどちらかが間違っている。
  人に報告して、どちらを直すかを決めてもらう
