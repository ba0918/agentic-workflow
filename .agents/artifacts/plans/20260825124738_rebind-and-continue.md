三つの仕様書の役割: `workflow.md` の「止まっても続けられる」は、指紋の不一致で止まっても実行は
死なず、読む・止まるは指紋に関係なくでき、予定に無い事実は止める理由ではなく人に見せる事実で
ある、という横断の約束で、この手順書はその約束のうち implement が担う部分を実装する。
`implement.md` は implement の振る舞いそのものを定め、この手順書が変える 4 点 — 束ね直して
続ける選択肢、読む・止まる操作を指紋の検査から外すこと、範囲外の未コミット変更を止める理由に
しないこと、終端で証拠の外のコミットを列挙して人が承認すること — の意味と制限を決めている。
`plan.md` は、手順書の改訂で古くなった証拠は捨てる物ではないこと、いま対象の手順書を切り替える
ときに作業ツリーの未コミットの変更を止める理由にしないことを決めており、この手順書は後者を
plan の補助スクリプトから外す。

## この手順書の言葉

- **手順書**: この文書のように、plan が作り、人が承認し、implement が実行する文書。改訂すると
  新しい版が新しいパスにでき、索引（`.agents/artifacts/plans/open-plans.json`）の項目が
  新しい版を指す。古い版のファイルは残る。
- **指紋**: ファイルや記録の内容から計算した SHA-256 の値（`sha256:` で始まる文字列）。
  承認したときから変わっていないことを機械的に確かめるために使う。
- **実行と証拠**: implement が 1 つの手順書を 1 回実行する単位が実行で、実行 ID、ブランチ
  `implement/<実行 ID>`、作業ディレクトリ（git worktree）が結び付く。証拠は
  `.agents/artifacts/executions/<手順書 ID>/<実行 ID>/` に置かれ、`binding.json`（束ねの記録。
  どの手順書と仕様書の指紋に基づくか、書き込み範囲、宣言された人の判断）と、番号順に追記する
  出来事のファイル（`000001-worktree-bound.json` のような 1 件 1 ファイル）からなる。
- **出来事の連鎖**: 各出来事は、実行 ID、手順書の指紋、仕様書の指紋、直前の出来事の指紋を
  持ち、直前の出来事と食い違うと連鎖が壊れているとして読めなくなる。いまは全出来事で手順書と
  仕様書の指紋が同じでなければならない。
- **有効な束ね**: `binding.json` に、後から記録した束ね直しの出来事を重ねて得られる「いま
  この実行が基づいている手順書・仕様書・書き込み範囲・宣言された判断」。束ね直しが無ければ
  `binding.json` そのもの。この手順書で導入する言葉。
- **手順の文面の指紋**: 手順書の `### N.` の見出しと本文の内容から計算した指紋。手順の番号は
  含めない。改訂の前後で同じ手順かどうかを、番号ではなくこれで突き合わせる。
- **書き込み範囲**: 手順書の `## Scope` に書かれた、implement が変更してよいファイルの木。
  範囲内・範囲外はこれで決まる。
- **証拠で説明できないコミット**: ブランチの始点から先端までのコミットのうち、`commit` の
  出来事に SHA が記録されていないもの。
- **正本と複製**: implement と plan の補助スクリプトの正本は `tools/workflow-runtime/` にあり、
  skill ディレクトリ `skills/ba0918-implement/scripts/` と `skills/ba0918-plan/scripts/` には
  配布用の複製が置かれる。複製は `bunx agentic-skill-vendor gen` が正本から作り、`verify` が
  一致を検査する。手で複製を直さない。implement の複製は plan の複製の `plan_artifact.py` を
  読み込む。

## 目的

5.2 の brainstorm で、仕様書とスクリプトの止まる箇所を全部洗い出したところ、止まると実行ごと
失う箇所が implement に 2 つあった。

- 手順書を改訂すると、束ねの指紋が索引と合わなくなり、記録から状態を組み立て直す `load` の
  段階で拒否される。`load` を通らないと `stop` も `context` も動かないので、止まったことすら
  記録できず、「新しく始める」しか残らない。「手順書を直したら全部やり直し」の正体
- 終端（`implementation-green`）は、ブランチの全コミットが `commit` の出来事と 1 対 1 で
  対応しないと通らない。再開（`resume`）は証拠の外のコミットを事実として見せるだけで許すので、
  「再開はできるが永遠に終われない」実行ができる

さらに、仕様書が「範囲外の未コミット変更は残る」と約束しているのに、`context` は作業
ディレクトリに範囲外の変更が 1 つでもあると拒否していた。

仕様書はこれらを決め直した（読む・止まるは指紋に関係なくできる / 指紋の不一致は「新しく
始める」と「束ね直して続ける」の 2 択 / 範囲内の未コミット変更は止める理由、範囲外は事実 /
終端は説明できないコミットを列挙して人が承認する）。この手順書はそれを implement の補助
スクリプトと文書に反映し、あわせて plan の切り替え時の作業ツリーの汚れ検査を外す。

## 利用者が得る結果

- 手順書を改訂したあと、同じ手順書 ID で implement を起動すると、残っている実行に対して
  「新しく始める」だけでなく「束ね直して続ける」が選べる。選ぶと、改訂前後の手順を文面の指紋で
  突き合わせた表（持ち越す / やり直す / 新しい / 続きから）が出て、人が続けると言えば束ね直しの
  出来事が 1 つ記録され、文面の変わっていない完了済みの手順はやり直さずに続く
- 手順書や仕様書が承認時から変わっていても、残っている実行を見る（`residual`）、記録から
  組み立て直す（`load`）、止まったと記録する（`stop`）はできる。書き進める操作（`context`
  以降）だけが指紋を見る
- 手順書の範囲外のファイルに未コミットの変更があっても、`context` は止まらない。範囲外の変更は
  事実として答えに含まれる
- 終端で、証拠で説明できないコミット、履歴の差分に含まれる範囲外のパス、範囲外の未コミット
  変更が列挙され、人が「意図した物」と承認すると終わる。範囲内の未コミット変更（コミットし忘れ）
  だけは今までどおり止まる
- いま対象の手順書を切り替えるとき、作業ツリーに未コミットの変更があっても止まらない

## 外部への影響と、主なリスク

- 外部サービスとの入出力は無い。ネットワークにも触れない
- **review 側が追いつくまで、束ね直した実行は review を始められない。** review の `bind` は
  `binding.json` の手順書の指紋を索引と比べるので、束ね直した実行（`binding.json` は古い指紋
  のまま）は `plan_drift` で拒否される。review が有効な束ねを読む変更は review 側の手順書で
  行う。それまでは、束ね直した実行を終端まで進めることはできるが review に渡せない。文書に
  その旨を書く（手順 6）
- **過去の証拠は連鎖の規則の変更で読めなくならない。** 変更は「束ね直しの出来事のときだけ
  指紋の変化を許す」であり、束ね直しの無い過去の連鎖は今までと同じ規則で検証される。手順 1 の
  テストで、既存の連鎖がそのまま読めることを確かめる
- **やり直す手順の古いコミットは履歴に残る。** 文面が変わった完了済みの手順をやり直すと、古い
  コミットと新しいコミットが両方ブランチにある。古いコミットは証拠で説明できないコミットに
  なり、終端で列挙されて人が承認する。仕様書の「コミットは残し、消すかどうかは人が決める」
  のとおりで、この手順書が新しく決める意味ではない
- **改訂前の手順書のファイルが無いと束ね直せない。** 手順の突き合わせには改訂前の文面が要る。
  改訂前の版は `binding.json` が指すパスに残っているのが普通だが、消されていたら束ね直しは
  「改訂前の手順書が読めない」と答えて拒否し、「新しく始める」だけが残る。5.4 で終わった手順書を
  git の履歴へ移すときに、この前提を見直す
- **範囲外の変更を `context` が止めなくなるので、AI が手順の途中で範囲外を触っても、その場では
  気づかない。** 範囲を守るのはコミットの境界（`stage` が範囲外を拒否する）と終端（列挙して
  人が承認する）に移る。仕様書がそう決めている
- 正本を直したあと複製の同期を忘れると、配布される skill が古い振る舞いのままになる。手順 7 で
  `gen` と `verify` を通す

## 仕様書にあって、この手順書が値を決めないこと

- **出来事の記録形式**（フィールド名、対応表の並び）: 仕様書は「既存の出来事と同じ方式で実装が
  決める」としている。この手順書は、各出来事が最低限持つ内容だけを手順 1 に書く
- **束ね直しのコマンドの形**: 表を見せる段階と記録する段階を 2 つのコマンドにするか、1 つの
  コマンドの引数で分けるかは実装に任せる。どちらでも「人が表を見てから記録する」順序が守られる
- **手順の文面の指紋の正規化**: 見出しと本文の空白の扱い（行末の空白、改行の違い）を無視するか
  どうかは実装に任せる。「番号を含めない」ことと「見出しと本文の両方を含める」ことだけを決める
- **終端の承認の理由の上限**: 他の文章の欄と同じ上限（いま 500 文字）を流用する

  テスト名は振る舞いを書く。手順ごとに 1 コミット。コミットの本文には「なぜ」を書く
- 既存のテストのうち、この手順書が変える振る舞いを固定しているもの（手順書の指紋の不一致で
  `load` が止まる、範囲外の変更で `context` が止まる、切り替え時の汚れで止まる）は、新しい
  振る舞いを言う名前に改める。消すだけにしない
- 手順書に無い振る舞いが必要になったら、止まって brainstorm に戻す
- テストの中で秘密情報に似た文字列が要るときは、実行時に文字列を連結して組み立てる（implement の
  コミット前の走査が、ファイル全体を秘密情報の判定にかけるため）

## Steps

### 1. 束ね直しと終端の承認の出来事を連鎖に足し、有効な束ねと手順の対応を導く

**目的:** 仕様書 `implement.md` の「証拠の残し方」「選んだあと」「完了と引き渡し」と、
`workflow.md` の「止まっても続けられる」に合わせる。`execution_model.py` の、ファイルにも git
にも触らない部分だけを変える。

- 出来事の種類に `rebound`（束ね直し）と `history_approved`（終端の承認）を足す。`rebound` が
  最低限持つ内容: 改訂後の手順書（ID、パス、版、指紋）、参照する仕様書の指紋、改訂後の書き込み
  範囲と宣言された人の判断（`binding.json` が持つのと同じ項目）、手順の対応表（改訂後の各手順に
  ついて、改訂前のどの手順に対応するかと、持ち越す / やり直す / 新しい / 続きから のどれか）、
  そのときのブランチの先端、証拠で説明できないコミット、未コミットの変更の有無。
  `history_approved` が最低限持つ内容: 承認した「証拠で説明できないコミット」の一覧、履歴の
  差分に含まれる範囲外のパスの一覧、範囲外の未コミット変更の一覧、任意の理由
- 連鎖の規則: `rebound` の出来事は、自分の手順書の指紋と仕様書の指紋を、直前の出来事と違う値に
  できる（その値は自分が持つ改訂後の手順書と仕様書の指紋と一致しなければならない）。それ以外の
  出来事は今までどおり直前と同じでなければならない。`stopped` のあとには `resumed` に加えて
  `rebound` も追記できる。`implementation_green` が終端であることは変わらない
- 有効な束ねを導く関数: `binding.json` の内容に、最後の `rebound` の手順書・仕様書・書き込み
  範囲・宣言された判断を重ねたものを返す。`rebound` が無ければ `binding.json` の内容そのもの
- 手順の対応を反映した出来事の見方を導く関数: 最後の `rebound` より前の出来事は、対応表に
  従って手順 ID を改訂後の番号に付け替える。対応表で「やり直す」とされた手順と、改訂後に対応の
  無い手順の古い出来事は、この見方からは除く（ファイルは残る）。`rebound` より後の出来事は
  そのまま。手順ごとの証拠の判定（`validate_step_evidence`）と、次に進む手順の導出は、この
  見方に対して行う

- `rebound` 以外の出来事が直前と違う指紋を持つと、今までどおり `stale_event_chain` で拒否される

- `stopped` のあとに `rebound` を追記できる。`implementation_green` のあとには追記できない
- 束ね直しの無い既存の出来事の列（`worktree-bound` から `implementation_green` まで）が、
  変更前と同じく読める
- 有効な束ねは、`rebound` があれば最後の `rebound` の手順書・仕様書・書き込み範囲・宣言された
  判断を返し、無ければ `binding.json` の内容を返す
- 対応表で「持ち越す」とされた手順の古い出来事は改訂後の番号で数えられ、`test` の手順として
  完了と判定される。「やり直す」とされた手順の古い出来事は数えられず、未完了と判定される。
  番号が 1 つずれた（途中に手順が挿入された）対応表でも同じ

**実装側に任せてよい選択:** フィールドの名前、対応表の並び、有効な束ねと見方を返す関数の名前と
戻り値の形。

**止まる条件:** `binding.json` そのものを書き換えたくなったら止まる（仕様書が「変えない
ファイル」と決めている）。連鎖の規則の変更が、束ね直しの無い既存の連鎖の検証結果を変えると
分かったら止まる。

### 3. 束ね直して続ける

**目的:** 仕様書 `implement.md` の「残っている作業があるとき」「選んだあと」と、`workflow.md`
の「止まっても続けられる」「人の判断の置き場」に合わせる。

- 束ね直しは 2 段階。まず、改訂前の手順書（`binding.json` が指すパス）と改訂後の手順書（索引が
  指す現在の版）の手順を、手順の文面の指紋で突き合わせ、対応表を人に見せる。改訂後の各手順に
  ついて: 文面が同じ改訂前の手順があり、それが完了（`commit` の出来事あり）なら「持ち越す」、
  未完了なら「続きから」。文面が同じ手順が無ければ「新しい」。改訂前で完了していたが改訂後に
  文面が同じ手順が無い物は「やり直す」（改訂後の手順の側から見れば「新しい」と同じで、古い
  コミットが履歴に残る旨を表に書く）。次に、人が続けると言ったら `rebound` の出来事を記録し、
  次に進む手順（対応を反映した見方で、`commit` の出来事が無い最初の手順）を返す
- 束ね直しの相手は、索引に登録されている（人が承認した）手順書と、その手順書が参照する仕様書
  だけ。手順書 ID が違う、索引に無い、仕様書の指紋が手順書の参照と合わない、のどれかなら拒否
- 改訂前の手順書のファイルが読めなければ、理由を返して拒否する（「新しく始める」だけが残る）
- 改訂で書き込み範囲が狭まっていても、束ね直しの時点では止めない
- `rebound` のあとの `context`、`stage`、`record-commit` は改訂後の手順 ID で動き、持ち越した
  手順は再実行を求められない

### 4. 終端で、証拠で説明できないコミットと範囲外の変更を列挙し、人の承認で終わる

**目的:** 仕様書 `implement.md` の「完了と引き渡し」「コミット」と、`workflow.md` の
「止まっても続けられる」「人の判断の置き場」に合わせる。

- 終端（`implementation-green`）は、ブランチの始点から先端までのコミットを `commit` の

  列挙して「承認が要る」と答え、`stopped` は書かない

  要らず、今までどおり終わる
- 範囲内の未コミット変更があれば、今までどおり `post_verification_dirty` で止まる
  （コミットし忘れ）。記録した `commit` の出来事の SHA が履歴に無ければ、今までどおり止まる
