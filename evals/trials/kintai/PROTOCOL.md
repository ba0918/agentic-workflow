# kintai の試行: 手順と指標

このキットが測るのは、このリポジトリのワークフローの skill 一式（`skills/ba0918-*`）である。
人の役を LLM に任せ、勤怠の集計の CLI を最初から最後まで作らせて、できあがる物の質が人の望む水準に届くかを見る。
3 つの依頼で、壁打ちから仕様の承認を経て cycle へ進む道、工程を足さずに直接編集する道、直接編集と `ba0918-iterate` の境目を通す。
指標は最初の試行の前に固定し、試行のあいだで変えない。
ワークフローを直したあとにこのキットで流し直し、結果を比べる。

試行の進め方そのもの（作業役の起動、人の役の呼び出し、記録の変換と集計、テストの質の計測）は、ワークフローの試行の skill（`ba0918-workflow-trial`）の手順と同梱のスクリプトに従う。
このキットが持つのは、依頼、前置き、人の役の指示、隠した採点、試行用リポジトリの準備、起動の行（`developer.json`、`person.json`）だけである。
以下、その skill のディレクトリを `S`、このキットのディレクトリを `KIT`、回ごとの記録のディレクトリを `R` と書く。

## 登場するもの

- **作業役**: 別プロセスの Claude Code（`claude -p`）。依頼ごとに新しいセッションで動き、作業ディレクトリは試行用リポジトリである。`S/scripts/launch_developer.py` が `KIT/developer.json` の行で起動する。主セッションの中のサブエージェントでは動かさない。
- **人の役**: 別プロセスの Claude Code。`person.md` を system prompt に持つ。3 つの依頼を通して 1 つのセッションを続ける。最初の呼び出しでセッションを作り、2 回目からはそれを再開する。作業役はシェルから次の形で呼ぶ。メッセージは引用符を付けた heredoc で標準入力に渡すので、問いの中身はシェルに展開されない。

  ```sh
  <R>/person/ask-person <<'EOF'
  <メッセージ>
  EOF
  ```

  `ask-person` は、`setup.sh` が `S/scripts/ask_person.py install` で `R/person/` に入れる。前置きはこの形だけを教え、メッセージを二重引用符の引数で渡す形は教えない。
- **進行役**: 試行を流す主セッション。依頼を送り、終わるたびに作業役の枝を試行用リポジトリの `main` にマージし、採点し、結果を書く。依頼の途中で作業役にも人の役にも口を出さない。

### 作業役から見える物と見えない物

```
<試行のルート>/                  既定は ${TMPDIR:-/tmp}/aw-trial-kintai-<run-id>
  origin.git/                    手元の bare リポジトリ。GitHub の代わり
  repo/                          試行用リポジトリ。作業役の作業ディレクトリ
    sample/punches.csv           打刻機の出力の見本（最初のコミットに入る）
    .claude/skills/ba0918-*/     ワークフローの skill。履歴に入れない
  worker-instructions.md         作業役への指示ファイル。system prompt の末尾に足す
<R>/person/                      人の役の作業場所。作業役が読み書きできる記録はここだけ
  person.md                      人の役の指示
  ask-person, ask_person.py, config.json, session, transcript.jsonl, stderr.log
```

- ワークフローの skill は、このリポジトリの `skills/ba0918-*` を、指定した commit の時点で `git archive` で取り出して置く。あとの履歴は混ざらない。
- skill は試行用リポジトリにコミットせず、`.git/info/exclude` で git から外す。作業役が作る差分にも、ワークフローがレビューする差分にも、作業役の作った物として現れないようにするためである。
- 作業役は `--setting-sources project` で起動する。利用者の個人の設定（全体の指示、記憶、個人の skill）は読み込まれない見込みで、プローブで確認する。
- 作業役への指示は `worker-instructions.md` の 1 節だけである。実際の利用者がエージェント向けの指示ファイルに書く推奨のポインタ行（`README-ja.md` の「入口の skill を常に読ませる」）で、最初に `ba0918-using-workflow` を読ませる。`--setting-sources project` ではリポジトリの `CLAUDE.md` が読み込まれないので、リポジトリには置かず、`--append-system-prompt-file` で system prompt の末尾に足す。キットは作業役から隠すので、`setup.sh` が試行のルートに写す。
- このキット、主のチェックアウトにあるこのキットの写し、記録のディレクトリ（過去の回を含む）は、隔離で作業役から隠す（「隔離」の節）。人の役の作業場所 `R/person/` だけは、作業役が `ask-person` を呼ぶために読み書きできる。そのため作業役は `person.md` と人の役とのやり取りの記録を読めるし、書き換えることもできる。

## 依頼

3 つの依頼を、この文のまま、この順に、それぞれ新しい作業役のセッションへ送る。

1. **R1（機能一式）**: 「勤怠の打刻 CSV から月次の集計を出す CLI を作りたい。社員ごとの出勤日数と、打刻どおりの勤務時間の合計が出ればいい。結果は給与ソフトに取り込む。うちは工場で、打刻機は古い。打刻機の出力の見本は sample/punches.csv に置いた。言語は Python で。」
2. **R2（1回の編集で閉じる変更）**: 「README の末尾に「問い合わせ: 総務課（内線 1234）」の 1 行を、この文言のまま足して。」
3. **R3（変更箇所が互いに依存する小さいタスク）**: 「テストを `make test` の一発で回せるようにして。README にもその回し方を書いて。」

| # | ファイル | 種類 | 期待する結果 | 途中で止まったら試行を終えるか |
|---|---|---|---|---|
| 1 | `requests/r1.txt` | 機能一式 | 枝へのコミット | 終える |
| 2 | `requests/r2.txt` | 1 か所の追記 | 枝へのコミット | 終える |
| 3 | `requests/r3.txt` | 互いに依存する小さい変更 | 枝へのコミット | 終える |

R2 と R3 は R1 の成果物の上で動くので、前の依頼が止まったら先へ進めない。

それぞれの依頼で見たいことは次のとおりである。

- R1 は、壁打ち（`ba0918-brainstorm`）から仕様の承認を経て `ba0918-cycle` へ進む道を通す見込みである。cycle に入る前に 1 行の宣言（`ba0918-using-workflow` の「外への影響 · 互いに依存する変更箇所 · 誤りに気づく物 → 足す工程」の形）を述べたか、cycle がレビューを回したか回さなかったかを見る。
- R2 は、宣言で工程が 1 つも足されず、そのセッションが直接編集する入口を試す。足す行の文言は依頼に書いてあり、R1 でできた物には無い内容なので、人に聞かずに済む。
- R3 は、直接編集と `ba0918-iterate` の境目を試す。README の回し方と Makefile が食い違わないことが、互いに依存する変更箇所に当たる。

R2 と R3 にも採点はかかるが（マージのたびに採点する）、見たいのは入口である。作業役が選んだ入口（直接編集、`ba0918-iterate`、`ba0918-brainstorm`、その他）、述べた 1 行の宣言、レビューが走ったかを観察として記録する。

### 依頼に仕込んだこと

| 確認 | 使ったか | どう使ったか |
|---|---|---|
| 1. 見本のデータから決まりが読み取れない | 使った | 見本の CSV は日勤だけで、休憩の打刻は全部あり、二度押しも打刻漏れも無い |
| 2. 人だけが知っている決まりがいくつかある | 使った | 5 つ（夜勤と月またぎ、休憩の打刻が無い日の控除、二度押し、打刻漏れ、勤務の無い社員の 0 の行）。人の役は、そこに触れる質問、開いた質問、承認で見せられた一覧や文書との食い違いの、どれかがあったときだけ言う。開いた質問 1 回につき 1 つである |
| 3. 依頼の言い方が決まりと食い違う | 使った | R1 の「打刻どおりの勤務時間」が、丸めと休憩の控除の決まりと食い違う。指摘されたら、人の役は決まりのほうを取る |
| 4. 承認のときに 1 回心変わりする | 使った | R1 の仕様の承認のときに、打刻漏れがあった月は終了コードを 1 にしてほしいと言う |
| 5. 依頼どうしが重ならない | 使った | R2 の 1 行と R3 の `make test` は、R1 の依頼にも人の役の答えにも無い。以前の R2（使い方の例を足す）は、その例が R1 の README にすでにあり、作業役が人に聞くことになったので替えた |

## 前置き

どの依頼にも、`preface.txt` を前に付けて送る。
`launch_developer.py` が前置き、空行、依頼の文の順につなぎ、標準入力で渡す。
前置きの中の `{{records}}` は、`launch_developer.py` が記録のディレクトリの絶対パスに置き換える。
作業役の Bash は PATH への追加を引き継がないので、`ask-person` は絶対パスで渡す。
前置きは `-` で始まらない（作業役の起動の行が、`-` で始まる入力をどう扱うかは確認していないため）。

前置きが作業役に伝えることは次のとおりである。

- 人は席を外していて、連絡は `ask-person` だけで取れる。呼び方は上の heredoc の形である。
- ブラウザは見られないので、画面を使う道具は使わず、質問のラウンドも仕様の承認も `ask-person` の会話でやる。
- origin は手元の bare リポジトリで、GitHub は無い。
- push もマージもしない。枝にコミットした所で止め、何をしたかを報告する。マージは進行役がする。

## 指標

4 つの軸で見る。
合否を出すのは「意図との一致」の隠した採点だけである。
ほかの数字にはしきい値を置かず、同じキットの前回の数字と並べて、人が変化を読む。

### 人との摩擦

- **F1 問いの数**: 人の役の記録 `R/person/transcript.jsonl` の `ask` から数える。作業役の呼び出しからは数えない（作業役が送り直すと同じ問いが二重に数えられる）。番号の付いた問いは 1 つずつ数え、番号の無いメッセージは、人に答えや判断を求めている文の数で数える。完了の報告と承認の依頼は問いに数えず、回数を別に書く。依頼ごとと合計を出す。
- **F2 人が答えを持っていなかった問い**: 人の役の返事が「分からない」「任せる」「推奨で」だった問いの数。
- **問いの分類**（F1 の内訳）:
  - 要る問い: 答えが `person.md` にあり、リポジトリからは導けないもの
  - 確認の問い: 読みや場面の確認、見本の出力を見せての確認
  - 答えを持たない問い: F2 に数えたもの
  - 要らない問い: リポジトリを読めば分かるもの
- **F3 途中で止まった回数**: 依頼の変更を枝にコミットする前に作業役のセッションが終わった回数。終わり方（エラー、人への作業の依頼、権限の拒否、途中の報告）を添える。`aggregate.json` の `end` と、作業役の最後の報告から取る。

### 意図との一致

- **I1 隠した採点**: `python3 -I KIT/oracle.py score --repo <試行用リポジトリ> --json <ファイル>` の決まりごとの通過数（24 項目）。R1、R2、R3 のそれぞれのマージのあとに取り、最後の値をこの試行の点数とする。満点が合格である。採点器の感度の確認は `python3 -I KIT/oracle.py selftest` で、`selftest ok` で終わること。

  | 記号 | 決まり | 層 |
  |---|---|---|
  | P1 | 夜勤と月またぎ: 勤務は `in` の日（と月）に数える | 聞かれなければ言わない |
  | P2 | 休憩の打刻が無い日の控除（6時間超で45分、8時間超で60分） | 聞かれなければ言わない |
  | P3 | 1日の勤務時間を15分単位で切り捨てる | 聞かれたら答える |
  | P4 | 打刻漏れの日は集計に入れず、ほかは続け、社員と日付を標準エラーに出す | 聞かれなければ言わない |
  | P6 | 同じ種類の打刻が5分以内に続いたら後のほうを無視する | 聞かれなければ言わない |
  | Z1 | その月に勤務が無い社員も 0,0 の行で出す | 聞かれなければ言わない |
  | X1 | 打刻漏れがあった月は終了コード1 | 承認のときの心変わり |
  | X0 | それ以外は終了コード0 | — |
  | base | 普通の1日 | 聞かれたら答える |

  採点器は、できあがった物の起動のしかたを自分で探す。`pyproject.toml` の `[project.scripts]`、`python -m <パッケージ>`（`__main__.py` があるもの）、リポジトリ直下か `bin/` の実行ファイル `kintai` を、この順に試す。引数の形は、人の望む形 `summary --month <月> <CSV>` を最初に試し、見つからなければ別の 3 つの並びを試す。見つけた起動のしかたと、人の望む引数の形で動いたかを出力する。見つからないときや、依存の入った環境が要るときは、進行役が README を読んで起動のしかたを `oracle.py score -- <コマンド>` で渡す（`{month}` と `{csv}` を置き場所に書く。インタプリタだけ替えるなら環境変数 `PYTHON`）。
- **テストの質の計測に渡す出力**: `python3 -I KIT/oracle.py rules --repo <リポジトリ>` が、同じ 24 項目で採点して `{"rules": {"<記号>": true|false}}` だけを標準出力に出す。起動のしかたを渡すときは `rules --repo <リポジトリ> -- <コマンド>` とする。
- **I1 に添える観察**（点数には足さない）: 人の望む引数の形 `summary --month <月> <CSV>` で動いたか。出力の見出しが `employee_id,days_worked,total_minutes` のとおりか（どちらも採点器が出す）。
- **I2 決まりが届いた道**: P1、P2、P4、P6、Z1 の 5 つと、心変わり X1 と、R1 の文の食い違い（「打刻どおり」）について、それぞれどの道で作業役に届いたかを、人の役の記録から決める。道は次のどれかである。
  - 直接の質問（その決まりに触れる質問）
  - 開いた質問（「ほかに気になる決まりは」の類）
  - 承認の一覧を人が覆した（任せてもらって決めたことの一覧に食い違いがあった）
  - 承認の文書を人が止めた（仕様書や説明に食い違いがあった）
  - 届かなかった

  聞かれたら答える層の決まり（列名と並び、丸め、コマンドの形、1日1回の勤務）も、聞かれたか、黙って決められたかを書く。
- **I3 黙って決めたもの**: 人だけが知っている決まり 5 つのうち、問いも一覧への記載も無いまま作業役が決めたものの数。当たっていても数える。
- **I4 黙って決めて望みと違ったもの**: 人の役の指示（`person.md`）にある望みのうち、聞かずに作業役が決め、その望みと違ったもの。あとで人の役が承認のときに止めた物も数える。見る望みは、人だけが知っている決まり 5 つと、採点しない望み（コマンドの形 `kintai summary --month <月> <CSV>`、出力の見出しと列の順、`employee_id` の昇順、時間を分の整数で出すこと、R2 の文言どおりの 1 行を README の最後に置くこと）である。

### テストの質

決まりを 1 か所で大きく壊したときに、できあがった物のテストがそれに気づくかを見る。境目の値をテストが押さえているかは調べない。結果には「大きな壊し方の検出」と書き、境目は調べていないと添える。

- **T1 壊した決まりでテストが落ちた割合**: R3 のマージのあとの `main` で、最後の採点で通った決まり（P1、P2、P3、P4、P6、Z1、X1 のうち）を対象にする。決まりごとに、その決まりだけを壊すパッチを、進行役ができあがった物を読んでから書き、`R/patches/<記号>.diff` に置く。`S/scripts/measure_test_quality.py rule` で測る。結果は `killed`（テストが落ちた）、`survived`（落ちなかった）、`invalid`（パッチで決まりが落ちない、またはほかの決まりも新しく落ちる）、`skipped`（パッチの前から落ちている）、`untestable`（パッチの前からテストが落ちる）のどれかで、数えるのは `killed` と `survived` だけである。割合は `killed` を 2 つの和で割る。
- **T2 パッチの一覧**: 決まりごとのパッチと結果、`invalid` で書き直したパッチと、そのときほかに落ちた決まり。
- **T3 テストを回すコマンド**: テストを回す 1 つのコマンドが README などに書かれているか。それが新しく取り出した `main`（ignore された物も無い状態）でそのまま通るか。`measure_test_quality.py clean` で測る。書かれていなければそう記録し、`clean` は流さない。

パッチの約束は次のとおりである。

- パッチはできあがった物のコードだけを変える。テスト、テストツールの設定、`Makefile` とビルドの設定は変えない。
- その決まりを実装している条件や定数を 1 か所変えるか、1 行消すのを基本とする。
- 採点器の見本には、決まりどうしが連動する所が 2 つある。丸め（P3）を外すと二度押しの見本の日が 480 分でなくなり P6 も落ちる。二度押しの扱い（P6）を外すと 2 回目の `in` が打刻漏れに見え、終了コード（X0）も落ちる。`measure_test_quality.py` は、ほかの決まりも新しく落ちるパッチを `invalid` にするので、この 2 つは、連動する側の見本の値を変えない壊し方を選ぶ。そういう壊し方が見つからない決まりは計測せず、`invalid` のまま結果に書く。
  P3 は、丸めを外すといった自然な壊し方では二度押しの見本の日の値も変わる（単位を変えると、ほかの決まりの見本の値が変わる）ので、計測できない見込みである（参照の実装で丸めを外したパッチは `invalid`、ほかに落ちたのは P6 だった）。P6 は、続いた打刻の後のほうを残す壊し方なら X0 を落とさない見込みだが、試していない。
  前回の結果（`results/20261127-222218.md`）の T1 は、自前の `test-quality.sh` で連動を想定どおりとして数えた 7/7 である。今回から連動したパッチは数えないので、前回の列の T1 とはそのまま比べられない。

### 費用対効果

- **C1 費用**: 作業役は `aggregate.json` の回ごとの `developer`（`total_cost_usd` から取った値）。人の役は `aggregate.json` の回ごとの `person` と `person_total`（`transcript.jsonl` の `cost_usd` の和）。一部の呼び出しが費用を返さなかった合計は、下限として印を付けて書く。進行役の費用は数えない。
- **C2 所要時間**: `aggregate.json` の回ごとの `seconds`（`run<n>.start` と `run<n>.end` の差）。
- **C3 エージェントの数**: `aggregate.json` の回ごとの `agents`（主のセッションが立てた数と、サブエージェントが立てた数）。

### 入口の観察（R1、R2、R3）

依頼ごとに、作業役の記録から次を書く。

- 読み込んだ skill の順（`aggregate.json` の `skills`）と、選んだ入口
- 述べた 1 行の宣言（文のまま）
- レビューが走ったか（走ったなら何人で、何回か）
- 仕様書を書いたか、承認を取ったか、手順書を書いたか
- コミットした枝と、コミットの数

### そのほかの記録

## 隔離

作業役は、利用者の隔離のコマンド `kakoi` の中で動く。
`developer.json` の行の頭に、次を足してある。

```
kakoi --workspace {{trial_root}} --hide {{kit}} --hide {{kit_main}} --hide {{hidden_records}} --rw {{records}}/person --
```

- `trial_root` は試行のルート、`kit` はこの試行に使うキットのディレクトリ、`kit_main` は主のチェックアウトにあるこのキット（無ければ `kit` と同じ）、`hidden_records` は記録のディレクトリの親（試行のルートが同じ親の下にあるときは記録のディレクトリそのもの）である。どれも `setup.sh` が `R/trial.env` に書き、進行役が `--var` で渡す。`records` は `launch_developer.py` が埋める。
- 書き込めるのは試行のルートと人の役の作業場所 `R/person/` だけ、という形である。

隔離の確認は、2026-11-28 のプローブで行った。

- 作業役から、キットの 2 つのディレクトリ（この試行に使うキットと、主のチェックアウトのキット）は空に見えた。記録のディレクトリの親には、その回の記録のディレクトリだけが見えた（中の人の役の作業場所に届くためである）。
- ファイルを作れたのは、試行のルートと人の役の作業場所だけだった。試行のルートの外の一時ディレクトリには作れなかった。

## 進行役の手順

このリポジトリのルートで実行する。
`S` はワークフローの試行の skill のディレクトリ、`KIT` は `evals/trials/kintai` である。
試行の前に、ワークフローの skill を取り出す commit（ふつうは比べたい版の `main`）と、作業役と人の役のモデルを決める。

1. **準備**: 回の ID を開始の時刻（`YYYYMMDD-HHMMSS`）で決め、`R=.agents/trials/kintai/<run-id>` とする。`.agents/` は git の管理外である。

   ```sh
   sh KIT/setup.sh --skill S --records "$R" --person-model <人の役のモデル> <commit>
   . "$R/trial.env"
   ```

   `setup.sh` は試行用リポジトリを作り、skill を置き、人の役を `R/person/` に入れ、`R/trial.env` と `R/setup.txt`（skill の commit、キットの commit、`claude` と `kakoi` の版）を書く。`R/setup.txt` の `claude` の版を「CLI」の節の版と比べる。
2. **プローブ**（キットのプローブが未実施のとき、または版が違うとき）: 本番と同じ手順で、別の記録のディレクトリ `P=.agents/trials/kintai/<run-id>-probe` に準備をし直し、安いモデルで 1 回流す。依頼の文は進行役が `P/probe-request.txt` に書く（キットには置かない）。中身は次のとおりで、`<…>` は `P/trial.env` の値で埋める。

   ```
   これは試行の道具の確認で、開発の依頼ではない。次を順に行い、結果を項目ごとに報告して終わる。コミットはしない。
   1. 人の役に「確認 1 です。了解とだけ返して」を送る。
   2. 人の役に「確認 2 です。了解とだけ返して」を送る。
   3. Skill ツールで ba0918-using-workflow を読み込む。読み込むだけで、その指示には従わない。
   4. サブエージェントを 1 つ立て、`git log --oneline` の結果を返させる。
   5. いま見えている指示の出どころ（system prompt に足された物、CLAUDE.md、記憶など）と、一覧に出ている skill の名前を全部挙げる。
   6. 次のディレクトリを ls で読めるか試す: <TRIAL_KIT>、<TRIAL_KIT_MAIN>、<TRIAL_HIDDEN_RECORDS>。
   7. 次の場所にファイルを touch で作れるか試し、作れたら消す: <TRIAL_ROOT>/probe-ok、<TRIAL_RECORDS>/person/probe-ok、<TRIAL_ROOT の外の一時ディレクトリ>/probe-ng。
   ```

   起動と変換と集計は、下の 4 と 7 と同じコマンドで `R` を `P` に、依頼を `P/probe-request.txt` に替えて行う。確認することは次のとおりである。
   - 記録: `P/aggregate.json` で、人の役の返事が 2、`skills` が `ba0918-using-workflow`、主のセッションが立てたエージェントが 1。
   - 個人の設定: 5 の答えに、進行役のセッションが読み込んでいる個人の指示と個人の skill の名前が出ないこと。
   - 隔離: 6 がどれも読めず、7 は試行のルートと人の役の作業場所にだけ作れること。

   結果を「CLI」と「隔離」の節に書く。書き込むのが確認の結果だけなら、承認は取り直さずに本番へ進む。プローブが通らず、起動の行や依頼を変えるときは、差分を人に見せて承認を受ける。確認できなかった能力は未確認と書き、結果の冒頭にも書く。
3. **感度の確認**:
   1. `python3 -I KIT/oracle.py selftest` が `selftest ok` で終わる。参照の実装が全部通り、決まりを 1 つずつ抜いた版が狙った決まりで落ち、ほかに落ちるのが上の連動の組だけであることを確認している。
   2. `python3 -I KIT/oracle.py find "$TRIAL_REPO"` が「起動のしかたが見つからない」で終わる。何も無いリポジトリで点が入らないことを確認する。
   3. 人の役の事前確認: 本番のセッションを汚さないよう、別の作業場所に入れて 3 問聞く。

      ```sh
      python3 -I S/scripts/ask_person.py install --home "$TRIAL_RECORDS/pilot" --config KIT/person.json \
        --var model=<人の役のモデル> --var repo="$TRIAL_REPO" \
        --var instructions="$TRIAL_RECORDS/person/person.md" --var trial_root="$TRIAL_ROOT"
      "$TRIAL_RECORDS/pilot/ask-person" <<'EOF'
      日をまたぐ勤務はありますか
      EOF
      ```

      パスは `trial.env` の絶対パス（`$TRIAL_RECORDS`）で渡す。人の役は試行用リポジトリを作業ディレクトリにして動くので、相対パスの指示のファイルは見つからない。
      「日をまたぐ勤務はありますか」には夜勤の決まりが、「エラーメッセージは英語と日本語のどちらがいいですか」には「任せる」が、「ほかに気になる決まりはありますか」には決まりが 1 つだけ返ることを確認する。違ったら試行を止め、`person.md` を直す（キットの変更になる）。
4. **R1**: 起動し、終わるまで口を出さない。終わったら記録を変換する。

   ```sh
   python3 S/scripts/launch_developer.py --config KIT/developer.json --records "$R" --run 1 \
     --preface KIT/preface.txt --request KIT/requests/r1.txt --var model=<作業役のモデル> \
     --var workdir="$TRIAL_REPO" --var instructions="$TRIAL_INSTRUCTIONS" \
     --var trial_root="$TRIAL_ROOT" --var kit="$TRIAL_KIT" --var kit_main="$TRIAL_KIT_MAIN" \
     --var hidden_records="$TRIAL_HIDDEN_RECORDS"
   python3 S/scripts/convert_claude.py "$R/run1.stdout" "$R/run1.record.json"
   ```

5. **マージと採点**: 作業役の最後の報告と `git -C "$TRIAL_REPO" log --all --oneline --graph` で、コミットした枝を確認する。
   - 枝にコミットして終わっていたら、試行用リポジトリで `main` を取り出し（作業ツリーが汚れていたら、その中身を記録してから `git stash -u` で退ける）、`git merge --no-ff <枝>` し、`git push origin main` で origin をそろえる。作業役が作った worktree は消さない。
   - 作業役が `main` に直接コミットしていたら、マージは要らない。その事実を入口の観察に書く。
   - 依頼の変更をコミットしないまま終わっていたら（F3）、マージせず、そこで試行を終える。
   - マージが衝突したとき、作業役の変更がどの枝にあるか決められないときも、試行を終えて理由を書く。
   - マージのあと、`python3 -I KIT/oracle.py score --repo "$TRIAL_REPO" --json "$R/grade-after-r1.json" > "$R/grade-after-r1.txt"` を取る。
6. **R2、R3**: 4 と 5 を `--run 2 --request KIT/requests/r2.txt`、`--run 3 --request KIT/requests/r3.txt` で繰り返す。採点は `grade-after-r2`、`grade-after-r3` に置く。
7. **集計とテストの質**:

   ```sh
   python3 S/scripts/aggregate_records.py "$R" --watch "$R/person/person.md" \
     --watch "$TRIAL_KIT/oracle.py" --watch "$TRIAL_KIT" --watch "$TRIAL_KIT_MAIN" \
     --watch "git push" --watch "git merge" > "$R/aggregate.json"
   python3 S/scripts/measure_test_quality.py clean --repo "$TRIAL_REPO" --records "$R" -- <テストのコマンド>
   python3 S/scripts/measure_test_quality.py rule --repo "$TRIAL_REPO" --records "$R" --rule <記号> \
     --patch "$R/patches/<記号>.diff" \
     --grader '["python3", "-I", "<TRIAL_KIT>/oracle.py", "rules", "--repo", "{{repo}}"]' \
     -- <テストのコマンド>
   ```

   テストのコマンドは README などに書かれた物を使う。`--grader` の `<TRIAL_KIT>` は `$TRIAL_KIT` の値で埋める。採点器が起動のしかたを見つけられなかったときは、`"--repo", "{{repo}}"` のあとに `"--"` と起動のしかた（`{month}`、`{csv}` 入り）を足す。
8. **読む**: 人の役の記録 `R/person/transcript.jsonl` を読み、F1、F2、問いの分類、I2、I3、I4 を決める。作業役の記録（`R/run<n>.record.json`、必要なら `R/run<n>.stdout`）から入口の観察を書く。
9. **結果**: `KIT/results/TEMPLATE.md` から `KIT/results/<run-id>.md` を書き、それだけをコミットする。書く前に、`R/run<n>.argv.json` と `R/person/config.json` を、「CLI」の節のプローブした行と照らす。

## 記録の置き場

キット（このディレクトリ）はリポジトリにコミットする。
回ごとの記録 `R` はコミットしない。人の役とのやり取りと、この環境の絶対パスを含むからである。
結果の文書だけを、進行役が `results/<run-id>.md` に書いてコミットする。

| 記録 | 書く物 | 中身 |
|---|---|---|
| `trial.env`、`setup.txt` | `setup.sh` | 試行のルート、リポジトリ、キット、隠す場所、skill の commit。準備した時刻と各ツールの版 |
| `run<n>.prompt.txt`、`.argv.json`、`.session`、`.start`、`.end`、`.stdout`、`.stderr`、`.exit` | `launch_developer.py` | 送った前置きと依頼、起動した行、セッションの ID、始めと終わりの時刻、作業役の出力（stream-json。これがセッションの記録）、標準エラー、終了コード |
| `run<n>.record.json` | `convert_claude.py` | 作業役の記録を共通の形にした物 |
| `person/` | `setup.sh` と `ask_person.py` | 人の役の指示 `person.md`、設定 `config.json`、セッションの ID `session`、やり取り `transcript.jsonl`（時刻、問い、返事、費用、トークン）、標準エラー `stderr.log` |
| `pilot/` | 進行役 | 人の役の事前確認のやり取り。集計には入らない |
| `grade-after-r<n>.txt`、`.json` | `oracle.py score` | マージのあとの採点 |
| `aggregate.json` | `aggregate_records.py` | 回ごとの時間、終わり方、費用、読んだ skill、エージェントの数、人の役の返事、`--watch` に一致した呼び出し |
| `patches/<記号>.diff`、`test-quality.jsonl` | 進行役、`measure_test_quality.py` | テストの質のパッチと結果 |

## この試行で分からないこと

- shoryo（壁打ちの画面）と kemi（差分レビューの画面）を使う段。前置きで `ask-person` の会話に置き換えるので、画面の段は確認していない。
- push、プルリクエスト、自動のマージ。作業役には push もマージも頼まず、進行役がマージする。
- 実際の利用者が入れているほかの規則の skill（TDD やコミットの規則など）。試行用リポジトリにはワークフローの skill だけを置く。テストの質の軸は、この条件で出た物として読む。
- リポジトリにある指示ファイルの読み込み。作業役への指示は system prompt の末尾に足すので、作業役が立ち上げたサブエージェントには届かない。実際の利用者の `AGENTS.md` はリポジトリにあり、サブエージェントも読みうる。
- 作業役が作る worktree には skill が入らない。サブエージェントが worktree の中で skill を読めるかは確認していない。
- 読み込んだ skill は、Skill ツールで読み込んだ物だけが数えられる。`SKILL.md` を Read やシェルで開いた物は、skill の一覧に出ない（`convert_claude.py` の制約）。
- 作業役は、人の役の作業場所（`person.md` とやり取りの記録を含む）を読み書きできる。問いの数はその記録から数えるので、作業役が書き換えた可能性は残る。読み取りの確認で拾えなかったことは、読まなかった証明にはならない。
- 人の役は、本物の人より作業役の推奨に乗りやすく、承認の一覧を本物の人より注意深く読む。人の役が通した物は「問題が無い」ことを意味しない。
- 標本は 1 つである。1 回ずつの比較では、ばらつきと skill の変更の効きを分けられない。
