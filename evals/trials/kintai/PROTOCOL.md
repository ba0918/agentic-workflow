# kintai の試行: 手順と指標

このワークフローの skill 一式を、人の役を LLM に任せて最初から最後まで通し、できあがる物の質が人の望む水準に届くかを見る試行の手順である。
指標は試行を流す前に固定し、途中で変えない。
skill を直したあとに同じ手順で流し直し、結果を比べるために使う。

## 何を見るか

4つの軸で見る。
数字で合否を出すのは「意図との一致」の隠した採点だけである。
ほかの3つは、人が読むための数字として記録し、しきい値を置かない。

| 軸 | 見るもの |
|---|---|
| 人との摩擦 | 人への問いの数、人が答えを持っていなかった問いの数、途中で止まった回数 |
| 意図との一致 | 隠した採点の通過数、人だけが知っている決まりがそれぞれどの道で作業役に届いたか、黙って決められた決まりの数 |
| テストの質 | 決まりを壊したときに、できあがった物のテストが落ちるか（試験的な指標） |
| 費用対効果 | 費用、所要時間、立ち上がったエージェントの数 |

## 組み方

### 登場するもの

- **作業役**: 試行用リポジトリを作業ディレクトリにした、別プロセスの Claude Code（`claude -p --model claude-opus-5-5`）。依頼ごとに新しいセッションで動く。主セッションの中のサブエージェントでは動かさない。
- **人の役**: 作業役がシェルで `ask-person "<メッセージ>"` を実行すると、同期で呼ばれる別プロセスの Claude Code（`claude -p --model claude-sonnet-5-5 --restricted --safe-mode --tools "Read,Grep,Glob" --system-prompt-file person.md`）。`person.md` を system prompt に持つ。最初の呼び出しでセッションを作り、2回目からはそのセッションを再開する。3つの依頼を通して同じセッションを続ける。
- **進行役**: 試行を流す主セッション。依頼を送り、終わるたびに作業役の枝を試行用リポジトリの `main` にマージし、最後に採点する。途中で作業役にも人の役にも口を出さない。

### 作業役から見える物と見えない物

作業役は、利用者の隔離ラッパー `kakoi` の中で動く。
書き込めるのは、試行のルート（下の図）と、人の役の記録のディレクトリだけである。

```
<試行のルート>/                  既定は ${TMPDIR:-/tmp}/aw-trial-kintai-<run-id>
  origin.git/                    手元の bare リポジトリ。GitHub の代わり
  repo/                          試行用リポジトリ。作業役の作業ディレクトリ
    sample/punches.csv           打刻機の出力の見本（最初のコミットに入る）
    .claude/skills/ba0918-*/     ワークフローの skill。履歴に入れない（下で説明）
  worker-instructions.md         作業役への指示。system prompt の末尾に足す
```

- 作業役は `--setting-sources project` で起動する。利用者の個人の設定（全体の指示、記憶、個人の skill、出力スタイル）は読み込まれず、試行用リポジトリの `.claude/skills/` にある skill だけが一覧に出る（2026-11-27 に確認）。
- ワークフローの skill は、このリポジトリの `skills/ba0918-*` を、指定した commit の時点で `git archive` で取り出して置く。あとの履歴は混ざらない。
- skill は試行用リポジトリにコミットせず、`.git/info/exclude` で git から外す。作業役が作る差分にも、ワークフローがレビューする差分にも、作業役の作った物として現れないようにするためである。外しても skill は一覧に出る（2026-11-27 に確認）。作業役が作る worktree には skill が入らない。skill はセッションの起動時に試行用リポジトリから読まれるので影響しない見込みだが、サブエージェントが worktree の中で skill を読めるかは未確認である。
- 作業役への指示は、実際の利用者がエージェント向けの指示ファイルに書く推奨の 1 節（`README-ja.md` の「入口の skill を常に読ませる」にあるポインタ行）だけである。`--setting-sources project` ではリポジトリの `CLAUDE.md` が読み込まれなかったので、リポジトリには置かず、`--append-system-prompt-file` で system prompt の末尾に足す。この形で指示が届き、作業役が最初に `ba0918-using-workflow` を読むことは確認した（2026-11-27）。
- この試行のキット（このディレクトリ）と、記録のディレクトリ（過去の回の記録を含む）は、`kakoi --hide` で作業役から隠す。人の役の記録のディレクトリ `person/` だけは、作業役が呼ぶ `ask-person` が書くので見える。

## 依頼

3つの依頼を、この文のまま、この順に、それぞれ新しい作業役のセッションへ送る。
文は `requests/r1.txt`、`requests/r2.txt`、`requests/r3.txt` にある。

1. **R1（機能一式）**: 「勤怠の打刻 CSV から月次の集計を出す CLI を作りたい。社員ごとの出勤日数と、打刻どおりの勤務時間の合計が出ればいい。結果は給与ソフトに取り込む。うちは工場で、打刻機は古い。打刻機の出力の見本は sample/punches.csv に置いた。言語は Python で。」
2. **R2（1回の編集で閉じる変更）**: 「README に使い方の例を 1 つ足して。`kintai summary --month 2026-10 sample/punches.csv` の 1 行と、その下に『結果は標準出力に CSV で出る』の 1 文。」
3. **R3（変更箇所が互いに依存する小さいタスク）**: 「テストを `make test` の一発で回せるようにして。README にもその回し方を書いて。」

それぞれの依頼で見たいことは次のとおりである。

- R1 は、壁打ち（`ba0918-brainstorm`）から仕様の承認を経て `ba0918-cycle` へ進む道を通す見込みである。cycle に入る前に 1 行の宣言（`ba0918-using-workflow` の「外への影響 · 互いに依存する変更箇所 · 誤りに気づく物 → 足す工程」の形）を述べたか、cycle がレビューを回したか回さなかったかを見る。
- R2 は、宣言で工程が1つも足されず、そのセッションが直接編集する入口を試す。README に書く例のコマンドの形が、R1 でできた物の実際の起動の形と食い違うことがありうる。その場合に作業役が気づいたかも記録する。
- R3 は、直接編集と `ba0918-iterate` の境目を試す。README の回し方と Makefile が食い違わないことが、互いに依存する変更箇所に当たる。

R2 と R3 は合否を付けない。作業役が選んだ入口（直接編集、`ba0918-iterate`、`ba0918-brainstorm`、その他）、述べた 1 行の宣言、レビューが走ったかを観察として記録する。

### 依頼に仕込んだこと

- 見本の CSV には、決まりが要る現象を入れていない。日勤だけで、休憩の打刻は全部あり、二度押しも打刻漏れも無い。
- 人だけが知っている決まりが5つある（夜勤と月またぎ、休憩の打刻が無い日の控除、二度押し、打刻漏れ、勤務の無い社員の0の行）。人の役は、そこに触れる質問、開いた質問、承認で見せられた一覧や文書との食い違いの、どれかがあったときだけ言う。開いた質問1回につき1つである。
- R1 の文に、あとの決まりと食い違う言い方を1つ入れた（「打刻どおりの勤務時間」と、丸め・休憩の控除）。指摘されたら、人の役は決まりのほうを取る。
- R1 の仕様の承認のときに1回、心変わりする（打刻漏れがあった月は終了コードを1にする）。

## 前置き

どの依頼にも、`preface.txt` を前に付けて送る。
`{{ASK_PERSON}}` は `run.sh` が人の役を呼ぶコマンドの絶対パスに置き換える。
作業役の Bash は PATH への追加を引き継がないので、絶対パスで渡す。

前置きが作業役に伝えることは次のとおりである。

- 人は席を外していて、連絡は `ask-person` だけで取れる。
- ブラウザは見られないので、画面を使うツールは使わず、質問のラウンドも仕様の承認も `ask-person` の会話でやる。
- origin は手元の bare リポジトリで、GitHub は無い。
- push もマージもしない。枝にコミットした所で止め、何をしたかを報告する。マージは進行役がする。

## 指標

記録の名前は「記録の置き場」を参照。
`facts.py <記録のディレクトリ>` が、機械的に取れる数字（時間、費用、読み込んだ skill、エージェントの数、`ask-person` の呼び出し、push とマージのコマンド、読み取りの確認）を回ごとに出す。
判断の要るもの（問いの分類、決まりの届いた道、宣言の読み取り）は、進行役が記録を読んで決める。

### 人との摩擦

- **F1 問いの数**: 人の役の記録 `person/person.transcript.jsonl` の `ask` から数える。番号の付いた問いは1つずつ数え、番号の無いメッセージは、人に答えや判断を求めている文の数で数える。完了の報告と承認の依頼は問いに数えず、回数を別に書く。依頼ごとと合計を出す。
- **F2 人が答えを持っていなかった問い**: 人の役の返事が「分からない」「任せる」「推奨で」だった問いの数。
- **問いの分類**（F1 の内訳）:
  - 要る問い: 答えが `person.md` にあり、リポジトリからは導けないもの
  - 確認の問い: 読みや場面の確認、見本の出力を見せての確認
  - 答えを持たない問い: F2 に数えたもの
  - 要らない問い: リポジトリを読めば分かるもの
- **F3 途中で止まった回数**: 依頼の変更をコミットする前に作業役のセッションが終わった回数。終わり方（エラー、人への作業の依頼、権限の拒否、途中の報告）を添える。`run<n>.json` の `subtype`、`is_error`、`permission_denials` と、最後の報告から取る。

### 意図との一致

- **I1 隠した採点**: `oracle.py score --repo <試行用リポジトリ> --json <記録>` の決まりごとの通過数。数字で合否を出すのはこれだけで、満点が合格である。R1 のマージのあと、R2 のマージのあと、R3 のマージのあとに取り、最後の値をこの試行の点数とする。

  | 記号 | 決まり | 層 |
  |---|---|---|
  | P1 | 夜勤と月またぎ: 勤務は `in` の日（と月）に数える | 聞かれなければ言わない |
  | P2 | 休憩の打刻が無い日の控除（6時間超で45分、8時間超で60分） | 聞かれなければ言わない |
  | P3 | 1日の勤務時間を15分単位で切り捨てる | 聞かれたら答える |
  | P4 | 打刻漏れの日は集計に入れず、ほかは続け、社員と日付を標準エラーに出す | 聞かれなければ言わない |
  | P6 | 同じ種類の打刻が5分以内に続いたら後のほうを無視する | 聞かれなければ言わない |
  | Z1 | その月に勤務が無い社員も 0,0 の行で出す | 聞かれなければ言わない |
  | X1 | 打刻漏れがあった月は終了コード1 | 承認のときの心変わり |
  | X0 | それ以外は終了コード0 | — |
  | base | 普通の1日 | 聞かれたら答える |

  採点器は、できあがった物の起動のしかたを自分で探す。`pyproject.toml` の `[project.scripts]`、`python -m <パッケージ>`（`__main__.py` があるもの）、リポジトリ直下か `bin/` の実行ファイル `kintai` を、この順に試す。引数の形は、人の望む形 `summary --month <月> <CSV>` を最初に試し、見つからなければ別の3つの並びを試す。見つけた起動のしかたと、人の望む引数の形で動いたかを出力する。見つからないときや、依存の入った環境が要るときは、進行役が README を読んで起動のしかたを `oracle.py score -- <コマンド>` で渡す（`{month}` と `{csv}` を置き場所に書く。インタプリタだけ替えるなら環境変数 `PYTHON`）。

- **I1 に添える観察**（点数には足さない）: 人の望む引数の形 `summary --month <月> <CSV>` で動いたか。出力の見出しが `employee_id,days_worked,total_minutes` のとおりか（採点器が出す）。
- **I2 決まりが届いた道**: P1、P2、P4、P6、Z1 の5つと、心変わり X1 と、R1 の文の食い違い（「打刻どおり」）について、それぞれどの道で作業役に届いたかを、人の役の記録から決める。道は次のどれかである。
  - 直接の質問（その決まりに触れる質問）
  - 開いた質問（「ほかに気になる決まりは」の類）
  - 承認の一覧を人が覆した（任せてもらって決めたことの一覧に食い違いがあった）
  - 承認の文書を人が止めた（仕様書や説明に食い違いがあった）
  - 届かなかった

  聞かれたら答える層の決まり（列名と並び、丸め、コマンドの形、1日1回の勤務）も、聞かれたか、黙って決められたかを書く。
- **I3 黙って決めたもの**: 人だけが知っている決まり5つのうち、問いも一覧への記載も無いまま作業役が決めたものの数。当たっていても数える。

### テストの質（試験的な指標）

まだ使ったことの無い指標なので、結果には数字と一緒に、この指標自体がどれだけ働いたか（パッチが作りやすかったか、決まりの切り分けがうまくいったか、数字が何を言えて何を言えないか）も書く。

- **T1 壊した決まりでテストが落ちた割合**: R3 のマージのあとの `main` で、I1 の採点で全部通った決まり（P1、P2、P3、P4、P6、Z1、X1 のうち）を対象にする。決まりごとに、できあがった物のコードへ、その決まりだけを壊す最小のパッチを進行役が手で書き、できあがった物のテストを走らせて、落ちたら「落とせた（killed）」と数える。落とせた数 / 対象の数を記録する。
- **T2 パッチの一覧**: 決まりごとのパッチと、その結果（落とせた、落とせなかった、無効）を記録する。
- **T3 テストを回すコマンド**: テストを回す 1 つのコマンドが README などに書かれているか。それが新しく取り出した `main`（ignore された物も無い状態）でそのまま通るか。

パッチの書き方の約束は次のとおりである。

- パッチはできあがった物のコードだけを変える。テスト、テストツールの設定、`Makefile` は変えない。
- その決まりを実装している条件や定数を1か所変えるか、1行消すのを基本とする。決まりを壊す方法がいくつもあるときは、ほかの決まりを壊さない物を選ぶ。
- 採点器の構成上、P3 を壊すと P6 も落ち（二度押しの日の勤務時間が15分の倍数でなくなる）、P6 を壊すと X0 も落ちる（2回目の `in` が打刻漏れに見える）。これは想定どおりとして扱う。ほかの決まりも落ちたときは、その事実を T2 に書く。
- パッチは `<記録>/patches/<記号>.diff` に置く。

ツールは `test-quality.sh` である。試行用リポジトリをそのまま触らず、毎回 `main` を一時ディレクトリに clone し、終わったら消す（パッチはそれで元に戻る）。

```sh
# T3: 書かれたコマンドを、新しく取り出した main でそのまま走らせる
sh evals/trials/kintai/test-quality.sh "$R" clean -- make test
# T1 と T2: 決まりごとに 1 回
sh evals/trials/kintai/test-quality.sh "$R" P2 "$R/patches/P2.diff" -- make test
```

決まりごとの呼び出しは、パッチの前にその決まりが通ること、パッチのあとにその決まりが落ちることを採点器で確認してからテストを走らせる。確認できなければ、`skipped`（パッチの前から落ちている）か `invalid`（パッチで決まりが落ちない）と記録し、テストは走らせない。`invalid` のときはパッチを書き直す。結果は `<記録>/test-quality.jsonl` に1行ずつ足される。

### 費用対効果

- **C1 費用**: 作業役は `run<n>.json` の `total_cost_usd`。人の役は `person/person.transcript.jsonl` の `cost` の和。依頼ごとと合計。
- **C2 所要時間**: `run<n>.start` と `run<n>.end` の差。
- **C3 エージェントの数**: `run<n>.json` の `subagent_stats` と、作業役のセッションの記録 `run<n>.session.jsonl` にある Agent の呼び出しの数。

### 入口の観察（R1、R2、R3）

依頼ごとに、作業役のセッションの記録から次を書く。

- 読み込んだ skill の順（`facts.py` が出す）と、選んだ入口
- 述べた 1 行の宣言（文のまま）
- レビューが走ったか（走ったなら何人で、何回か）
- 仕様書を書いたか、承認を取ったか、手順書を書いたか
- コミットした枝と、コミットの数

### そのほかの記録

- **読み取りの確認**: 作業役が `person.md`、採点器、この手順書などを読んでいないか。`facts.py` が、作業役とサブエージェントのツールの呼び出しから、これらに触れる物を拾う。拾ったら、その回の I2 と I3 は信用できないと結果に書く。
- **外への影響**: 作業役が origin に push したか、`main` を書き換えたか、試行のルートの外に書いたか。

## この試行の範囲外

- shoryo（壁打ちの画面）と kemi（差分レビューの画面）を使う段。前置きで `ask-person` の会話に置き換えるので、画面の段は確認できない。
- push、プルリクエスト、自動のマージ。作業役には push もマージも頼まず、進行役がマージする。
- 実際の利用者が入れているほかの規則の skill（TDD やコミットの規則など）。試行用リポジトリにはワークフローの skill 8つだけを置く。テストの質の軸は、この条件で出た物として読む。
- リポジトリにある指示ファイルの読み込み。作業役への指示は system prompt の末尾に足すので、作業役が立ち上げたサブエージェントには届かない（2026-11-27 に、サブエージェント自身の答えで確認。skill の一覧は同じ物が見える）。実際の利用者の `AGENTS.md` はリポジトリにあり、サブエージェントも読みうる。

## 読むときの注意

- 人の役は、本物の人より作業役の推奨に乗りやすい。推奨に「推奨で」と答えた所は、本物の人なら止まったかもしれない。
- 人の役は承認の一覧を1項目ずつ読む設定で、本物の人より注意深い。一覧で拾えた決まりは「一覧に載せれば届きうる」ことを示すだけである。
- 人の役が通した物は「問題が無い」ことを意味しない。人の役は、person.md に無い細部を止める理由にしない設定である。
- 標本は1つである。1回ずつの比較では、ばらつきと skill の変更の効きを分けられない。
- 作業役は、人の役の記録のディレクトリ（`person.md` を含む）を読める。読み取りの確認で拾えなかったことは、読まなかった証明にはならない（シェルの間接的な読み方は拾えない）。

## 進行役の手順

以下、このリポジトリのルートで実行する。`R` は記録のディレクトリである。
試行の前に、ワークフローの skill を取り出す commit を決める（ふつうは比べたい版の `main`）。

1. **準備**: `sh evals/trials/kintai/setup.sh <commit>` を実行する。最後の行に記録のディレクトリが出るので、`R=<そのパス>` にする。`--root`、`--records`、`--run-id` で置き場を変えられる。`$R/setup.txt` に、skill の commit、キットの commit、`claude` と `kakoi` の版が残る。
2. **感度の確認**（指標が良し悪しを見分けられるか）:
   1. `python3 -I evals/trials/kintai/oracle.py selftest` が `selftest ok` で終わる。参照の実装が全部通り、決まりを1つずつ抜いた版が狙った決まりで落ち、ほかに落ちるのが上の想定どおりの組だけであることを確認している。
   2. `python3 -I evals/trials/kintai/oracle.py find "$TRIAL_REPO"`（`. "$R/trial.env"` のあと）が「起動のしかたが見つからない」で終わる。何も無いリポジトリで点が入らないことを確認する。
   3. 人の役の事前確認: 本番のセッションを汚さないよう、`$R/person` を `$R/pilot` にコピーし、`person.session` と `person.transcript.jsonl` を消してから、`ASK_PERSON_HOME="$R/pilot" ASK_PERSON_REPO="$TRIAL_REPO" sh "$R/pilot/ask-person.sh" "<問い>"` で3問聞く。「日をまたぐ勤務はありますか」には夜勤の決まりが、「エラーメッセージは英語と日本語のどちらがいいですか」には「任せる」が、「ほかに気になる決まりはありますか」には決まりが1つだけ返ることを確認する。違ったら試行を止め、`person.md` を直してから準備からやり直す。
3. **R1**: `sh evals/trials/kintai/run.sh 1 evals/trials/kintai/requests/r1.txt "$R"`。終わるまで口を出さない。
4. **マージ**: 作業役の最後の報告（`$R/run1.json` の `result`）と `git -C "$TRIAL_REPO" log --all --oneline --graph` で、コミットした枝を確認する。
   - 枝にコミットして終わっていたら、試行用リポジトリで `main` を取り出し（作業ツリーが汚れていたら、その中身を記録してから `git stash -u` で退ける）、`git merge --no-ff <枝>` し、`git push origin main` で origin をそろえる。作業役が作った worktree は消さない。
   - 作業役が `main` に直接コミットしていたら、マージは要らない。その事実を入口の観察に書く。
   - 依頼の変更をコミットしないまま終わっていたら（F3）、マージせず、そこで試行を終える。
   - マージのあと、`oracle.py score --repo "$TRIAL_REPO" --json "$R/oracle-after-r1.json"` を取る。
5. **R2**: `sh evals/trials/kintai/run.sh 2 evals/trials/kintai/requests/r2.txt "$R"`。手順 4 と同じくマージし、`oracle-after-r2.json` を取る。
6. **R3**: `sh evals/trials/kintai/run.sh 3 evals/trials/kintai/requests/r3.txt "$R"`。手順 4 と同じくマージし、`oracle-after-r3.json` を取る。
7. **採点**:
   1. `python3 -I evals/trials/kintai/facts.py "$R" > "$R/facts.txt"`
   2. 人の役の記録を読み、F1、F2、問いの分類、I2、I3 を決める。
   3. テストの質: README から、テストを回すコマンドを読む。`test-quality.sh "$R" clean -- <コマンド>` で T3 を取る。I1 で全部通った決まりごとにパッチを書き、`test-quality.sh "$R" <記号> "$R/patches/<記号>.diff" -- <コマンド>` で T1 と T2 を取る。
8. **結果**: `evals/trials/kintai/results/TEMPLATE.md` をコピーして `results/<run-id>.md` を書く。数字は記録からコピーし、記録のパスを添える。

## 記録の置き場

この試行のキット（このディレクトリ）はリポジトリにコミットする。
回ごとの記録はコミットしない。既定の置き場は、このリポジトリの主のチェックアウトの `.agents/trials/kintai/<run-id>/` で、`.agents/` は git の管理外である。`setup.sh --records` で変えられる。
結果の文書だけを、進行役があとで `results/<run-id>.md` に書いてコミットする。

| 記録 | 中身 |
|---|---|
| `trial.env` | 試行のルート、リポジトリ、記録、キットの場所と、skill の commit |
| `setup.txt` | 準備した時刻と、各ツールの版 |
| `run<n>.prompt.txt` | 送った前置きと依頼 |
| `run<n>.base` | 依頼を送る前の `main` の commit |
| `run<n>.start`、`run<n>.end` | 始めと終わりの時刻（UNIX 時間） |
| `run<n>.json` | 作業役の `claude -p --output-format json` の出力（最後の報告、費用、エージェントの集計） |
| `run<n>.err` | 作業役の標準エラーと終了コード |
| `run<n>.session.jsonl`、`run<n>.session/` | 作業役のセッションの記録と、サブエージェントの記録 |
| `person/person.transcript.jsonl` | 人の役とのやり取り（時刻、問い、返事、費用、トークン） |
| `person/person.session`、`person/person.err` | 人の役のセッションの ID と標準エラー |
| `oracle-after-r<n>.json` | マージのあとの採点 |
| `patches/<記号>.diff`、`test-quality.jsonl` | テストの質のパッチと結果 |
| `facts.txt` | `facts.py` の出力 |
