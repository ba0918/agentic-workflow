# 開発ワークフロー仕様

この文書は、5 つの skill（brainstorm、plan、cycle、implement、review）を組み合わせて開発を進めるときの約束を、人が読んで判断できる形で書いたものである。
5 つの skill はリポジトリの `skills/` に置き、ディレクトリ名は `ba0918-` に skill 名を付けた物（`ba0918-brainstorm` など）である。
skill の本文と参照資料は LLM 向けの英語で、この文書の内容を実行者への指示として写したものである。
両者の意味が食い違ったときは、この文書を正とする。
この文書の上位に、利用者が自分の言葉で書いた理念（`docs/principles.md`）がある。
理念と食い違ったときは理念に従う。
用語集はリポジトリ直下の `CONTEXT.md` にある。
仕様書をどの粒度で分け、どう互いに参照させるかは、[仕様書の分け方 仕様](spec-documents.md)にある。

5 つの skill の責務を基準にし、これを越える物は実利用で必要だった実績が無ければ持たない。
各 skill の責務は単純に保ち、依存を極力持ち込まない。
5 つの skill は組み合わさって初めてワークフローになり、各 skill は独立しない。
結び付きは、前の工程の成果物のパスを次の工程が入力として受け取ることだけで、それを強制する実行環境は持たない。
review だけは、ワークフローの外から単独で呼ばれても動く。

このリポジトリが提供するのは skill の集まりであって、フレームワークではない。
判定は「`skills/ba0918-*/` を `~/.claude/skills/` に置くだけで、他に何も入れずに動くか」である。
実行環境、状態を保存する仕組み、状態を読み書きする script を提供した時点でフレームワークになるため、これらは持たない。
記録の形式は skill 本文の指示で担い、形式の検査や編集の禁止（ロック）を行う機構は置かない。

skill 本文と参照資料は減る方向が基本で、この文書の内容を本文へ書き写して太らせない。
本文に書くのは実行者がその場で要る指示だけである。
行数の目安は、SKILL.md と参照資料の合計で brainstorm 135 / plan 156 / cycle 110 / implement 217 / review 242 である。
値は作り直し前の本文の実測から取った。
目安を超えたときにまず疑うのは、その skill の責務が過剰になっていないかである。
責務が増えていないなら、足した行が実行者にその場で要ることをその変更のレビューで示して超えてよい。
数に合わせて文を削るのは反例である。
すぐに陳腐化する事は書かない。

skill の肥大とは、長さではなく、次の 5 種類が本文と参照資料にあることを指す。
無駄な指示、冗長な文章、フロンティアモデルに効果の薄い指示、重複する指示、一度に読む必要の無い文章である。
フロンティアモデルに効果の薄い指示とは、次の 3 つである。
モデルが言われなくてもする振る舞いの言い直し（強調のための繰り返し、中身の無い役割の一文など）。
今のモデルでは起きない失敗への回避策。
今の規則を変えない経緯の記述。
作者だけが知る文脈（環境の事実、品質の基準、道具の契約、判断の難しい場面、制約の理由）は長くても残す。
過去の事故から生まれた禁止で、その事故が今のモデルでも起きうるか判断できない物も、短く書き直して残す。
skill を校正するときは、この 5 種類を基準に削り、構造を分け、必要な所だけを一度に読ませる。
行数や語数は肥大の判定に使わない。上の行数の目安は、責務が過剰になっていないかを疑う合図に留まる。
規則の正本は、skill を全部通して 1 か所に置き、他の場所はそこを指す。
別の skill の参照資料を指すときは、skill の名前とその参照資料の名前で指す（cycle が review の参照資料を読むのと同じ形）。
委譲先は skill を読まないので、実行時に正本から委譲先のプロンプトへ貼るのは重複に数えない。
食い違っていない写しでも、置き場が複数あると直すときにずれるので、ファイルに写して置かない。
校正の結果は、5 種類を見る項目として渡したレビューで確かめる。
LLM を走らせて振る舞いを比べる確認は、人が明示したときだけ行う。
行数が減ったことを肥大が減った根拠にしたら反例である。
実行時に貼れば足りる規則を、別の skill のファイルに写して置いたら反例である。

## 全体の考え方

### 工程は既定で足さない

工程（壁打ち、計画、計画のレビュー、実装の委譲、小ささの判定、レビュー、ループ）は、
どれも別文脈の agent 1 体ぶんの費用を持つ。
その agent はリポジトリと上位文書を読み直すので、費用は変更の大きさにほとんど関係なく掛かる。
小さい変更ほど、工程の費用が変更そのものの価値を上回る。

よって既定はどの工程も足さないことであり、足すには 1 行の理由が要る。
理由が書けない工程は足さない。
どの工程を足したかは動く前に 1 行で宣言し、そのまま動く。人の承認は待たない。
人はその宣言を覆せる。
入口と宣言の決め方は入口 skill 仕様（`docs/spec/using-workflow.md`）にある。

レビューを足す理由は 1 つだけである。
依存し合う変更箇所が複数あり、実装が自分の中で矛盾しうることである。
機械の検査にも差分の一読にも映らないのはこれだけだからである。
1 箇所で閉じる変更、互いに独立した変更、既存の検査が捕まえる間違いには足さない。

レビューが必ず走る条件は 1 つも置かない。
レビューを増やしても正しさは保証されず、抜けはそのまますり抜けるので、安心感のために体数を増やさない。
抜けたレビューは人が後から頼める（review の診断、または同じブランチでの iterate）。

### 人が見るのは最終成果物だけ

人は最終成果物だけを見る。
実装とレビューと修正の改善ループは自律で回る。
製品の方向は brainstorm で人から受け取り、仕様書と手順書の承認より後の工程は人を待たない。
途中で止めて人に渡しても、人の答えは「直さない」にならず、答えも自明であることが多いからである。
誤った判断は終端報告で人が見つけて覆せるので、止める費用のほうが大きい。

作業の途中で人を止めるのは、次の 2 つの場面だけである。
それ以外の躓きは、実行している側が自分で立て直す。

1. 不可逆な操作、人の権限が要る操作、本番のデータや設定など危険な対象に触れる直前
2. 秘密情報の露出、意図しない公開、データ破壊など、続けると被害が広がる事故

次のような躓きでは人を止めない。
予定外だが安全なファイルの補完、補助ツールの不具合、再構成できる記録の欠け、hook の失敗、通常のコマンド失敗、主観的な磨き。

製品、設計、永続化、技術選定の判断が足りないとき（承認済みの文書に判断の根拠が無いか、二通りに読めるとき）も止めない。
根拠のいちばん強い答えを**暫定の答え**として選んで進め、その答えと**覆る条件**（人が何を言えばその答えを取り消すか）を 1 行ずつ終端報告に載せる。
動かせば分かる問いは判断ではなく事実なので、暫定の答えにせず動かして確かめる（implement の「人に返す場面と再開」）。
承認済みの仕様書や手順書と矛盾する変更が要るときだけは、進めずにその実行を終えて上流へ返す（仕様書なら brainstorm、手順書なら plan）。
承認した内容を変えるのは人だからである。
診断して方法を変えても進まないときは、直しが共通に置いた仮定を疑う（cycle の「仮定を疑う段」）。
判断が足りないことを理由に、途中で人に問いを投げて答えを待ったら反例である。
暫定の答えで進んだのに、答えか覆る条件を終端報告に載せなかったら反例である。

brainstorm の対話、仕様書と手順書の承認、cycle の終端で成果物を見せることは、この「止める」には当たらない。
対話は人と話すことが責務そのものであり、承認と終端は作業を終えて結果を渡す動作だからである。

subagent が 2 つの場面に当たって止まったときは、委譲した側（メインセッションまたは cycle）がその内容をそのまま人へ渡す。
人の回答を受けて、その subagent を再開するか、回答を含めて委譲し直す。
cycle の中で起きたときの扱いは cycle の「終わり方」に書く。

### ドメインの用語と境界を磨く

人と LLM の認識のズレは、普段の対話の中で次の形で現れる。
人が二通り以上に読める言葉を使う。
人の発言から、ドメインの概念同士の境界があやふやだと分かる。
人の説明とコードの中身が一致しない。

これらは brainstorm の中に限らず、どの工程の対話でも起こる。
承認より前の対話では、気づいた側がその場で用語の意味を問い、例外的なシナリオで境界を確かめ、定義や決めごとが明らかになり次第書き留める。
ドメインモデルは受け取って使うだけの物ではなく、対話の中で作り、磨き上げる物である。

定義の置き場は用語集（既定は `CONTEXT.md`。[分けるとき](spec-documents.md#用語集)）で、brainstorm が更新する。
用語集と仕様書を直すのは brainstorm だけである。
承認より後の工程で見つかったズレは、暫定の答えで進めて終端報告に載せ、用語集と仕様書の直しは次の brainstorm に送る。

### 確かめ方が証拠として数えられる条件

検証もコードと同じく、規模と釣り合わずに膨らむ。
各工程に「足す」操作しかなく「削る」操作が無いと、仕様が境界を全部反例にする。
手順書がテストを名指しで足し、review が未テストの項目を全部指摘にし、修正役が指摘ごとに fixture を作る。
これを止めるため、確かめ方（テスト、検査、fixture）が証拠として数えられる条件を、次の 4 つで固定する。

1. 確かめ方が作り出す条件を、宣言された動作環境のどれかが運用中に生み出せる。テストまたは指摘が、その条件の運用上の生み手を名指しできる。境界に届く信頼できない入力も生み手の 1 つである
2. 確かめ方の対象が製品（補助 script や workflow を含む）または検査であって、確かめ方自身ではない
3. 検査が強制する規則を、仕様書が述べている
4. 確かめ方が固定する文言、ファイルの構造、内部の名前を、仕様書が契約として宣言している

1 つでも欠ければ、その確かめ方は証拠ではなくコストである。
足す理由にも、残す理由にも、要求する理由にもならない。
規模では裁かない。
大きな fixture でも対象が到達可能な振る舞いなら正当で、一行の断言でも宣言の無い文言を固定すれば証拠ではない。
条件 3 と 4 が参照する規範は、そのプロジェクトの仕様書である。
仕様書を持たないプロジェクトでは、利用者向けの公開文書（README、help、公開 API の文書）を規範として読む。
動作環境は、その規範が宣言する物である。

唯一の確かめ方がこの条件を満たさない要求は、機械では検証できない。
コード以外の要求なら、人が実行して確認する検査か、プラットフォーム自身の検査器で確認する要求として書く。
コードの振る舞いなら、その要求を落とし、失敗は到達可能な失敗が既に証明している汎用のエラー経路に合流させる。
実装者に fixture を作らせることで解決したら反例である。

この条件の正本は agentic-rules リポジトリの `contracts/oracle-evidence.md`（英語 2 段落）である。
agentic-rules は規則の skill `ba0918-verification` を配るリポジトリで、この条件はその規則の一部である。
第 1 段落が 4 条件と「満たさない確かめ方を足さない、残さない、要求しない」の禁止、第 2 段落が要求の処遇である。
条件の意味がこの文書と正本で食い違ったときは正本に従い、この文書を直す。
skill の中の写しは、skill を全部通して review skill の参照資料の 1 か所だけに置き、規則名と写した時点の agentic-rules のリリース版を 1 行で添える。
brainstorm と plan は、確かめ方を決めるときにその参照資料を review skill の名前と参照資料の名前で指して読み、自分では写しを持たない。
reviewer と修正役には、呼んだ側が実行時にその参照資料から条件を貼る。
この文書には版を書かない。
写しが正本より古くなったことは、版の照合で見つける。
適用は変更の差分だけで、既存の確かめ方の棚卸しは求めない。

この条件は、run-if-present での実測（「根拠」の節）から採った。
人の言葉では「検証の検証は勝手に実装しない」である。

### 承認はコミットと同じ操作

承認を儀式にしない。
黙っていることや「もう少し話そう」は承認ではなく、承認は人が明示する。

人が承認する文書は、理念、用語集、仕様書、手順書の 4 種類である。
どれも、人が差分を読んで承認してからコミットする。
この 4 種類のコミットは人が打つか、人の明示の指示で打つ。
コミットされていない物は未承認である。
それ以外の文書（README、skill 本文など）は承認の対象ではなく、成果物として cycle の終端で受け入れる。

承認を求めるときは、対象だけをステージし、パスと差分を見るコマンドと判断点だけを会話に出す。
全文を貼らず、要約を承認の対象にしない。

### 記録の置き場は 1 本線

人が承認した文書は `docs/` に、実行者が書いた記録は `.agents/`（git 管理外）に置く。
`.agents/` は、その skill が動いている作業ツリーの直下を指す。
worktree で動くときは worktree 側にでき、worktree と共に消える。

| 場所 | 何が入るか | 寿命 |
|---|---|---|
| `docs/principles.md` | 理念 | 永続 |
| `CONTEXT.md` | 用語集 | 永続 |
| `docs/spec/` | 仕様書 | 永続 |
| `docs/plans/<名前>.md` | 進行中の手順書 | 完了したらメインセッションが消す。過去は git で読む |
| `.agents/artifacts/reviews/<ブランチ名>.json` | review の指摘の現在の状態 | 人が消すまで（worktree ごと消えてよい） |
| `.agents/tmp/` | 壁打ちの途中経過、人向けのレビュー報告、その他の一時ファイル | 人が消すまで。壁打ちの途中経過は仕様書の承認後に brainstorm が消す |

ブランチ名に `/` が含まれるときは、そのままサブディレクトリになる（`feat/foo` なら `reviews/feat/foo.json`）。
`docs/` の下にある物が、いま何が進行中かを表す。

記録するかどうかの線引きは「git に痕跡が残る種類の情報か」である。
実装の進捗はコミットとして残るので、別の進捗記録を持たず git log から読む。
brainstorm の途中経過（承認前の合意、禁止、未決定、委任、却下、改訂）と、review の指摘とその open / closed は git に残らないので、`.agents/` に書く。
brainstorm の却下と未決定と委任は、承認時に仕様書の節へ移し、`.agents/` 側の途中経過を消す。
記録はどれも現在の状態を 1 ファイルに上書きする形（current-state）で、出来事を追記するログは作らない。
指摘ごとの往復ごとの評価は、その指摘の現在の状態の一部として持つ。

commit メッセージに工程名や指摘の ID を書かない。
指摘と修正コミットの対応は、指摘の側に持つ。

### ブランチと手順書の対応

手順書は `docs/plans/<名前>.md` として作る。
実装用のブランチと worktree は、cycle を起動する前にメインセッションがブランチごとに 1 つ作る。
ブランチ名に手順書の名前を含めることで、ブランチと手順書を結ぶ。
対応を記録で持たず、命名で持つ。

## 5 つの skill の流れ

brainstorm が人との対話で仕様書を作り、plan が仕様書から手順書を作る。
cycle は手順書を受け取って改善ループを回し、終端で成果物を人に見せる。
ループの中身は implement、review、修正役への委譲である。
人が成果物を受け入れてブランチを取り込む。

```
brainstorm ──▶ docs/spec/（承認 = コミット）
                 │
plan ──────────▶ docs/plans/（承認 = コミット）
                 │
cycle ─────────▶ implement ──▶ review ──▶ 修正役 ──▶ review ──▶ …
                 │
                 └──▶ 終端報告（人の 1 回の確認）──▶ 人が取り込む
```

完了した手順書の削除は skill の仕事ではなく、メインセッションの掃除である。
人が成果物を受け入れてブランチを取り込んだ後、または人が作業の終了を明言した後に消す。

## brainstorm

責務は、人と共通理解が得られるまで対話を続け、要件と仕様を抽出することである。
これは実質的なドメインモデリングにあたる。
受け取る物は、人の相談内容と、既存の仕様書を直すときはそのパス（分けてあれば索引のパス）である。
返す物は、承認されてコミットされた仕様書と、今回変えた仕様書のパスの一覧である（[1 回で複数の仕様書を変えてよい](spec-documents.md#責務ごとに-1-本)）。

人と LLM の認識のズレを無くし、暗黙の了解を 0 にする。
少しでも曖昧な点が残っていればそれは合意ではなく、妥協せずに続ける。
勝手に終わらない。

### 決めごとを木として扱う

決めることを 1 本の木として扱う。
どの決めごとにも前提（先に決まっていること）があり、決めると小さな決めごとが枝分かれする。

対話はラウンド制で進める。
前提が揃って今すぐ答えられる質問だけを集め、通し番号を振り、各質問に LLM の推奨回答を添えて 1 ラウンドでまとめて出す。
推奨回答を添えるのは、人の得意領域の外では白紙から答えるのが難しいからである。

```
Q1: 質問内容

A. 推奨される回答

Q2: 質問内容

A. 推奨される回答
```

人の回答で木を計算し直すと、前提の揃った質問が解放されて次のラウンドへ進む。
全部の枝を辿り切り、暗黙の了解が 1 つも残らなくなるまで繰り返す。

無回答の質問の推奨回答は採用しない。
それは暗黙の了解として残り、次のラウンドで再び問う。

### 対話の作法

設計を丸ごと提案して承認を求めることはしない。
質問に推奨回答を添えるのとは粒度が違う。
はい / いいえの質問を連射して「決まった」状態を作ることもしない。

一度決まったことを理由なく聞き直さない。
人の案にも LLM の案にも反論や反例を出す。
「反対が無い」は「合意」ではない。
確認した事実、事実からの推測、確かめていない仮説を区別して言う。
既存の物を置き換える判断は中身を読んでから行い、名前や概要で決めない。

事実確認の調査は subagent に任せ、メインセッションを止めずに質問を続ける。

### 用語とシナリオを質問にする

二通り以上に読める言葉が出たら、「『X』はこの意味でいいか」と LLM の読みを添えて、通常のラウンドの質問にする。
確定した定義は用語集に書く。
対象は解釈が分かれる語だけで、辞書を作る作業にはしない。

ドメインの概念同士の関係を決めるときは、正常系と境界のケースの具体的なシナリオを出し、「このとき何が起きるか」を質問にする。
人が考えていなかった境界を、人の目の前に出すのが目的である。
シナリオで見つけた反例は、仕様書の各要求に付ける反例の元になる。
1 ラウンドに出すシナリオは、前提が揃った関係の物だけにする。

要件が製品の観測できる振る舞いを変えないとき（リリースの自動化、ライセンス、CI など）は、その扱いをそのラウンドの質問にする。
選択肢は 3 つで、その仕様書に含めるか、別の仕様書にするか、作らない物にするかである。
本体に関係ない要件を黙って仕様書に含めたら反例である。

### 記録

記録する種類は 6 つである。

- **合意**：決まったこと
- **禁止**：やらないと決めたこと
- **未決定**：まだ決まっていないことと、誰が決めるか
- **委任**：実装側に任せると決めたことと、その理由
- **却下**：退けた案と、その理由
- **改訂**：何を置き換えたか

未決定と委任を混ぜない。

途中経過は `.agents/tmp/brainstorm-<題材の名前>.md` に Markdown 1 ファイルとして置き、意味が変わったときだけ上書きする。
題材の名前は、その回で話す題材の短い名前にする。分けた範囲の改訂なら、索引の名前を使う。
会話が切れたら、次のセッションがそれを読んで再開する。

合意は仕様書の本文に、禁止は仕様書の「作らない物」に書く。
却下した案と理由、未決定、委任は、仕様書の中に節として書き残す。
改訂は途中経過の中だけの記録で、承認後は git の履歴が代わりになる。
仕様書が承認された後は、途中経過のファイルを消す。
却下した案が仕様書に残るので、次の brainstorm が同じ案を知らずに再提案することを防げる。

### 仕様書に書く前の見直し

書く前に見直す。
書きかけ、矛盾、曖昧な語、範囲の境界の欠け、関係する未決定、黙って決めた事があれば、書かずに対話へ戻る。
既存の仕様書に足すのか新しく作るのかの判断、同じ事実の探し方、分ける目安に当たったときの確かめ方は、[仕様書の分け方 仕様](spec-documents.md)に従う。
変えた見出しへリンクしている仕様書は、テキスト検索で拾って読み直し、食い違いが無いかを確かめる。
これは仕上げのレビューを足すかどうかに関係なく毎回行う。
レビューに任せると、レビューを足さないときに誰も見なくなるからである。
「仕様が黙っている」は「実装に任せる」ではない。
これは brainstorm が仕様書を書くときの規則で、黙っている所を残さずに書き切ることを求める。
承認より後の工程が仕様の黙っている所に当たったときの扱いは、暫定の答え（「人が見るのは最終成果物だけ」）である。

仕様書は見出しで参照できる粒度にし、各要求に観測できる成功条件と反例を持たせる。
要求ごとに、成功条件の確かめ方が「確かめ方が証拠として数えられる条件」を満たすかを見る。
満たさない要求は、コード以外なら人が実行する検査かプラットフォームの検査器で確認する要求として書き、コードなら落として汎用のエラー経路に合流させる。
落とした要求は、欠けた条件を理由にして却下として記録する。
起き得ない失敗のための固定文言を要求に残したら反例である。
対話で確定した定義は用語集に足し、仕様書と一緒に承認を受ける。
LLM を実際に走らせる高価な確認は、人が明示したときだけ要求する。

### 仕上げ

完了後のレビューは既定では行わない。
要件どうしが矛盾しうるときだけ足す。
互いに依存する要件を複数持つ場合と、記録や理念から引き剥がされうる要件を持つ場合である。
その理由を宣言して subagent に敵対的なレビューをさせる。
足すときの reviewer は 1 体で、仕様書そのものの品質を見る。
理念と brainstorm の記録（合意、禁止、却下）への突き合わせを別の 1 体に足すのは、記録がここで読み返して食い違いに気づける長さを超えているときだけである。
reviewer に渡す仕様書は、今回変えた仕様書と、それとリンクで直接つながる仕様書（1 段、リンクする側とされる側の両方）だけで、仕様書の置き場の全体は渡さない。
大きな文脈を一度に渡すと、reviewer も矛盾を見落とすからである。
独立した要件が数本あるだけの仕様書には足さない。
新しい指摘が出た場合は木の枝に追加し、質問を続ける。

レビューを終えたら、plan に進める条件を brainstorm が確かめる。
満たしていれば対象をステージし、人が読んで承認し、コミットする。
承認後に途中経過を消す。

plan に進める条件は次のとおりである。
成果物が 1 単位（1 本のブランチで作れる範囲）に限られる。
得る結果を一文で言える。
作る物と作らない物がある。
保存する状態と寿命が決まっているか、無いと確認した。
外部依存の採否が決まっている。
人が判断する場面と、そのとき見せる物が決まっている。
要求を見出しで辿れる。

## plan

責務は、抽出された要件と仕様を元に実装計画を立てることである。
文脈を一切知らない LLM が、手順書を見て作業を円滑に進められる粒度を要求する。

受け取る物は、brainstorm が変えたコミット済みの仕様書のパスで、複数でよい。
索引からは辿らない。
受け取った仕様書がリンクしている仕様書は 1 段まで読んでよく、手順が基づく物はリンク先の物も含めて手順書に挙げる。
返す物は、承認されてコミットされた `docs/plans/<名前>.md` である。

### 手順書の形

手順書は Markdown 1 ファイルで、人の言葉で書く。
機械向けの節を持たない。

仕様を書き写さない。
仕様書へのリンクと見出しで参照して読ませ、この計画に固有の判断だけを書く。
固有の判断とは「なぜこの順序か」「なぜこのファイルか」「どこで止まるか」である。
足りない文脈は実装側がリポジトリを読んで補う。

手順書全体に書く物は次のとおりである。
仕様のどの節をどの手順で確かめるか、実装方針と根拠、変更するファイルの範囲、手順の順序と前提、実装側に任せてよい選択、止まる条件。

各手順に書く物は次のとおりである。
目的と基づく仕様書の見出し（リンク）、前提、変更してよい範囲、この手順が終わったと言える条件とその示し方（テスト / 検査 / 作った物 / 外で確かめる）、任せてよい選択、止まる条件。

示し方で名指しするテストは、「確かめ方が証拠として数えられる条件」を満たす物だけである。
満たさないテストは名指ししない。
名指しできるテストが無く、仕様書がその要求を人の検査やプラットフォームの検査器で確かめる要求として書いてもいないなら、仕様の欠けとして brainstorm へ返す。
これは暫定の答えにしない。
確かめ方が証拠になるには仕様書の宣言が要り（条件 3 と 4）、その宣言は手順書では作れないからである。
既に成立している条件にテストを足さず、テストの数を「終わったと言える条件」の数に合わせない。
成立済みの物には失敗するテストが作れず、テストは実装する振る舞い 1 つに 1 つだからである。
仕様書に無いテスト（例: 依存木の走査、CI ヘルパの不一致 fixture）を手順書が名指ししたら反例である。

### 任せてよい選択の範囲

実装側に任せてよい選択は、どれを選んでも承認した振る舞いが変わらない範囲だけである。
新しい入力の種類、受け入れの境界、エラーの扱いのように仕様書に無い判断が要るときは、根拠のいちばん強い答えを暫定の答えとして手順書に書く。
その答えと覆る条件は、手順書の承認を求めるときの判断点に載せる。
手順書の承認で人がどのみち見るので、brainstorm へ戻して待たない。
黙って決めて判断点に載せなかったら反例である。

実装途中で人へ返す場面は、その手順の中に普通の文で書く。
置けるのは、不可逆な操作、人の権限が要る操作、危険な対象への確認だけである。
手順書に無い判断は実装側が暫定の答えで進める。
上流へ返すのは cycle の終わり方 4 に挙げた理由のときだけである。
成果物の受け入れは cycle の終端へ送る。

### 仕上げ

完了後のレビューは既定では行わない。
手順書の中の決めごとが互いに矛盾しうるとき、つまり互いに依存する手順があるか、1 つの仕様書の見出しが複数の手順を動かすときに、その理由を宣言して subagent に敵対的なレビューをさせる。
足すときの reviewer は 1 体で、手順書そのものの品質を見る。
仕様書との突き合わせを別の 1 体に足すのは、その突き合わせが機械の検査に映らないときだけである。
手順が互いに独立している手順書には足さない。
指摘は、意思決定が要る物も含めてそのまま対応する。
意思決定が要った物は、暫定の答えと覆る条件を手順書の承認を求めるときの判断点に載せる。
承認済みの仕様書と矛盾する直しが要る指摘だけは、手順書を直さず brainstorm へ返す。

承認は仕様書と同じ手順で行う。
コミット済みの手順書だけが承認済みである。

## implement

責務は、与えられた手順書を元に実装を進めることである。
コードは TDD で進める。
文書や小さい script はそのまま進めてもよい。

受け取る物は、手順書のパスとブランチである。
返す物は、ブランチ上の commit である。

手順書の手順を、書かれた順に実行する。
手順書に無い重要な設計判断が要るなら、暫定の答えで進め、答えと覆る条件を報告に載せる。
承認済みの仕様書や手順書と矛盾する変更が要るときだけ、止めて上流へ返す（仕様書なら brainstorm、手順書なら plan）。

### 完了の示し方

手順ごとの完了の示し方は 4 種類ある。

**テスト**：RED、GREEN、REFACTOR の順に進める。
RED では振る舞い 1 つに小さなテスト 1 つを書き、走らせて「作っていないから失敗する」ことを確かめる。
書き間違い、読み込み失敗、依存不足、権限、ネットワーク、無関係な既存の失敗は、期待した失敗ではない。
GREEN では通すのに必要なコードだけを書き、テストは変えない。
REFACTOR で直す物が無ければ、何を見て不要と判断したかを記録して進む。

**検査**：手順書が挙げた検査コマンドを順に走らせ、全部成功したときだけ完了とする。
その場で別のコマンドに差し替えない。

**作った物**：README や skill 本文などの文書。
形式の検査があれば通し、独立した review で意味を確かめられる状態にする。

**外で確かめる**：実機や実測。
安全に実行できない、人の権限が要る、不可逆のいずれかなら、実行前に人へ返す。
出力やログの全文は残さず、実行したコマンドと判定に要る要約だけを完了の証拠として残す。

テストを走らせるコマンドは、手順書、プロジェクトの指示、標準の道具の順で決める。
手順書とプロジェクトの指示で決まらず、エコシステムの標準の道具が何も入れずに使えるなら、それを暫定の答えにして進め、コマンドと覆る条件を報告に載せる。
標準の道具を入れる必要があるなら、何かを入れる操作なので、下の試しと同じく入れる前に人へ返す。
どれにも当たらなければ、製品コードを書く前に plan へ返す。

### コミット

1 つの関心事につき 1 コミットとする。
テストとそれを通す最小実装は 1 つの関心事である。
`git add <パス>` で個別にステージし、`git add .` や `-A` は使わない。
hook を無効化しない。

予定範囲外の直しは、大筋を変えない補完なら理由を記録してコミットし、終端で報告する。
検査やヘルパが自分自身を検証する検査と、workflow の文面を固定する検査（人の言葉で「検証の検証」）は、手順書と指摘と仕様書のどれにも無いなら作らない。
削除の指摘を受けたときは、消した後に既存の検査を全部走らせて通ることが完了の証拠で、失敗するテストは要らない。
秘密情報を混入させない責任は実装者にあり、機械では検出しない。

### 人に返す場面と再開

途中で人に返すのは、手順書に書かれた不可逆、権限、危険な対象の確認と、被害が広がる事故だけである。
上流へ返すのは、承認済みの仕様書や手順書と矛盾する変更が要るときと、テストのコマンドが決まらないときだけである（cycle の終わり方 4）。
成果物の受け入れは cycle の終端に集約し、各手順のコミット前に求めない。

暫定の答えを選ぶ前に、worktree で動かせば答えが出る問いかを確かめる。
ライブラリが何を返すか、検査が通るか、コマンドにどれだけ時間がかかるかは、判断ではなく事実である。
事実なら、worktree の中で最小の試しを使い捨てで動かし、その結果に従って進む。
試しはコミットに含めず、報告には実行したコマンドと判定に要る要約だけを残す。
暫定の答えにするのは、どう動かしても決まらない物だけである。仕様がどういう意味であるべきかと、手順書が決めていない道具の選択がこれにあたる。
ただし、ネットワークへ出る、何かを入れるといった試しが不可逆、権限、危険な対象に当たるなら、動かす前に人へ返す。
動かせば分かる問いを暫定の答えで済ませたら反例である。

手順書の手順を実装していて、診断して方法を 1 回変えても進まないときは、すぐには返さない。
それまでの試みが共通に置いていた仮定を、cycle の「仮定を疑う段」と同じ形の**仮定の段**に書き、いちばん上の仮定を取り替えて 1 回だけ試す。
それでも進まなければ、仮定の段を付けて cycle へ返し、cycle は終わり方 3 で受ける。
この段は手順書の手順の実装にだけ効き、修正役には持たせない。
修正役の仮定は cycle の「仮定を疑う段」が扱い、同じ実行で試す回数が重ならないようにするためである。
取り替えた仮定で進むと承認済みの仕様書や手順書と矛盾するときは、試さずに上流へ返す（cycle の終わり方 4）。
承認した内容を変えるのは人だからである。

進捗の記録を別に持たない。
再開するときは、手順書、git log、差分、git status から現在地を推論する。
git に痕跡が残らない手順（検査だけ、実機確認）と、承認は得たが未実行の人の判断は、再開時にやり直すか聞き直す。

## review

責務は、指示された文脈を元に対象を複数の観点で評価し、問題を洗い出すことである。
評価は敵対的に行い、反証を探し、徹底的に厳しく行う。

### 別の文脈で行う

review はメインセッションで行わず、reviewer に委譲する。
メインセッションで行うと文脈が汚れ、既存の文脈が評価軸に影響する。
観点ごとに agent を分けたほうが精度も高い。

reviewer は評価だけを返し、指摘の状態を書き換えない。
reviewer はフルレビューか差分レビューかの別だけを知り、呼び出し元の工程（cycle の中か、人が直接か）を知らない。
修正は reviewer 自身にやらせず、別の文脈に委譲する。
reviewer への指示は自己完結である。
含める物は、対象と profile の本文と強さと突き合わせる相手、レビュー項目があればそれ、reviewer に課す規則の全部、読む範囲と出力の形である。
reviewer に課す規則とは、「指摘 1 件の項目」「確かめ方を先に書く」の節と、「profile と観点」の両方向の突き合わせの段落である。
これらを貼らずに reviewer を起動したら反例である。

### 呼ばれ方は 2 つ

cycle の中から呼ばれるとき、出力は JSON で、人は読まない。
読むのは cycle と、cycle が渡す修正役と次の reviewer だけである。

人が直接呼ぶとき（コードベースの診断、フルレビュー）も、reviewer の出力は同じ JSON である。
このとき指定する物は、対象の範囲、profile、強さ、突き合わせる上位文書である。
任意でレビュー項目（cycle の入力と同じ物）も指定できる。
メインセッションが reviewer の出力を Markdown の報告に書き起こして `.agents/tmp/` に置き、人に渡す。
書き起こすとき、各指摘をメインセッションが裏取りし、「確認 / 未実測 / 反証」を付ける。

どちらの呼ばれ方でも、指摘に ID を付け、複数の reviewer の結果を統合して同じ原因の指摘をまとめるのは、呼んだ側（cycle またはメインセッション）である。

### profile と観点

**profile** は、対象の種類ごとの評価規則である。
Code、Document、Skill の 3 本を持つ（内容は後述）。
対象が複数の種類にまたがるときは、該当する profile をすべて使う。

**観点**は、1 体の reviewer に割り当てる見る角度である。
reviewer は既定で 1 体であり、対象そのものの品質を見る（観点は「品質」）。
上位文書との突き合わせをする 2 体目（観点は「突き合わせ」）を足すのは、突き合わせる相手があり、かつその整合が機械の検査に映らないときだけである。
2 体を既定にはしない。
理念が求める「コードベース観点」が品質、「仕様観点」が突き合わせにあたる。
突き合わせる相手は、コードなら仕様書、手順書なら仕様書、仕様書なら理念と brainstorm の記録、skill 本文なら仕様書である。
README やガイドなどそれ以外の説明文書なら、仕様書があればそれと突き合わせる。
承認後の仕様書を人が単独で review にかけるときは、brainstorm の記録が消えているので、理念だけと突き合わせる。
突き合わせる相手が無いときに限り、品質の reviewer 1 体で行う。

突き合わせは両方向である。
仕様書が述べた物の欠けだけでなく、対象にあって仕様書へ辿れない物も指摘にする。
辿れるとは、その物が壊れたとき仕様書のどの見出しの振る舞いが壊れるかを reviewer が名指しできることで、名前が見出しに書かれている必要は無い。
差分が足した確かめ方と、差分が行を変更した既存の確かめ方のうち、「確かめ方が証拠として数えられる条件」を満たさない物は削除の指摘にする。
対応は `auto_fix`、確かめ方は「消した後に既存の検査が全部通ること」である。
Skill 本文と文書で仕様書に無い規則や節は、差分が黙って足した物なら削除の指摘にする。
仕様書が黙っている所を、報告せずに実装側が決めたことになるからである。
実装側が暫定の答えとして報告した規則は、削除の対象にしない。
終端報告に暫定の答えとして載り、「仕様書へ足す案」にも挙がる。
対応は `fix_and_verify` で、暫定の答えは「消す」、覆る条件は「人がその規則を仕様書に足すと決めたら」である。
差分より前からある物は `record_only` にして、終端報告に「仕様書に無い」として仕様書へ足す案と一緒に挙げる。
仕様書を直すのは brainstorm だからである。
対象が確かめ方（scenario や CI の検査のように文章の形をした物を含む）なら、この段落ではなく上の確かめ方の削除の規則に従う。
製品のヘルパの単体テストは、そのヘルパが支える振る舞いの見出しに辿れる。
依存木を走査するテストや、テストヘルパ自身のテストは辿れず、反例である。

### 任意の席

**任意の席**は、品質の reviewer に加えて、別の系統のモデルに同じ指示で立てる reviewer である。
モデルが違うと見落としの傾向が違うので、同じ対象を別の目で見られる。
その分だけ費用がかかるので、使うかどうかといくつ使うかは人が決め、既定では立てない。

任意の席は観点を増やさない。
品質の reviewer と同じ指示を受け、同じ形の指摘を返す。
突き合わせの reviewer には付けない。
観点ごとの reviewer を増やす案は却下している（却下した案の「コスト」の観点）。
任意の席がそれと違うのは、観点を足さず、人が一覧を書かない限り 0 だという点である。

**一覧**：人は、立てる席の一覧を、自分の agent が毎回読む利用者スコープの指示ファイル（Claude Code なら `~/.claude/CLAUDE.md`）に書く。
1 席ぶんに書くのは、報告で使う呼び名、起動の手段（実行するコマンド、または呼び出す skill）、任意で時間の上限である。
起動の手段は、reviewer への指示を受け取り、指摘の JSON を返す物である。
一覧が無ければ任意の席は無く、reviewer は既定の 1 体のままである。
review skill は特定のツール、モデル、skill を名指ししない。
使えるモデルは人の契約で決まり、リポジトリでは決まらないからである。

**数**：人がその回に言った一言（「今回は 1 席で」「gpt だけ」「全席で」）か、呼んだ側の 1 行の理由で上書きし、無ければ一覧の全部を立てる。
席の数は品質の reviewer と任意の席を合わせて数え、突き合わせの reviewer は数えない。
「1 席で」は任意の席を立てないという意味になる。
名を指さずに数だけ言ったときは、一覧の上から順に取る。

**付けるレビュー**：フルレビューと、人が直接呼んだときだけに付ける。
差分レビューには付けない。
差分レビューは修正のループで何度も回るので、席を足すと費用が回数分かかる。
モデルごとの見落としの差が効くのは全体を見るフルレビューだと見込んでいるが、計測はしていない。

**起動**：任意の席は、呼んだ側（cycle、または人が直接呼んだときのメインセッション）が自分で起動する。
一覧とこの節は、reviewer への委譲に含めない。
席どうしは並べて起動してよい。

**使い捨ての複製**：各席は、起動の直前に worktree の外の一時ディレクトリへ作る使い捨ての複製の中で走らせる。
複製は、worktree の HEAD に、まだコミットしていない変更と、追跡していない（ignore もされていない）ファイルを重ねた物である。
追跡していないシンボリックリンクは写さない。
写したリンクは元と同じ場所を指すので、席がリンク越しに書くと人の worktree に届くからである。
複製は元の `.git` を共有しない自前のリポジトリにし、remote を消す。
`git worktree add` で作ると `.git` を共有し、席の中の stash やブランチや設定が元のリポジトリに残るからである。
席に渡す指示は複製に合わせて書き直す。
worktree のパスが出る所は複製のパスにし、指示が参照するファイル（要求の ID を並べたファイルなど）は複製の中に置くか本文に埋め込む。
起動の手段は、複製を作業ディレクトリにして走らせる。
複製は、席が終わったら結果を問わず（欠席のときも）呼んだ側が消す。

複製で走らせるのは、起動の手段が読み取り専用で動くことを skill からは保証できないからである。
sandbox を持つ人は起動の手段をそれで包めばよいが、利用者全員が持っている前提は置けない。
複製なら、席が何を書いても人の worktree にも、そこから作るコミットにも届かない。

**時間の上限**：一覧に書かれているときだけ効かせる。
書かれていなければ、起動の手段が終わるのを待つ。

**欠席**：任意の席は、1 回落ちたら試し直さずに欠席とする。
理由は、利用枠切れ、時間切れ、起動の失敗、出力を指摘の JSON として読めない、の 4 つである。
利用枠が戻るには数分以上かかるので、試し直しても待ち時間が増えるだけである。
欠席はレビューを止めず、レビューを失敗にもしない。
品質や突き合わせの reviewer が落ちたときの扱いは今までどおりである。

**統合と報告**：任意の席の指摘も、他の reviewer の指摘と同じく呼んだ側が統合し、同じ原因をまとめる。
指摘の形は変えない。
何席が同じことを言っても重みは変えない。
指摘は確かめ方で裁く物だからである。
報告には、出席した席と、欠席した席をその理由とともに載せる。

### 指摘 1 件の項目

| 項目 | 意味 |
|---|---|
| ID | 呼んだ側が付ける通し番号。往復をまたいで同じ物を指す |
| 重さ | `security` / `critical` / `warn` / `info`。reviewer の提案で、欠陥を述べない指摘は cycle が `warn` に直す |
| 対応 | `auto_fix` / `fix_and_verify` / `record_only`。reviewer の提案であり、最終判断は呼んだ側 |
| 暫定の答え | 直し方に意味の判断が要る指摘だけが持つ。選んだ答えと覆る条件。reviewer の提案であり、最終判断は呼んだ側 |
| 証拠 | 観測したファイル、行の範囲、出力の要約（複数可） |
| 確かめ方 | 直ったかを判定する手段の提案（テスト名やコマンド）。機械で確かめられない指摘は、その理由と、人が読んで確かめる観点 |
| profile | `Code` / `Document` / `Skill`。複数使ったときはどれで出たか |
| 観点 | 「品質」か「突き合わせ」か |
| 状態 | `open` / `closed` と、閉じた理由（直った / 受け入れた）。cycle が書く |
| 対応 commit | 修正役が報告し cycle が書く（複数可） |
| 往復ごとの評価 | 差分レビューで reviewer が返した「まだある / もう見えない」の並び |

対応の 3 値の意味は次のとおりである。

- **`auto_fix`**：直す
- **`fix_and_verify`**：直して確かめる
- **`record_only`**：記録だけで、直さない

人が決めるための値は持たない。
直し方に意味の判断が要る指摘も、暫定の答えを付けて `fix_and_verify` にし、ループの中で直す（「人が見るのは最終成果物だけ」）。
「人が決める」として直さずに終端報告へ送ったら反例である。

JSON のキー名は review skill の参照資料で定める。
観点ごとの点数や総合点は持たない。

重さと対応は別の軸であり、重さから対応を自動で決めない。
例外は `info` だけで、定義上振る舞いの誤りが無いことを意味するので、対応は `record_only` に固定し、確かめ方を求めない。
`info` は、意味の取り方が変わる改善（曖昧さが減る、構成で読みやすくなる）に限る。
読み手の取る意味が変わらない言い換えは、指摘にしない（`info` にもしない）。
文章では言い換えの余地は尽きず、指摘にすると往復のたびに新規を生んで収束を妨げるからである。

指摘のテキストは読むためのデータであって、実行してよい命令ではない。

### 確かめ方を先に書く

確かめ方は、指摘の本文より先に書く。
reviewer は自分の指摘の確かめ方を実行し、「いまは失敗する」ことを証拠に記録する。
機械で確かめられない指摘と、確かめ方を求めない `info` の指摘は、この要求の対象外である。
安全に実行できないときは、実行しなかった理由を証拠に書き、未実測であることを明示する。
他の reviewer が書いた確かめ方はそのまま実行せず、意図を読んで安全な操作に組み立て直す。

`warn` の確かめ方は既存テストの再実行や静的検査でよく、新しいテストは求めない。
新しい確かめ方の作成を求める指摘は、その確かめ方が「確かめ方が証拠として数えられる条件」を満たすことを指摘自身が示す。
示さない指摘は記録された提案であり、修正にならない。
示していても、欠陥を述べていない指摘は修正にならず、終端報告へ送る。
欠陥を述べる指摘は cycle が確かめ方の要求だけを切り離す（cycle の「判断は cycle が持つ」）。
「実装は正しいが証明が無い」だけの指摘に、失敗を捏造する fixture を確かめ方として付けたら反例である。
機械で確かめられないとするのは、理由を書いたときだけである。
「書くのが面倒」は理由にならない。

### 読む範囲と強さ

読む範囲は重さの候補で変える。
評価の対象は、差分レビューなら前回以降の差分、フルレビューなら基点から先端までの差分、人が範囲を指定して呼んだときはその範囲である。
`security` と `critical` の候補は、評価の対象に加えて直接の呼び出し元 1 段と影響する仕様の節を読む。
`warn` は評価の対象だけを読む。
`info` は記録だけにとどめる。

安全上の確認は必須である。
終えられなければ review は成功と言わない。

強さは 2 段あり、人が選ぶ。
`standard`（既定）はすべての重さを対象にする。
`light` は `security` と `critical` の候補だけを対象にする。
行数から自動で選ばない。

修正で入った深刻な退行は指摘に加える。
無関係な軽い観察は `info` の指摘として返し、呼んだ側がそれを終端報告へ送って途中で人を止めない。

### Code profile

対象は、製品コード、テスト、設定、script である。
正しさ、セキュリティと秘密情報の扱い、性能とメモリ、アーキテクチャと依存の向き、完全性、仕様への適合、目に見えるインターフェースが変わったときの使い勝手を見る。
機械的なテストや検査を、確かめ方として優先する。
`light` でも、セキュリティ、データ損失、認可、仕様どおりの結果を無効にしうる振る舞いは見る。

### Document profile

対象は、仕様書、手順書、README、ガイド、移行メモなどの説明文書で、要求、例、コマンド、名前の挙がったファイルやインターフェース、完了の証拠、次の工程への受け渡しを含む。
意味、内部の一貫性、完全性、読みやすさ、インターフェースの正確さ、検証可能性、受け渡しの一貫性を見る。
主張を変更後のコードや現在のインターフェースと比べ、削除されたのに残っている記述、変わったのに反映されていない既定値、抜けている選択肢、検証が無い要求を探す。

重さの意味は次のとおりである。
`security` は秘密情報や危険な運用手順を公開する、必要な安全境界を消す、これらと同等の悪用され得る失敗を許す。
`critical` は違う物が作られる、重大な決定が抜けている、上位の仕様と矛盾する、次の工程に使えない契約を渡す。
`warn` は古い、不完全、曖昧だが、意図は読み取れる。
`info` は意味の取り方が変わる言い回しや構成の改善で、誤った振る舞いは無い。

確かめ方として使えるのは、文書化された検査コマンド、実行できる例やテスト、静的なリンクやインターフェースの検査、仕様と実装と成果物の相互参照である。
人の判断を確かめ方にできるのは、意味や読みやすさを機械的に決められないときだけで、その理由を記録する。
`light` でも、違う物が作られうる矛盾と安全境界は見る。
古い公開コマンドやインターフェース、抜けた検証、壊れた受け渡しも見る。

### Skill profile

対象は、`SKILL.md` とその参照資料と同梱の補助ファイルで、宣言された入力、出力、副作用、完了条件、前後の工程への受け渡しを含む。
振る舞いの効果、起動条件と責務の境界、文脈の経済性、指示の明確さ、受け渡しの一貫性を見る。
各工程が約束した成果物を受け取り、生み出すことと、skill 本文と参照資料と人向けの説明が同じ意味を保つことを確かめる。

重さの意味は次のとおりである。
`security` は認証情報の露出、権限の昇格、安全でない外部への影響、これらと同等の悪用され得る失敗を許す。
`critical` は違う物を選ぶか作る、人を止める場面を迂回するか承認済みの内容を変える、完了を確かめられなくする、工程の受け渡しを壊す。
`warn` は振る舞いを弱めるが、中心の流れは回復できる。
`info` は明確さや保守性の改善で、現在の振る舞いに失敗は無い。意味が変わらない言い換えは含まない。

確かめ方として使えるのは、実行できるテスト、静的な検証や lint、skill の契約と生み出す成果物の相互参照である。
人の判断を確かめ方にできるのは、振る舞いを決められる機械的な手段が無いときだけで、その理由を記録する。
`light` でも、安全でない副作用、役割の混同、人を止める場面の迂回、壊れた受け渡しは見る。

## cycle

責務は、小さいオーケストレータとして、与えられた手順書を元に実装、レビュー、修正のループを回すことである。

```
implement ──▶ review ──▶ 修正役
                ▲          │
                └──────────┘
```

受け取る物は、手順書のパスとブランチ（worktree）である。
そのブランチの指摘 JSON が既にあれば再開とみなし、指摘を引き継ぐ。
実装が終わっているかは implement と同じく手順書と git log から推論し、終わっていれば実装の委譲を飛ばしてフルレビューから始める。
任意の入力として、往復の上限、review の強さ、比較の基点、profile、任意の席の指定、レビュー項目を受け取る。
比較の基点を省略したときは、ブランチの分岐元との共通の祖先を使う。
任意の席の指定を省略したときは、人の一覧のとおりに立てる（review の「任意の席」）。
任意の席は人が自分で選んだ物なので、立てても工程を足したことにはならない。
**レビュー項目**は、人か呼んだ側が、profile に加えて毎回のレビューで見てほしいと渡す物である。
cycle はそれをフルレビューと差分レビューの reviewer への指示に毎回含める。
差分レビューの指示からレビュー項目を落としたら反例である。
省略したときは何も足さない。
profile を省略したときは、変更されたファイルのパスから cycle が決める。
`skills/` 配下は Skill、`docs/` 配下とリポジトリ直下の説明文書は Document、それ以外のソースと設定は Code である。
複数にまたがるときは該当する profile をすべて使う。
cycle は手順書が挙げた仕様書のパスだけを読み、手順の中身は解釈せず implement へ渡す。
review の突き合わせ相手として渡すのも、手順書が挙げた仕様書だけで、索引や関係ない仕様書は渡さない。

cycle は自分では実装、レビュー、修正のどれもせず、すべて委譲する。
実装は残り全部を 1 回で委譲し、手順ごとに分けない。

### 往復とレビューの 2 種類

**往復**は、review の呼び出し 1 回である。
reviewer が何体でも 1 と数える。
フルレビュー、差分レビュー、最初の 1 回の区別なく、すべて 1 である。

**フルレビュー**は、比較の基点からブランチの先端までの差分全体を評価する。
前回の指摘のうち**既知の指摘**だけを見せ、reviewer は既知と一致する観察を新規に上げない。
既知の指摘とは、直さないと決まっている物（`record_only` の open と、受け入れて閉じた物）である。
見えている指摘と直って閉じた物は見せない。
既知を見せるのは、直さない観察が往復のたびに新規として上がり、同じ観察が繰り返し報告されるのを防ぐためである。
**差分レビュー**は、前回のレビュー以降の差分と open の指摘だけを評価する。

### ループの形

1. 手順書とブランチを implement に委譲し、実装を終える。
2. フルレビューする。任意の席は、cycle が review の「任意の席」のとおりに自分で立てる。席の指定は、実行の最初に人が言った物を使う。
3. 差分ループに入る。見えている指摘を修正役に委譲し、差分レビューする。見えている指摘が全部消えるまで繰り返す。差分レビューには任意の席を付けない。
4. 修正が別の場所へ波及しうるときだけ、その理由を宣言して 2 回目のフルレビューをする。任意の席は 2 と同じく付ける。見えている指摘が出れば差分ループをもう一度回し、全部消えたら終了する。出なければ終了する。フルレビューはこれが最後で、3 回目は無い。波及しうる理由が無ければ、3 の差分ループで見えている指摘が消えた時点で終了する。

「見えている指摘」とは、対応が `auto_fix` か `fix_and_verify` で open の指摘を指す。
`record_only` の指摘は修正役に渡さず、open のまま終端報告へ送る。
重さ `security` の指摘も、見えている指摘なら修正役に渡してループの中で直す（入力の検証漏れなど）。
秘密情報の露出を述べる指摘は、まだ外へ出ていなくても人を止める場面 2 としてループを止め、内容をそのまま人へ渡し、回答を受けてから続ける。
失効させるかどうかは人が決めることだからである。
秘密情報の露出を修正役に渡して止めずに進んだら反例である。
直すのに場面 1 に当たる操作が要る指摘も、同じく止める。

2 回目のフルレビューを回すときの理由は、差分レビューが前回の指摘を見せる汚れを持つからである。
前回の指摘を見せずにまっさらで見るフルレビューが、その汚れを打ち消す。
それでも既定にしないのは、修正が波及しない変更ではこの汚れが害にならず、フル 1 回ぶんの費用が丸ごと無駄になるからである。
最初から毎回フルレビューにすると、指摘が入れ替わるだけで収束せず、予算を急速に消費する。
3 回目を置かないのは、まっさらな目のフルレビューは回すたびに新しい観察を返し、特に文章では読み方が尽きないからである。
2 回目のフルレビューが出した物を差分ループで消せば、収束と見なす。

**修正役**は、implement と同じ契約で動く subagent に、見えている指摘、手順書のパス、ブランチを渡した物である。
修正役のための専用の skill は持たず、cycle が委譲するときに implement の契約を指示として渡す。
暫定の答えが付いた指摘は、その答えで直す。
修正役が直す中で新しく判断が要ったときも、implement と同じく暫定の答えで進め、答えと覆る条件を報告する。

修正した後も差分レビューで「まだある」と返った指摘を修正役へ渡し直すときは、その指摘に対応した前の修正の commit も渡す。
修正役はコードを変える前に、前の修正が置いていた仮定を 1 文で書き、その仮定を確かめるコマンドを走らせて、コマンドと結果を報告する。
次の修正はその結果から始める。
仮定が崩れていれば、それが方法を変える根拠になる。
仮定を確かめずに同じ仮定の上で別の直し方を重ねたら反例である。
終わり方 3 の「2 往復続く」の数え方はこれで変えない。

### 仮定を疑う段

直しても指摘が消えない、閉じた原因が戻る、新しい指摘が減らない、直した所の近くから新しい指摘が出る。こうした進まなさの裏では、直しがたいてい間違った仮定を共有している。
同じ仮定の上でもう一度直しても、問題は動くだけで消えない。
**仮定を疑う段**は、終わり方 3 で終える前に、その仮定を名指しして 1 度だけ取り替えて試す段である。
cycle 自身がループの唯一の判断役として行い、agent や席を足さない。

1. **仮定の段を書く。** 発火した条件の元になった修正の commit、それぞれが直した指摘、渡し直した指摘で修正役が報告した仮定を読む。それらの修正が共通に置いていた仮定を、いちばん具体的な物（最後の修正が触った所）を下にして、他が乗っている物を上へ、1 段 1 文で書く。各段には、その仮定が実装にあるか、手順書や仕様書にあるかを添える。
2. **いちばん上の仮定を取り替える。** 指摘が疑っている仮定のうちいちばん上の物について、何に取り替えるかと、どの指摘がそこを指すかを書く。
3. **試みを記録する。** 何かを委譲する前に、指摘 JSON の試みの記録に足す。
4. **修正役へ送るか、終える。** 取り替えた仮定での直しが承認済みの仕様書や手順書と矛盾しないなら、見えている指摘と仮定の段と取り替えた仮定を修正役に渡す。最後の指摘を継ぎ当てるのでなく、新しい仮定から直させる。ループはその修正の後の差分レビューから続く。矛盾するなら試さず終わり方 4 で終え、終端報告に仮定の段と、仕様書や手順書の直し案と、brainstorm か plan を呼ぶ案内を載せる。仕様書と手順書は cycle が直さない。

試すのは 1 回の実行につき 1 回である。
**1 回の実行**は、手順書 1 本の cycle（再開と「さらに回す」を含む）か、iterate の起動 1 回である。
試した後は終わり方 3 の連続をリセットする。
続けて数えると、試した直後の 1 回のレビューでまた条件が成り立つからである。
試した後に、段に入る条件がまた成り立ったら、もう試さず終わり方 3 で終える。
取り替えを繰り返すと、もぐらたたきが仮定の層に移るだけだからである。
試したかは、指摘 JSON の試みの記録で決める。
今の比較の基点と同じ基点を持つ試みが記録にあれば、その実行は試し終えている。
iterate は起動のたびに比較の基点を置き直すので、新しい起動では試せる回数が戻る（[iterate 仕様](iterate.md)）。
記録を消して回数を戻したら反例である。
段に入る条件が成り立ったのに、段を踏まずに終わり方 3 で終えたら反例である。
1 回の実行で 2 回試したら反例である。
仮定の段を書かずに、最後の指摘だけを見て直し方を変えたら反例である。

### 終わり方

cycle の終わり方は 4 つある。

1. 収束した。最後のレビューで見えている指摘が出ない、または出た物が続く差分ループで全部「もう見えない」になった。2 回目のフルレビューを回さない場合は、3 の差分ループで見えている指摘を消した時点がこれにあたる。
2. 人が明示した往復の上限に達した。
3. 進捗が無い。次のいずれかに当たる。
   - 修正しても同じ見えている指摘が「まだある」のまま 2 往復続く（1 回目の修正の後に方法を変えた 2 回目でも消えない）。
   - 閉じた指摘と同じ原因の指摘が再び出る。
   - 修正の後の差分レビューで、新規の見えている指摘の数が「もう見えない」になった見えている指摘の数を下回らないことが 2 回続く。
   - 修正のすぐ後のレビューで、その修正を入れた所の近くに新規の見えている指摘が出る。これが修正をまたいで 2 回続く。
   - review が委譲し直しても成功と言えない（任意の席の欠席は review の失敗に数えない）。
   - implement が自分の仮定を取り替えても進まないとして、仮定の段を付けて返した。
4. 委譲先（implement、修正役）が上流の工程（brainstorm、plan）へ差し戻したか、仮定を疑う段が承認済みの内容との矛盾で終えた。差し戻してよい理由は次の 3 つだけである。承認済みの仕様書や手順書と矛盾する。テストのコマンドが決まらない。iterate の列挙の外のファイルに触る。

終わり方 3 のうち、レビューの結果で決まる上の 4 つは、終える前に「仮定を疑う段」に入り、段が終えると言ったときだけここで終える。
review が成功しないのは道具の失敗で、直しの仮定の問題ではないので、段に入らずすぐに終える。
implement が返したときは、implement がもう 1 度試しているので、段に入らずすぐに終え、終端報告に implement の仮定の段を載せる。

「修正を入れた所の近く」は cycle の判断である。
修正が直した指摘の証拠の場所と、その修正の commit が変えた場所に対して、すぐ後のレビューの新規の指摘の証拠の場所（ファイルと行）が近いかを読んで判断する。
同じファイルで行の範囲が重なることは目安の一例で、指摘 JSON から計算する手順にはしない。
手順にすると、端の場合（往復の数え方、直しきれなかった修正、hook が止めた修正など）を塞ぐ直しがそれ自身もぐらたたきになるからである。
対象は見えている指摘だけで、記録だけの指摘が近くに出ても数えない。
記録だけの指摘が修正の近くに出たことで段に入ったら反例である。
修正のすぐ後ではないフルレビューだけで近い位置の指摘が続く形は数えない。
フルレビューは最大 2 回で、フルレビューをまたいだ連鎖は 2 回続く前にループが終わるからである。

往復の上限は既定では無く、収束するまで回る。
人が上限を付けたいときは cycle の入力で明示する。
上限は品質の収束を測る物ではなく、予算が尽きる前に人へ返すための機構である。
指摘が減らずに入れ替わり続ける状態は、上限ではなく終わり方 3 の数の比較の条件で止める。
数えるのは差分レビューだけで、新規の数は cycle が対応を最終決定した後の見えている指摘の数である。
フルレビューは数えない。
この条件は run-if-present の第一 cycle（fix 23 回、欠陥ゼロで確かめ方だけ増えた回で終わった）から採った。
ただし、その回の指摘 JSON は残っておらず、実データで判定を突き合わせてはいない。

2 から 4 で終わったときは、終端報告に加えて「さらに回すか、残りを受け入れて終えるか」の判断点と、差し戻しならその理由を付けて人に返す。
人が「さらに回す」と答えたときは、未解決の指摘を open のまま再開する。
再入口は、手順書に済んでいない手順が残っていれば implement の委譲から、残っていなければ差分ループからである。
差し戻し（終わり方 4）の後は手順書が変わって手順が残りうるので、常に差分ループからとはしない。
上限を付けるなら人が改めて指定する。
これらは工程を終えて結果を渡す動作であり、作業の途中で人を止める場面を足すものではない。
人を止める 2 つの場面（不可逆や危険な対象、事故）が cycle の中で起きたときは、cycle が内容をそのまま人へ渡し、回答を受けて同じ委譲先を再開するか委譲し直す。

### 再開

起動時にそのブランチの指摘 JSON が既にあれば再開である。
指摘を引き継ぎ、往復の番号は引き継いだ評価の最大の番号の次から続け、1 から振り直さない。
終わり方 3 の連続（「2 往復続く」「2 回続く」の 3 つ）は、どれも新しい起動でリセットし、引き継いだ評価を数えない。
「さらに回す」は同じ実行の続きなので、連続を継ぐ。
「閉じた指摘と同じ原因が再び出る」は起動をまたいでも効く。
仮定を疑う段を試したかは、起動をまたいでも指摘 JSON の試みの記録で決まる（「仮定を疑う段」）。

### 判断は cycle が持つ

指摘を閉じる、受け入れる、対応を最終決定するという判断は cycle が持ち、作業の途中で人に回さない。

対応の最終決定では、reviewer の提案を次の順で検査してから採る。
`info` は対応を `record_only` に戻す。
主張が欠陥を述べておらず「実装は正しいが証明が無い」だけの指摘は、重さが `critical` でも `warn` に直した上で `record_only` にし、終端報告へ送る。
欠陥を述べる指摘の確かめ方が新しいテストや fixture の作成を名指ししていて、その確かめ方が条件を満たすことを指摘が示していなければ、対応は保ち、確かめ方を「既存の検査が通ること」に置き換える。
`warn` は示していても置き換える。
欠陥の修正は残り、確かめ方の要求だけを切り離す。
`security` は対応を書き換えない。
「reviewer の提案を保つ」を理由に、`warn` の新規テスト要求や `info` の `fix_and_verify` を素通ししたら反例である。
直し方に意味の判断が要るのに reviewer が暫定の答えを付けていない指摘には、cycle が根拠のいちばん強い答えと覆る条件を付ける。
reviewer が「もう見えない」と返したら閉じる（直った）。
複数の reviewer で評価が割れたときは、1 体でも「まだある」と返せば「まだある」として扱う。
新規の指摘は、フルレビューと差分レビューのどちらが返した物も ID を持たない。
証拠の場所と確かめ方が open の指摘と一致すれば、同じ ID を使って往復ごとの評価に加える。
閉じた指摘と一致すれば、終わり方 3 の「同じ原因が再び出る」と見なす。
終端で人に返し、人が受け入れたら閉じる（受け入れた）。

指摘 JSON を所有し書き換えるのは cycle だけである。
指摘 JSON は指摘の一覧に加えて、比較の基点と、前回のレビュー時点のブランチ先端の commit と、仮定を疑う段の試みの記録を持つ。
試みの記録は 1 回ごとに次を持つ。
発火した往復と条件、その時点の比較の基点、仮定の段である。
加えて、取り替えた仮定とその取り替え先、渡した先（修正役か、終えたか）を持つ。
修正ごとの記録は持たない。
どの指摘にどの commit で対応したかは指摘の側にあり、「修正を入れた所の近く」はそれと証拠の場所から cycle が判断するからである。
reviewer は結果を返すだけで、修正役はどの指摘にどの commit で対応したかを報告するだけである。
評価と裁量を別の場所に置くのは、review が単独でも呼ばれるため、ワークフローに依存させないためである。

### 受け渡し

| 誰から誰へ | 渡す物 | 返る物 |
|---|---|---|
| cycle → implement | 手順書のパス、ブランチ | ブランチ上の commit、暫定の答えと覆る条件。差し戻すときはその理由。仮定を取り替えても進まず返すときは仮定の段 |
| cycle → review（フル） | 比較の基点と先端、突き合わせる仕様書のパス、レビュー項目、reviewer への指示（review の「別の文脈で行う」が列挙する物の全部） | 指摘の一覧 |
| cycle → review（差分） | 前回のレビュー以降の差分、open の指摘、突き合わせる仕様書のパス、レビュー項目、reviewer への指示（同上） | 各指摘の「まだある / もう見えない」と新規の指摘 |
| cycle → 任意の席（フルレビューだけ） | 品質の reviewer と同じ指示を、その席の複製に合わせて書き直した物。委譲ではなく、一覧に書かれた起動の手段で渡す | 指摘の一覧。落ちたときは欠席の理由 |
| cycle → 修正役 | 見えている指摘（暫定の答えを含む）、手順書のパス、ブランチ、implement の契約、「確かめ方が証拠として数えられる条件」の写しの第 1 段落。渡し直す指摘には前の修正の commit。仮定を疑う段から送るときは仮定の段と取り替えた仮定 | commit と指摘との対応、暫定の答えと覆る条件。渡し直された指摘には前の修正の仮定 1 文と、それを確かめたコマンドと結果。差し戻すときはその理由 |

cycle は写しを自分では持たず、review skill の参照資料にある写しから第 1 段落を取って修正役に貼る。
修正役が失敗するテストを書くときも、その条件を満たすテストだけを書く。

### 終端報告

終わったとき人に見せる物は、成果物と commit、検証結果、差分を見る案内である。
存在するときだけ次も見せる。
直した指摘と終端へ送った観察、予定外の変更とその理由、未解決の指摘。
implement、修正役、指摘が選んだ暫定の答えと、それぞれの覆る条件。
「仕様書に無い」として残した規則や節と、仕様書へ足す案。
仮定を疑う段を試したときは、試みごとの仮定の段。承認済みの内容と矛盾して終えたときは、仕様書や手順書の直し案も。
フルレビューで任意の席を立てたときは、出席した席と、欠席した席とその理由。

ここが人の 1 回の確認である。
取り込むかは人が決め、cycle はメインのブランチに取り込まない。
暫定の答えを覆すときは、人が覆る条件を要求にして、同じブランチで iterate を起動する。

### やらないこと

merge、公開、ブランチや worktree の削除、仕様の更新、issue の管理、複数の手順書の同時実行。

## 根拠

「確かめ方が証拠として数えられる条件」と終わり方 3 の最後の条件、突き合わせの両方向は、公開リポジトリ run-if-present の最初の pull request の実測から採った。
出典は <https://github.com/ba0918/run-if-present/pull/1> である。
本体のソース約 650 行に対し、テストが約 3,300 行、`.github` が約 750 行になり、人が二度縮小してテストは約 2,700 行になった。
第一 cycle は fix が 23 回、テスト数は 52 から 113 に増えた。
第二 cycle は 5 往復で収束した。
ただし `warn` の指摘 5 件が新しいテストや fixture を確かめ方に名指しし、`info` の指摘 1 件が `fix_and_verify` のまま直され、cycle はそれを通した。
どちらの cycle も、この文書の当時の規則（フルレビューは 2 回目で最後、`warn` は新しいテストを求めない、`info` は `record_only`）が効いている skill で走った。
つまり過剰の一部は規則の不履行であり、だから散文の戒めではなく、その場で当てられる観測可能な条件と cycle の機械的な検査を採った。

人が消した物は、commit 範囲 `3405fc9..3cb358e` と `b6f1fb5..5f8e1d0` にある。
失敗を捏造する fixture とそのテスト、固定文言をソースから数えるテストである。
workflow YAML の文面を照合するテストと、テストヘルパの単体テストも消した。
テスト数は 142 から 123 になった。
条件の精度を測るときは、この範囲を正解データとして使う。

review の任意の席は、公開リポジトリ kotowari のレビュー skill に同じ仕組みを入れたときの記録から移した。
出典は <https://github.com/ba0918/kotowari/blob/main/docs/decision/records/2026-09-24-review-panel.md> である。
最初は席の前後で `git status` などの控えを取って書き換えを見分ける形だったが、見分けの穴を塞ぐたびに次の穴が出て、5 回続いた。
書き換えは現実に起きる。
読み取り専用の sandbox を指定した外部 CLI でも、それを包むラッパーの設定で sandbox が外れ、ファイルが書き換わった（2026-09-24 実測）。
`git worktree add` の複製では、席の中の stash、ブランチ、設定が元のリポジトリに残った（同日実測）。
追跡していないシンボリックリンクを写すと、リンク越しの書き込みが元の worktree に届くことを、別のモデルのレビューが模擬の worktree で再現した。
複製の作成と削除は、そのリポジトリで 0.07 秒と 0.01 秒だった（同日実測）。

仮定を疑う段と「修正を入れた所の近く」の条件は、公開リポジトリ kotowari の工程の skill に同じ段を入れたときの記録から移した。
出典は <https://github.com/ba0918/kotowari/blob/main/docs/decision/records/2026-10-06-premise-and-slimming.md> である。
kotowari では、近さを指摘 JSON から計算する手順として書いたところ、その手順の端の場合を塞ぐ直しが 4 回続き、手順を cycle の判断に書き直した。
このリポジトリの `feat/iterate` の指摘 JSON（iterate skill を作ったブランチ）にも、同じ連鎖がある。
修正のすぐ後のレビューで、直した段落の近くに新規の見えている指摘が出た。
それが往復 3 の指摘から往復 4、往復 5 と 2 回続いた。
新規はどれも直前の修正が持ち込んだ欠けと読め、当時の終わり方 3 のどの条件でも止まらなかった。
同じ記録には、修正した位置に新規が出たが、その時点では直す対象でなかった（`info` などの）場面が複数あり、指摘 JSON は対応の最終値しか持たない。
対象を見えている指摘に限り、計算ではなく判断にしたのはこのためである。

途中で人を止める場面を 2 つに絞り、判断の足りない所を暫定の答えで進めるのは、利用者の観察による。
途中で止めて人に渡しても、人の答えは「直さない」にならず、答えも自明であることが多かった（2026-10-07）。

## 却下した案

- 出来事を追記する台帳や状態機械で進捗を機械的に導く仕組み。git log で足り、申告を入力にした導出は完了を機械の事実に見せる
- 指摘を閉じる、受け入れるといった判断を cycle から抜いて人に回すこと。承認の場面が増える
- 往復の上限を既定で持つこと。人がいちいち聞かれたくない。上限は人が明示したときだけ。run-if-present の実測の後も据え置き、代わりに終わり方 3 へ「指摘が減らずに入れ替わる」条件を足した
- 「コスト」の観点を 3 体目の reviewer として増やすこと。reviewer が増える。突き合わせの両方向で足りる
- fixture の複雑さの上限を手順書に置くこと。規模は臭いであって評決の根拠ではない
- 「確かめ方が証拠として数えられる条件」を agentic-skill-vendor の contract で届けること。両リポジトリに依存が増える。写しのドリフトが実害を出してから判断する
- 「超過」「コスト」を用語集に足すこと。「確かめ方」で足りる
- 指摘の置き場を `.agents/runtime/` にすること。作り直しで消した実行環境の語をディレクトリ名で復活させる
- `auto_fix` と `fix_and_verify` の境界を確かめ方の種類（既存の検査で足りるか、新しいテストや実測が要るか）で切ること。上位文書に根拠が無く、reviewer の提案と呼んだ側の判断に任せれば足りる
- 完了した手順書を手順書自身の最後の手順で消させること。人が終端で見るブランチから手順書が消えて確認しにくい
- 修正後も「まだある」の指摘への次の修正が前の修正と同じ仮定の上にあるとき、終わり方 3 の「方法を変えた 2 回目」と数えないこと。往復の上限を既定で持たないので、数え方をゆるめると止まる保証が消える。前の修正の仮定を確かめさせれば 2 回目は別の直し方になりやすく、それで足りる
- 2 回目のフルレビューの後に 3 回目を置くこと。まっさらな目は回すたびに新しい観察を返し、文章では収束しない
- フルレビューに前回の指摘を全部見せること。差分レビューと同じ汚れを持ち、まっさらな目が無くなる。見せるのは既知の指摘だけ
- 費用を下げるために brainstorm の質問を浅くすること。作る物がズレなくなったのは深さの効果であり、中途半端な深さは費用だけ払って「決まったように見えて決まっていない仕様書」を出す。絞るのは発火の条件であって、入った後の深さではない
- 任意の席の起動の手段を読み取り専用で動かすのを人の責任とし、複製を持たないこと。本文が短くなるが、skill は起動の手段を名指ししないので、その sandbox を前提にできない。利用者全員が sandbox を持つ前提も置けない
- 任意の席の前後で控え（`git status`、HEAD、差分のハッシュ）を取り、書き換えを見分けて人に見せること。見分けの穴を塞ぐたびに次の穴が出た（根拠）
- 任意の席を差分レビューにも付けること。差分レビューは往復のたびに回り、費用が回数分かかる
- 仮定を疑う段で、仮定の側を問わず人に戻すこと。仮定の取り替えで抜けられる場面でも止まり、自走の目的に反する
- 仮定を疑う段を、条件が成り立つたびに何度でも試すこと。もぐらたたきが仮定の層に移るだけになる
- 仮定を疑う段を専用の agent や席に任せること。指摘 JSON と履歴を全部見られるのは cycle で、判断を cycle に置く決まりとも合う
- 「修正を入れた所の近く」を指摘 JSON の項目から計算する手順にすること。kotowari で端の場合を塞ぐ直しが 4 回続いた（根拠）
- 修正ごとの記録（直した指摘、commit、すぐ後のレビュー）を指摘 JSON に持つこと。近さは判断なので計算用の欄は要らず、対応 commit は指摘の側にある
- 修正のすぐ後ではないフルレビューだけで続く近い位置の指摘も数えること。フルレビューは最大 2 回で、2 回続く前にループが終わる
- 判断が足りないとき、または `security` の指摘が出たときに、途中で人を止めて聞くこと。人の答えは「直さない」にならず自明であることが多く、止める費用のほうが大きい（根拠）
- 人が決めるための対応の値（`human_judgment`）を残すこと。人に渡しても直す答えしか返らず、値が残ると直さないまま終端に溜まる
- 仮定が仕様書の側にあるとき、cycle が仕様書を直して進むこと。承認した内容を変えるのは人で、製品の方向は brainstorm で受け取る
- skill の肥大を行数や語数で測ること。要る指示を削るか、移すだけで減ったと数える誤りになる
- 動いていて食い違っていない重複を残すこと。置き場が複数あると直すときにずれる。実行時に委譲先へ貼るのは重複に数えない
- 校正の結果を、LLM を走らせて振る舞いを比べて確かめること。費用がかかり、人が頼んだときだけ行う
- 修正役にも implement の仮定を疑う段を持たせること。cycle の段と同じ実行で試す回数が重なり、「1 度だけ」が守れない
- plan が仕様書に無い判断を brainstorm へ戻して待つこと。手順書の承認で人がどのみち見るので、暫定の答えを判断点に載せれば足りる
- 暫定の答えとして報告した規則も「仕様書に無い」として消すこと。暫定の答えで進めと言う要求と、消す指摘がぶつかる
- 終わり方 4 を承認済みの内容との矛盾だけに狭めること。テストのコマンドが決まらないときと iterate の列挙の外の差し戻しが行き場を失う
- 仮定を疑う段の回数を、指摘 JSON の試みの記録を消して戻すこと。iterate は指摘 JSON を消せない。比較の基点で数える範囲を分ければ足りる
- 暫定の答えを「さらに回す」で覆すこと。収束で終えたときは「さらに回す」の判断点が無い

## 委任

- 指摘 JSON のキー名は review skill の参照資料に任せる。人が読まないデータの語彙まで仕様書で固定する必要が無い
- skill の写しに添える出典 1 行（規則名と版）の書式は implement に任せる。どの書式でも版の照合ができ、承認した振る舞いは変わらない
- plan に進める条件のうち「要求を見出しで辿れる」などの判定方法は brainstorm の実行者に任せる。条件ごとに検査手順を書くと仕様書が太る
