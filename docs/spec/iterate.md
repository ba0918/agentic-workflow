# 小さいタスク skill 仕様

この文書は、仕様書と手順書のどちらも要らない小さいタスクを回す skill（iterate）の約束を、人が読んで判断できる形で書いたものである。
skill は `skills/ba0918-iterate/` に置き、本文と参照資料は LLM 向けの英語で、この文書の内容を実行者への指示として写したものである。
両者の意味が食い違ったときは、この文書を正とする。
この文書の上位に理念（`docs/principles.md`）があり、食い違ったときは理念に従う。
用語集はリポジトリ直下の `CONTEXT.md` にある。

iterate は、開発ワークフロー仕様（`docs/spec/workflow.md`）が定める 5 つの skill の流れの外にある入口である。
cycle が「手順書あり」の入口なのに対し、iterate は「手順書なし」の入口で、どちらも人が対話から起動する。
5 つの流れには加わらず、その仕様書も変えない。
cycle と同じ約束は写さず、開発ワークフロー仕様の cycle の節を見出しで参照する。
実行環境、状態を保存する仕組み、状態を読み書きする script を持たないという縛りは、5 つの skill と同じ形で効く。
skill 本文と参照資料の行数の上限は合計で 113 である。
値は作り直し前の本文 450 行から、持ち越さない節の 337 行を引いた実測から取った。
持ち越さないのは、実行環境の文脈、文脈取得のフォールバック、連続呼び出しの検出、大きいと判定したときの続行、レビューと Codex の節である。
手順書への追記、完了報告、軽いレビューの参照資料、ファイル数による判定も持ち越さない。
skill 本文は実行時に cycle の skill を名前で呼び出して本文を読み込むので、実行者が読む量は上限より多い。
超えたら肥大化と見なし、減らす。

## 責務

責務は、仕様書や手順書が要らないくらい小さいタスクのオーケストレータとして、実装、レビュー、修正のループを回すことである。
やることは cycle とほぼ同じで、違いは手順書の代わりに要求を受け取ることと、ループの前に小さいタスクかどうかの判定が付くことである。
iterate は cycle と同じく、自分では実装、レビュー、修正、判定のどれもせず、すべて別文脈の agent に委譲する。
人の要求が曖昧、仕様書と矛盾する、影響が読めないなど「小さいタスク」に収まらないと判定したら、実装を始めずに止まり、行き先を案内する。

iterate は人が対話から起動する。
cycle からは呼ばず、cycle の終端報告や指摘 JSON を入力として受け取らない。
cycle や iterate の直後に起動するときも、対話から起動するときも意味は同じで、メインセッションが対話で知っていることを要求に込めて渡す。
cycle のループは iterate のループと同じ物なので、cycle の中で小さい直しが要っても cycle 自身が回す。
cycle の側から iterate を呼ぶ必要は無い。

## 受け取る物と返す物

受け取る物は、作業ブランチとその worktree のパス、要求の 2 つである。
任意の入力は cycle と同じ 4 つ（往復の上限、review の強さ、比較の基点、profile）に、突き合わせる仕様書のパスを足した 5 つである。
既定も cycle と同じで、強さは `standard`、上限は無し、比較の基点はブランチの分岐元との共通の祖先、profile は変更されたパスから決める。
ブランチと worktree は、cycle と同じく、iterate を起動する前にメインセッションが 1 つ用意する。
ブランチ名はメインセッションが要求を表す短い名前で付け、接頭辞は決めない。
cycle または iterate の直後に同じブランチで頼まれたときは、そのブランチのまま使い、新しく切らない。
iterate は自分でブランチや worktree を作らない。

返す物は、ブランチ上の commit と終端報告である。
判定で止まったときは、commit を作らずに案内だけを返す。
実装の途中で差し戻されて止まったときは、それまでの commit をブランチに残し、終端報告に成果物と commit と差分を見る案内を載せ、そこに案内を足す。
途中の commit を消したり、ブランチを巻き戻したりしたら反例である。

### 要求

**要求**は、人の言葉に、メインセッションが対話で知っていることを補い、文脈を知らない実装役が読んで書ける自己完結の文章にした物である。
補う物は、名前の挙がったファイル、決まっている方針、cycle か iterate の直後ならその終端報告で見たことである。
要求が曖昧なら、メインセッションとの 1〜2 回のやり取りで明確にしてから iterate へ渡す。

人が「さっきの、直しといて」とだけ言ったとき、iterate に渡る要求は対象のファイルと直す内容に展開された物である。
「さっきの」のまま渡したら反例である。
展開できないなら、要求は曖昧であり、iterate は動かない。

## 小さいタスクの判定

### 4 つの条件

**小さいタスク**は、次の 4 つを全部満たすタスクである。
ファイル数は問わない。

1. 要求が一通りにしか読めない。実装役が読み方を選ばずに差分を書ける
2. 仕様の判断が要らない。新しい入力の種類、受け入れの境界、エラーの扱いを、このタスクで初めて決めない
3. 仕様書があるなら、それと矛盾しない
4. 影響が読める

**影響が読める**とは、判定役が変更する場所を全部列挙でき、その列挙が閉じていて（「他にもありうる」が残らない）、各所で何を変えるかを判断なしに言える状態である。
場所の単位はファイルで、作る予定のファイルも列挙に含む。
1 つのファイルの中で何を変えるかは列挙に添えるが、閉じているかはファイルで見る。
数で切らない。
インターフェースの変更なら、呼び出し元が全部列挙でき、各呼び出し元で何が変わるかを判断なしに言えるとき、影響が読める。
大きいタスクとは、影響が読めないタスクである。
条件 1 と条件 4 は読み手の判断を含むので、どちらとも言えないときは小さいタスクではないと判定する。
迷った要求を小さいタスクとして通したら反例である。

境界のシナリオは次のとおりである。

- 表記揺れの統一で 30 ファイルに触る変更は、4 つとも満たすので小さいタスクである
- 他の module から呼ばれる関数の改名は、呼び出し元が全部列挙でき、各所で何が変わるかを判断なしに言えるなら小さいタスクである。多数から呼ばれて影響が読めないなら大きいタスクである
- 呼び出し元が 4 か所で全部列挙できたが、1 か所は戻り値の使い方が違って直し方を選ぶ必要がある。列挙は閉じているが「判断なしに言える」に外れるので、影響が読めない
- 「エラーメッセージを分かりやすくして」で対象が 1 ファイルでも、どう分かりやすくするかを実装役が選ぶなら条件 1 から外れる。文言まで人が指定していれば小さいタスクである

### 判定役

判定は、実装を委譲する前に、別文脈の agent（**判定役**）へ読むだけの判定を委譲して行う。
用語集の「調査」は人の症状や疑問から出発する investigate の仕事であり、要求から出発する判定役の仕事とは呼び分ける。
委譲先のプロンプトは自己完結にし、要求、worktree のパス、仕様書があればそのパス、4 つの条件の本文を渡す。

読むだけの縛りは、調査 skill 仕様（`docs/spec/investigate.md`）の「読むだけの保証」が委譲先に写すと定める 5 つと同じである。
編集、作成、上書き、削除、移動、改名の禁止。
許す操作（ファイルを読む / パスを列挙する / 検索する / 読むだけと分かっているコマンドを走らせる / 参照を辿る）。
読むだけと分かっているコマンドだけを走らせること。
禁じる操作の列挙と、それが例示であること。
秘密の扱い（存在だけを報告し、値を書かない）。
加えて、判定役はファイルを一切書かず、さらに委譲しない、と明記する。
iterate は判定の前後で `git status` を取って比べ、差が出ていたら理念の「続けると被害が広がる事故」として止まり、差を人に示して判断を仰ぐ。
自分では元に戻さない。
判定役の報告に秘密の値が 1 文字でも現れたら反例である。

返る物は、変更する場所の列挙（ファイルと、そこで何を変えるか）と、4 つの条件それぞれの判定と根拠である。
仕様書のパスが省略されていたときは、判定役がプロジェクトの指示が示す仕様書の置き場（このリポジトリでは `docs/spec/`）から、変更する場所を扱う仕様書を探し、見つけたら報告する。
iterate はそれを、指定された仕様書と同じに扱う。
条件 3 の突き合わせと review の突き合わせに使い、案内の「仕様書があれば」にも数える。
見つからなければ仕様書無しとして進む。
仕様書のパスが指定されず、判定役も探さずに条件 3 を見ないまま通したら反例である。

判定役の判定は提案であり、最終決定は iterate が持つ。
これは reviewer の提案を cycle が最終決定するのと同じ関係である。
判定役が判定を返せなかったときは 1 回だけ委譲し直し、それでも返らなければ、判定できなかったことを報告して止まる。
判定を飛ばしてループに入ったら反例である。

実装の途中で、列挙に無いファイルを直す（編集、作成、削除、改名のどれも）必要に気づいたら、影響が読めていなかったことになる。
実装役はそこで差し戻し、iterate は条件 4 が外れた案内で終わる。
列挙にあるファイルの中で要求に無い変更（import の整理、テストの追随など）が要ったときは、差し戻さず、予定外の変更として理由付きで報告して進む。
列挙の項目と実際の変更の中身がずれた物（別名の追随のはずが引数の解析まで書き換えた、など）は、実装役の差し戻しでは拾わず、review が拾う。
実装役の差し戻しの理由と外れた条件の対応は 4 つで、判定の 4 つの条件と 1 対 1 である。
列挙に無いファイルは条件 4、設計の判断が無いは条件 2、仕様書と矛盾するは条件 3、要求が二通りに読めるは条件 1 で、行き先は案内の表どおりである。
列挙の上限が効くのは実装役だけである。
修正役は review の指摘に従う立場で、指摘が列挙に無いファイルを指すこともあり、そこを直しても差し戻さず、予定外の変更として終端報告に載せる。
修正役の差し戻しの理由は cycle の契約どおり設計の判断が無い（条件 2）に、仕様書と矛盾する（条件 3）を足した 2 つである。
実装役が黙って列挙の外を直して進んだら反例である。
実装役が列挙に無いファイル（テストを含む）を直したり作ったりして予定外の変更として報告したら反例である。

## 収まらないときの案内

収まらないと判定したら、止まって案内を出して終わる。
iterate は brainstorm や plan を自分で起動しない。
案内は、外れた条件と根拠、行き先、そのまま使える呼び出しの 3 つからなる。

| 外れた条件 | 行き先 | すぐ使える形 |
|---|---|---|
| 1（曖昧） | メインセッションで人に聞き直す | どこが二通りに読めるかと、聞き直しの文 |
| 2（仕様の判断が要る）、3（仕様書と矛盾する） | brainstorm | `/ba0918-brainstorm <題材>`。既存の仕様書があればそのパスを添える |
| 4（影響が読めない） | 仕様書があれば plan、無ければ brainstorm | `/ba0918-plan <仕様書のパス>` または `/ba0918-brainstorm <題材>` |

複数の条件が同時に外れたときは、外れた条件を全部並べ、行き先は表の上の行を優先する。
曖昧な要求は明確にしてから判定し直す物であり、明確にすれば条件 2 から 4 の判定が変わりうるからである。

案内で skill 名を名指しするのは、iterate が開発ワークフローとセットで使う前提だからである。
iterate 単体を独立させても恩恵がほぼ無い。
案内を出して止まるのは、工程を終えて結果を渡す動作であり、人を止める 4 つの場面に 5 つ目を足すものではない。

仕様書が無いのに plan を案内したら反例である。
plan は仕様書のパスが要るので動けない。
大きいと判定したのに「それでも iterate で続ける」の選択肢を出したら反例である。

## ループ

ループの形、往復の数え方、見えている指摘の扱い、`security` の指摘での中断は cycle と同じである。
判断の所有、指摘 JSON の所有と置き場、終わり方も cycle と同じである。
例外は終わり方 4 の判断点（下の「読み替える点」）だけである。
参照する節は、開発ワークフロー仕様の cycle の節のうち「往復とレビューの 2 種類」「ループの形」「終わり方」「判断は cycle が持つ」である。
skill 本文はこれらを写さず、実行時に cycle の skill（`ba0918-cycle`）を名前で呼び出して本文を読み込み、読み替える点だけを持つ。
呼び出しは名前で行い、パスでは参照しない。
cycle が review の skill を名前で読み込むのと同じ形で、同梱の skill 同士の依存として認める。

### 読み替える点

cycle の本文は手順書を前提に書かれている。
手順書に触れる記述は次のとおり読み替え、これ以外は読み替えない。

| cycle の本文 | iterate での読み |
|---|---|
| 必須の入力の手順書のパス | 要求 |
| ブランチ名に手順書の名前を含める | 要求を表す短い名前 |
| 手順書から仕様書のパスを読む | 入力の仕様書のパスか、判定役が見つけた仕様書 |
| 手順書と git log から済んだ手順を推論し、残りを implement に委譲する | 推論せず、要求を実装役に 1 回で委譲する。判定がループの前に付く |
| implement への委譲（手順書のパス、ブランチ、worktree のパス） | 実装役への委譲（要求、判定役の列挙、仕様書のパスがあればそれ、ブランチ、worktree のパス） |
| 修正役への委譲に含む手順書のパス | 要求と、仕様書のパスがあればそれ |
| 修正役の契約の「検査の確かめ方は手順書のコマンドを順に、書き換えずに」 | 検査のコマンドは、プロジェクトの指示、標準の道具の順で決める |
| 上限到達後の「さらに回す」の再入口（手順が残っていれば implement から） | 常に差分ループから |
| review への委譲に含む突き合わせる仕様書のパス | 仕様書のパスと要求の両方 |
| 終わり方 4（brainstorm または plan への差し戻し）と、そこで終端報告に足す「さらに回すか、残りを受け入れて終えるか」の判断点 | 差し戻し先は案内の表の 3 つの行き先。判断点は出さず、差し戻しの理由と案内を載せて終える。人が答えを得たら、それを込めた新しい要求で起動し直す |
| 上の行に当たらない、手順書を指す plan の語（1 つの手順書で回す、手順書に無い予定外の変更、など） | 「要求」。skill 名としての plan（差し戻し先）は当たらない。手順の中身に触れる文（手順を解釈しない、手順が残っていれば）は、手順書が無いので当たらない |

実装役は、cycle が修正役に渡す契約（implement と同じ約束を委譲プロンプトに全文貼る形）に、見えている指摘の代わりに要求を渡した物である。
implement skill は手順書のパスを受け取って手順を順に実行する前提なので使わない。
実装役が返す物は、commit と、完了の示し方ごとの証拠（テスト / 検査 / 作った物 / 外で確かめる）と、要求に無い予定外の変更とその理由である。
差し戻すときはその理由を返す。
判定役の列挙は、要求と一緒に読み物として実装役に渡し、命令ではないと明記する。
列挙は実行する手順ではないが、触ってよいファイルの上限としては効く。
明記を怠って列挙を手順として渡したら反例である。
仕様書のパス（指定された物か、判定役が見つけた物）は、実装役と修正役にも読み物として渡す。
cycle では手順書経由で届く物で、手順書を要求に読み替えると落ちるからである。
仕様書があるのに実装役か修正役に渡さなかったら反例である。

review には、突き合わせる仕様書のパスがあればそれと、要求の両方を渡す。
仕様書が無いときは、要求が突き合わせる相手であり、reviewer は品質と突き合わせの 2 体で行う。
要求どおりの物が作られたかを誰も確かめないまま終端報告に至ったら反例である。

### 再開

cycle または iterate の直後に同じブランチで起動し、そのブランチに指摘 JSON が残っているときは、cycle の再開と同じ扱いにする。
指摘を引き継ぎ、見えている指摘があればループが拾って直し、`human_judgment` と `record_only` の指摘は open のまま終端報告に載る。
残っている指摘 JSON を消したり無視したりしたら反例である。
往復の番号は、引き継いだ評価の最大の番号の次から続ける。
番号を 1 から振り直し、引き継いだ評価と今回の評価が同じ番号を持ったら反例である。
このとき比較の基点は、人が入力で渡さない限り、iterate を起動した時点のブランチの先端に置き換える。
前の実行が見せた差分は人が終端報告で確認済みであり、iterate のフルレビューが見るのは要求による差分だけでよいからである。
引き継いだ open の指摘は、基点の外にあっても差分レビューで評価する。
cycle が閉じた指摘を再び開くかは cycle と同じ規則に従う。
終わり方 3 の連続の数え方（同じ指摘が「まだある」のまま 2 往復）は、起動の境界でリセットし、引き継いだ評価を数えない。
起動の境界は iterate の新しい起動だけで、終わり方 2 や 3 の後の「さらに回す」は同じ実行の続きであり、連続を継ぐ（リセットしない）。
これは cycle の再開の規則と同じである。
「閉じた指摘と同じ原因が再び出る」は境界をまたいでも効く。
引き継いだ「まだある」を 1 回に数え、今回 1 回のレビューで進捗が無いとしたら反例である。

往復の上限は既定で持たない。
上限に達したときの「さらに回すか、残りを受け入れて終えるか」は cycle の終わり方 2 と同じで、数は起動時の入力で人が決める。
連続して iterate を起動した回数を数える仕組みは持たない。
毎回の終端報告と条件 4 の判定で足りる。
1 回ずつは影響が読めても積み重ねで設計が崩れるケースは、仕様書があれば review の突き合わせが拾う。
仕様書が無ければ拾えず、その線は受け入れる。

## 終端報告とやらないこと

終端報告とやらないことは、開発ワークフロー仕様の cycle の節（「終端報告」「やらないこと」）と同じである。
検証結果は実装役の報告にある完了の示し方ごとの証拠から取る。
「複数の手順書の同時実行」は「複数の要求の同時実行」と読み替える。
iterate だけに加わるのは、収まらないと判定して止まったときと、差し戻しで終わったときの案内である。

## 起動する言葉と境界

起動する言葉は「iterate」「ちょっと直して」「これも足して」「もう少し磨いて」「小さいタスク」である。
英語では "iterate" "one more fix" "fix this bit" "add this too" "polish it a little more" である。
「直して」「足して」だけでは起動しない。
人がメインセッションに直接直させる道は残り、iterate の値打ちは review が付くことなので、review 付きで回したい意思が読める言葉に限る。
起動する言葉は skill の description に置き、本文には書かない。

「調べて」は investigate、「動作確認して」「検証して」は review の診断が受け持つ。
iterate が「調べて」で動いて実装まで始めたら、境界の破れである。

## 作る物

1 つのブランチで作る物は次のとおりで、ブランチと worktree はこのリポジトリに立てる。

- `skills/ba0918-iterate/`（`SKILL.md` と、要るなら `references/`）
- `skills/ba0918-investigate/SKILL.md` の推奨表の行と小さい修正の定義文を、改訂した調査 skill 仕様に合わせる
- `PROJECT.md` の正本の表に `docs/spec/iterate.md` の行
- `evals/cases/ba0918-iterate/` に scenario 2 本と、`evals/inputs/ba0918-iterate/` にその入力
  - 仕様書の無い小さいタスクが実装、review、終端報告まで完走する
  - 影響が読めない要求で、commit を作らずに止まって案内を出す
  - scenario の `exercises` は自分の skill の本文だけを宣言する
- cycle の `SKILL.md`。呼び出して読んだとき読み替えを読み違えさせる文があれば、cycle の約束を変えない言い回しの直しに限って触ってよい。触ったときは `regression-lock.json` の cycle のエントリのハッシュを `accepted-without-run` で取り直す

この仕様書と一緒に承認する物は 2 つある。
用語集の「小さいタスク」「要求」「影響が読める」「判定役」「実装役」の 5 語と iterate の節、そして調査 skill 仕様の改訂である。
改訂は、推奨表の「小さい修正」の行を「小さいタスク → iterate」に書き換え、定義を用語集の参照に置き換え、iterate を待つ記述を消すものである。

scenario を走らせるかどうかは人が頼んだときだけ決める。

## 却下した案

- 「小さい」をファイル数で切ること。表記揺れの統一のように replace 一発で終わる変更は、ファイル数が多くても小さい
- 「1 commit で言い切れる」を小さいタスクの条件にすること。かなり限定されてしまう。commit は implement の契約どおり関心事ごとに複数でよい
- 外から見えるインターフェースの変更を一律に小さくないとすること。呼び出し元が少なくて影響を読めるなら小さい
- investigate skill の契約を判定に流用すること。出力が人向けの 6 節の報告で、iterate が読む形に合わない。読むだけの縛りの文言を写す方が小さい
- cycle のループの文章を iterate の本文に写すこと。cycle の約束が変わるたび、2 か所を直す手間が出る
- implement skill を要求の実装に使うこと。手順書のパスを受け取り進捗を推論する前提が空回りする
- 突き合わせる仕様書が指定されなければ黙って無しにすること。仕様書があっても突き合わせないまま通る穴が開く
- 旧 iterate の BLOCK / WARN / PASS と軽いレビュー。review の重さ、対応、強さに置き換わった
- Codex の second opinion。モデルの配線はユーザースコープの規則で持ち、配る skill 本体に書かない
- status.md へのフォールバック、workspace lock、artifact store、satellite の一式。捨てた実行環境の部品
- 大きいと判定したときの「それでも iterate で続行」の選択肢。影響が読めない物を review だけで通す道になる
- 往復の上限を iterate だけ既定で持つこと。cycle の仕様書が既定の上限を却下しており、約束が割れる。実測してから決める
- cycle の終端報告や指摘 JSON を iterate の入力にすること。cycle と iterate の間に受け渡しは無く、どちらも人が対話から起動する
- 迷ったときに小さいタスクへ倒すこと。影響が読めない物を review だけで通す道になる
- 同じブランチで再開したとき cycle の比較の基点を使い続けること。人が確認済みの差分を全部レビューし直し、閉じた指摘が「同じ原因が再び出た」として終わり方 3 を誘発する
- `PROJECT.md` の縛りの例外に「同梱の skill の本文を実行時に読む」を足すこと。縛りはパスでの参照を禁じる物で、skill を名前で呼び出す依存は既に cycle と review の間で認めている
- 仕様書が無いとき review を品質の reviewer 1 体にすること。要求どおりの物が作られたかを誰も確かめない
- 終わり方 4 でも cycle どおり「さらに回すか」の判断点を出すこと。open の指摘を差分ループから回す動作なので、影響が読めない物を review だけで通す道になる
- 「列挙の外」の単位を列挙の項目（ファイルと変える内容）にすること。差し戻しが増える。中身のずれは review が拾う
- 終わり方 3 の連続を起動をまたいで数えること。今回 1 回のレビューで「進捗が無い」が成立しうる
- 「さらに回す」を起動の境界に数えること。同じ実行の続きであり、新しい起動と同じに扱う根拠が無い
- 読み替え表の外に残る手順書の語を、cycle の本文の言い回しの直しで消すこと。lock の取り直しがセットで付き、総則の行で足りる
- scenario の `exercises` に cycle と review の本文を宣言すること。lock は名前で呼ぶ依存を辿らず（実測: cycle の本文の変更で挙がるのは cycle の scenario だけ）、効かない宣言は誤解を招く
- 行数の上限 113 を改訂で広げること。足す文は既存の重複を詰めて吸収する
- 修正役にも列挙を渡し、列挙の外は差し戻すこと。指摘 1 件で実行が終わり、改善ループが自律で回らない
- 「さらに回す」の後で終わり方 3 の連続をリセットすること。cycle の本文に途切れる根拠が無い
- 列挙に無いテストの新規作成を予定外の変更として通すこと。影響が読めているならテストを足す場所も読めている
- scenario の期待の緩め方を仕様書に書くこと。scenario ファイル自体が残る成果物で、理由は指摘の記録とコミットが持つ
