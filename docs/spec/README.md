# agentic-workflow の仕様書

## これは何か

agentic-workflow は、AI エージェント（Claude Code や Codex のようなコーディング支援 AI）に
ソフトウェアの変更を任せるときの、作業の進め方を決めた仕組みです。
「思いつき」から「レビュー済みの変更」までを、次のステップに分けて進めます。

1. **brainstorm** — 人と AI が対話して、何を作るかを決める
2. **plan** — 決めた内容を、実装の手順書に落とす
3. **cycle** — 実装からレビューの収束までを、人を止めずに回す
   - **implement** — 手順書どおりに実装し、証拠を残す
   - **review** — 実装を独立した目で確かめる

通常の人の確認は、仕様を決めたとき、手順書ができたとき、最終成果物を受け入れるときの
3 つの境界へ集約します。その間は実装とレビューと修正の往復が自走します。重要な設計判断が
未決定、不可逆な操作、人の権限、または被害が広がる事故の場合だけ途中で人へ返します。

各ステップは、エージェントが読む「skill」（手順を書いた文書と補助スクリプトの組）として
配布されます。この仕様書は、それぞれの skill が何をして何をしないか、ステップの間で何を
受け渡すかを、人が読んで判断できる形で説明します。

## なぜこの仕組みが要るか

AI に作業を任せると、次のことが起きがちです。

- 仕様に書いていないことを、AI が勝手に決めて実装してしまう
- 人が中身を理解しないまま「承認」のボタンを押す形になり、承認が儀式になる
- 途中で止まったとき、どこまで終わっていて何が残っているか分からなくなる
- テストを後回しにして「できました」と言われる
- 仕様書に要求があっても、それを確かめるtestや検査が実装から抜け落ちる

この仕組みは、これらを構造で防ぎます。仕様に無い重要な設計判断は brainstorm に戻して人と決める。
承認は人が読んで理解した文書に対して行う。作業の証拠はファイルとして残し、会話の記憶に
頼らない。実装は「先に失敗するテストを書く」ことを求めます。さらに、仕様書の要求をplanの手順と検証へ
結び、宣言した検証のevidenceが無いまま完了できないようにします。要求や検証の意味は独立reviewが
確認し、自然言語の要求を独自schemaや形式手法へ置き換えません。

同時に、**人を呼ぶ回数を増やすことを安全と混同しません。**機械が判定できることについて
承認を求めず、AI が自分の道具に躓いたときは人を呼ばずに立て直します。人を止めるのは、
重要な設計判断や不可逆な操作など、放置すると大きな問題になる場合だけです
（[workflow.md](workflow.md) の
「承認を儀式にしない」）。

## 文書の構成

| 文書 | 何が書いてあるか | こんなときに読む |
|---|---|---|
| [workflow.md](workflow.md) | 全体の流れ、想定する使い方、ステップ間で受け渡すもの | まず全体を知りたい。ステップの継ぎ目で何が起きるか知りたい |
| [brainstorm.md](brainstorm.md) | 対話で何を決め、どう記録し、どう承認を取るか | 新しい機能や変更を相談したい |
| [plan.md](plan.md) | 手順書に何を書くか、どう承認を取るか | 合意した内容を実装に渡したい |
| [cycle.md](cycle.md) | 実装からレビューの収束までをどう回し、どこで人に返すか | 実装からレビューまでを任せたい |
| [implement.md](implement.md) | 手順書をどう実行し、どんな証拠を残すか | 実装の中身を知りたい。止まった実装を再開したい |
| [review.md](review.md) | 何をどう確かめ、指摘をどう収束させるか | 実装や任意の差分をレビューしたい |

仕様書は「いまの仕組みがどう動くか」だけを書きます。どの順番で作ってきたか、
以前の仕組み（claude-skills）と何が違うかは、[ROADMAP.md](../../ROADMAP.md) にあります。

## この仕様書の読み方

- 読者として、この仕組みを初めて見る人を想定しています。仕組みの中でしか通じない言葉は、
  最初に出てくる場所で意味を説明します。
- 流れや関係は図で示します。図は Mermaid という記法で書いてあり、GitHub などの
  Markdown 表示でそのまま絵になります。
- 各文書には「人が判断する場面」の節があります。AI が勝手に決めてはいけないことが
  そこに書いてあります。

## 配布と動かし方

各 skill の実装先は、このリポジトリの `skills/ba0918-<名前>/` です。中身は次のとおりです。

```text
skills/ba0918-brainstorm/
├── SKILL.md        エージェントが最初に読む、短い手順書
├── references/     場面ごとに読む補足
└── scripts/        決まった処理をする補助スクリプト（Python）
```

補助スクリプトを持たない設計の skill もあります（`ba0918-cycle`）。補助スクリプトは、Git や
ファイルなど外の現実との照合に加え、壊れた入力や不正な状態遷移を読み込み境界で拒否します。
記録そのものを信用するためだけの独自の指紋や、書いた直後に自分の出力を読み直す検査は作りません
（[workflow.md](workflow.md) の「機械の検査は、現実との境界と壊れた入力を見る」）。

実装済みの skill は、エージェントがこのディレクトリを読める場所に置けば動きます。共有の
ランタイムやプラグイン全体を前提にしません。人が承認した文書は対象リポジトリの `docs/`
以下、AI が
書いた記録は `.agents/` 以下に置きます（詳しくは [workflow.md](workflow.md) の
「記録の置き場所」）。
