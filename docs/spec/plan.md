# plan の仕様

plan は、brainstorm で承認された仕様書を、実装の手順書に変えるステップです。
手順書は、人が読んで「何がどう変わるか」を判断できる文書であると同時に、次のステップ
（cycle と、その中の implement）がそのまま実行できる文書です。

全体の中での位置と、brainstorm から何を受け取り cycle へ何を渡すかは
[workflow.md](workflow.md) にあります。ここでは plan の中で何が起きるかを説明します。

## 何をするステップか

plan は「決まったことを、順番に並べる」だけのステップです。新しいことは決めません。
仕様書に書いていないことが手順を書く途中で必要になったら、自分で埋めずに brainstorm へ
戻します。これは、手順書が「2 回目の設計」になって、人が承認していない設計が実装に
流れ込むのを防ぐためです。

plan が終わったとき、次のものができています。

- 人が読んで承認した手順書（`docs/plans/` に置かれ、git で管理される）

未完了の手順書の一覧は、どこにも書きません。**作業ツリーにある手順書が、そのまま未完了の
一覧です。**手順書は git で管理し、完了して取り込まれたら作業ツリーから削除します。過去の
手順書は git の履歴から読めます。一覧を別に持つと、それと現実がずれるからです。

手順書ができても、cycle は自動では始まりません。人が「実装して」と言って初めて動きます。

## 受け取るもの

plan は、brainstorm または人が名前を挙げた仕様書だけを入力にします。リポジトリの中を
探して「これが関係ありそう」と仕様書を自分で選ぶことはしません。

手順書を書き始める前に、次がそろっているかを確かめます。

- 作る物が、1 回の実装と検証で終わる 1 つの単位になっている
- 参照する仕様書のパスと節が分かり、その内容がコミット済みである
- 仕様書に、完了を確かめる方法と、人が判断する場面が書いてある
- 配布の仕方、動かし方、保存する状態、外部サービスとの入出力が決まっているか、
  無いと確認されている
- 新しい外部依存を採用するかが決まっている。plan は未選定の外部依存を新しく決めない
- 決まっていないこと（未決定）が残っていない

1 つでも欠けていたら、手順書を書かずに、何が足りなくてどう困るかを人の言葉で説明し、
brainstorm へ戻します。

## 手順書に書くこと

手順書は 1 つの Markdown ファイルです。人が読む部分と AI が読む部分を分けません。
全体を人の言葉で書いたうえで、implement が機械的に読む箇所だけ、決まった書き方をします。

### 仕様書を書き写さない

**手順書は仕様の内容を書き写しません。**仕様書へ参照を張り、その計画で何をどう作るかだけを
書きます。

写しを持つと二重管理になります。仕様書が改訂されるたびに写しが古くなり、手順書ごと
作り直しになります。実際に、写しを求めていた時期の手順書は 788 行あり、そのうち大半が
仕様の写しでした。そして 1 つの実装で 3 回の改訂が起き、3 回とも引き金は仕様の改訂でした。

手順書に書くのは次です。

- **検証の対応**: どの仕様書のどの節を、どの手順と完了種別で確かめるか。版は手順書を承認した
  Git コミットのツリーから分かるので、独自の指紋は書かない
- **この計画で採る実装方針と、その根拠**: 仕様が許す範囲の中で、なぜこの作り方を選んだか
- **変更するファイル**: 手順書全体で予定する範囲と、各手順で触る予定の範囲
- **順序**: 手順の並びと、手順どうしの前提
- **各手順の検証 portfolio**: 要求を直接示す検証と、必要な補助検証
- **実装側に任せてよい選択**（あれば）
- **止まる条件**

仕様の詳細を知りたい読者は、参照から仕様書を読みます。承認する人は、その仕様書を既に
承認しているので、写しを読み直す必要はありません。

読んで分からないのは、**この計画に固有の判断**だけであってはいけません。「なぜこの順序か」
「なぜこのファイルを触るのか」「どこで止まるのか」は手順書だけで分かるように書きます。
それらは仕様書に書いていない、この計画の判断だからです。

### 機械が読む構造

機械が読む入口となる top-level block は次の 2 つです。手順内では、`Step N` 見出しと、完了種別に応じた `Checks` や `Human gates` も既存の構造として読みます。

| 箇所 | 書き方 | 何に使うか |
|---|---|---|
| 検証の対応 | `**Verification coverage:**` の下に、仕様パス、節、手順番号、完了種別を 1 行ずつ書く | 承認済み要求を手順と evidence へ結び、runtime が手順 contract を導く |
| 予定する変更範囲 | `## Scope` の下の、ファイルの木（`text` のコードブロック） | 予定外の変更が必要になったとき、その理由と影響を判断する起点にする |

検証の対応は要求本文を写しません。仕様パスと見出しを要求の住所として使います。

```markdown
**Verification coverage:**

- `docs/spec/account.md` / `再起動後の保持` -> `1:test`
- `docs/spec/account.md` / `重複登録` -> `1:test`
- `docs/spec/account.md` / `認証情報` -> `2:test`
- `docs/spec/skill.md` / `停止条件` -> `3:artifact`
```

手順本文の見出しは `## Step 1: ...`、`## Step 2: ...` のように、1 から始まる連続した番号を
使います。検証の対応に載せた全仕様節は 1 つ以上の手順へ結び、全手順は 1 つ以上の仕様節から
参照されなければなりません。同じ手順を複数行から参照でき、1 つの仕様節を複数手順へ結びつける
こともできます。同じ手順の完了種別は常に一致させます。

背景として読むだけで、その実装が満たす要求を持たない節は本文から普通に参照できます。検証の
対応へ載せるのは、実装が満たすべき要求を持つ節だけです。

plan は人へ見せる前に、書式、仕様パスと見出し、連続する Step 見出し、全仕様節と全手順の対応、
完了種別の一致を検査します。検証の対応に使う見出しは、同じ仕様ファイル内にちょうど 1 つだけ
存在しなければなりません。仕様書はコミット済みで、作業ツリーと同じでなければなりません。
旧 `**Target specifications:**` 形式は受け付けません。この workflow は未配布で未完了の旧 plan も
無いため、互換経路と移行処理は作りません。

予定する変更範囲は従来どおり `## Scope` の text code blockへ書きます。要求本文や検証 portfolio の
意味を独自の機械可読 metadata にしません。

### 完了の示し方

各手順は、完了をどう示すかを次の 4 種類から 1 つ選び、検証の対応へ書きます。

| 書き方 | 意味 | 何に使うか | implement が要求する証拠 |
|---|---|---|---|
| `test` | テストで示す | 決まった入力に決まった出力を返すコード | 先に失敗するテストを書き、通ったこと |
| `check` | 検査で示す | 生成した物、道具が判定できる成果物 | 手順に書いた検査コマンドがすべて成功で終わったこと |
| `artifact` | 作った物で示す | 人や AI が読んで意味を判断する文章 | ファイルと形式検査を記録し、cycle の完了までに独立レビューを通ったこと |
| `external` | 外で確かめる | 実機での動作確認、人が頼んだ実測 | 実行結果が記録され、手順書の条件を満たしたこと。不可逆または人の権限が要る操作は実行前に人へ返す |

この仕様書では、4 種類を「テストで示す」「検査で示す」「作った物で示す」「外で確かめる」と
呼びます。手順書に書く値は `test`、`check`、`artifact`、`external` です。

選ぶ基準は「何を作るか」ではなく、**誰が完了を判定できるか**です
（[workflow.md](workflow.md) の「plan → cycle」と「承認を儀式にしない」）。

- 決まったコマンドが判定できる → `test`（先に失敗するテストが書けるとき）か `check`
- 文章の意味を独立した目で判断する → `artifact`。作業場所の外で結果を確かめる → `external`

「検査で示す」を選んだ手順には、**成功を判定する検査コマンドを 1 つ以上、手順に書きます**。
検査を書かずにこの種類は選べません。生成した複製の同期（`gen` と `verify`）、リポジトリ
全体の検査の通過、書式の検査だけで完了が決まる手順がこれにあたります。人の承認は求めません。

検査コマンドは、その手順の中に `**Checks:**` の宣言として書きます。1 行に 1 つ、コマンド
全体を逆引用符で囲んだ箇条書きです。

````markdown
**Checks:**

- `bunx agentic-skill-vendor gen`
- `bunx agentic-skill-vendor verify`
````

implement は、ここに挙げたコマンドだけを、書かれた順に走らせます（[implement.md](implement.md)
の「検査で示す」）。手順の本文に文章としてコマンドが出てきても、それは走りません。走らせる物を
一箇所に集めるのは、手順書が名前を挙げた検査と、実際に走った検査を同じにするためです。

`**Checks:**` が無い、または 1 つもコマンドを挙げていない `check` の手順は、手順書として
受け付けません。`check` 以外の種類の手順に `**Checks:**` は置きません。

**人や AI が読んで意味を判断する文章を `check` にしてはいけません。** 検査コマンドが通った
ことと、文章の意味が正しいことは別だからです。仕様書、skill の本文、手順書、利用者向けの
文書は `artifact` です。この線引きは機械では判定できないので、plan が書くときに守ります。

文章に対して LLM を実際に走らせる確認（実測）は、人が scenario、model、token 予算の 3 つを
明示した場合だけ「外で確かめる」として手順に入れます。LLM 以外の外部実測は、承認済み仕様の
条件に従います。条件が無い実測を AI が手順へ足すことはしません。

### 各手順に書くこと

手順ごとに次を書きます。

- 目的と、仕様書のどの節に基づくか（節の名前を挙げる。節の内容は写さない）
- 前提（先に終わっているべき手順、先に決まっているべきこと）
- 変更してよいファイルの範囲（手順書全体の範囲の中で、さらに絞る場合）
- 検証の対応で割り当てた完了種別に対し、具体的に何を確かめるか。`check` なら検査コマンドも
- 実装側に任せてよい選択（あれば）
- 止まる条件

「具体的に何を確かめるか」は、仕様の再記述にならない範囲で書きます。仕様に書いてある
振る舞いをもう一度書くのではなく、**この手順が終わったと言える条件**を書きます。

実装側に任せてよい選択は、どれを選んでも承認された振る舞いが変わらない範囲に限ります。
新しい入力の種類、受け入れの境界、エラーの扱い、許容する誤差、検証の例を手順書で
初めて決めることはしません。それらは brainstorm に戻します。

### 実装途中で人へ返す場面の宣言

仕様書で「ここは実装途中に人へ返す」と決まっている手順には、人向けの説明に加えて、
implement が読む宣言を同じ手順の中に置きます。

````markdown
**Human gates:**

```json
{
  "version": 1,
  "gates": [
    {
      "gate_id": "profile-wording",
      "sections": ["Review profile"],
      "criterion": "観点の文言が承認した仕様の意味と一致しているか",
      "target": { "kind": "files", "paths": ["skills/ba0918-review/references/profile/default.md"] },
      "timing": "before_commit",
      "allowed_results": ["approved", "rejected"]
    }
  ]
}
```
````

- `gate_id` は手順書の中で一意
- `sections` は、この手順が基づく仕様書の節の名前。手順書冒頭の `**Verification coverage:**`
  に列挙した名前のどれかと一致させます。比べるのは節の名前そのもので、
  backquote は含めません（上の例なら `"残っている作業があるとき"` と書きます）。機械は
  この対応を検査しません。読み手が「この判断が仕様書のどこに基づくか」を辿れるように
  するためのものなので、書く側が確かめます
- `criterion` は、人が「はい / いいえ」で答えられる 1 つの問い
- `target` は、判断の対象。リポジトリ内の相対パスの集合（`files`）か、実行記録の番号
  （`event`）のどちらか
- `timing` は `before_edit`（編集の前）、`before_commit`（コミットの前）、
  `before_implementation_green`（全手順完了の前）のどれか
- `allowed_results` は `approved` と `rejected` だけ

この宣言に置けるのは、不可逆な操作、人の権限が必要な操作、または本番データなど危険な対象へ
触れる前の確認だけです。答えによって作る物の意味が変わる判断や、既に分かっている設計判断は
ここへ残さず brainstorm で決めます。成果物を読んで受け入れる判断は cycle の終端へ集約します。

## 独立したレビュー

人へ承認を求める前に、手順書を書いた文脈とは別のレビュアーが、承認済み仕様書と関連する
コード、テスト、プロジェクトの規則に照らして、手順書全体を 1 回レビューします。新しい設計を
決めることはせず、次を確かめます。

- 仕様書の要求を実現する手順が漏れなくあり、仕様に無い判断を足していない
- 検証の対応に、実装が満たす全仕様節と全手順が漏れなく結ばれている
- 各要求に、その反例を検出できる直接検証が少なくとも 1 つある
- unit、integration、E2E、PBT、静的検査、artifact、external の選択と組み合わせが対象に合う
- 全体test、型検査、lintなどの補助検証だけを、仕様適合の直接証拠としていない
- 変更する場所、順序、依存関係、完了の示し方が実際のリポジトリで実行できる
- 新しい外部依存、保存形式、権限、外部との入出力を plan が初めて決めていない
- 実装途中の人への確認が、上の例外だけに限られている

最初のレビュー後は、未解決の指摘、修正差分、その修正が影響する後続手順だけを見直します。
手順の追加・削除・並べ替え、予定範囲の大幅な拡張、依存関係、完了条件、参照仕様が動いた場合は、
一部だけでなく全体レビューへ戻ります。仕様不足を見つけたら、plan の中で補わず brainstorm へ
戻します。レビューの問題が無くなってから承認へ進みます。

## 承認

手順書は、brainstorm の仕様書と同じ手順で承認されます。

1. AI が `docs/plans/` に手順書のファイルを直接書く。補助スクリプト
   （`scripts/plan_artifact.py`）が、機械が決まった書き方で読む 2 箇所と、参照する仕様書が
   コミット済みであることを検査する。検査に通らなければ、どこが読めないかを返す。AI は
   それを直す
2. 独立したレビューを収束させたあと、AI は承認対象の手順書だけを Git のステージ領域へ置く
3. AI はチャットに、手順書のパス、ステージ済みの差分を見るコマンド、人が判断すべき点だけを
   出す。手順書の全文をチャットに貼らない。要約を承認の対象にしない
4. 人が自分の道具でステージ済みの内容を読み、「この内容を承認する」と明示する
5. AI が、承認されたステージ済みの内容をそのままコミットする

**承認とコミットは同じ操作です。**コミットが承認の記録になるので、承認を別のファイルに
書き留めることはしません。逆に、コミットされていない手順書は、まだ承認されていない
手順書です。

承認前の内容を別の場所に置くことはしません。置き場が 2 つあると、どちらが本物かを
名指しする必要が出て、2 つがずれる余地が生まれます。作業ツリーにあってコミットされて
いない、という状態が「承認待ち」を表します。

黙っていること、「もう少し話そう」と言うことは承認ではありません。直したいところがあれば
対話で受けて書き直し、レビューとステージ済みの差分を必要な範囲で出し直します。

承認の前に、状態ファイルを作ったり書き換えたりしません。

## 手順書の改訂

**改訂は、同じパスのファイルを書き換えて、新しい Git コミットとして承認します。**新しい
パスに作り直しては
いけません。2 つのファイルができると、どちらが本物かを名指しする必要が出るからです。

改訂の内容によって、扱いが 2 つに分かれます。

- **作る物の意味、禁止、許容する差異、人が判断する場面を変える必要が出たとき**は、手順書を
  直さずに brainstorm へ戻します。仕様書が改訂されたら、それに基づく手順書もそれに合わせて
  改訂します
- **意味を変えずに手順だけを直すとき**（たとえば、検査コマンドの対象範囲の書き損じ、
  変更してよいファイルの取りこぼし）は、本文を書き換え、**変更前と比べた差分**を人に見せて
  承認を取ります。全文を読み直させません。直したのがどこかを示すには、差分のほうが短くて
  正確です

改訂の理由はコミットメッセージに書きます。手順書自体に残す場合は、末尾に「版 / 一行の
要約 / コミット」の表を置き、そこに追記します。本文の先頭に改訂の説明を積み上げると、
版が上がるほど読み手が本文にたどり着けなくなります。

進捗の記録のために手順書を書き換えることは、改訂ではありません。しません。

改訂すると、以前の承認コミットに結び付いた実装の証拠は古い内容に基づくものになります。
古い証拠は捨てず、implement が内容の意味を比較し、重要な設計判断が動いていなければ自動で
新しい版へ追従します。動いていれば、人が新しい内容を確認して束ね直すか、新しく始めます
（[implement.md](implement.md) の「残っている作業があるとき」）。

## 未完了の手順書をどう知るか

一覧をどこかに書き出すことはしません。**作業ツリーの `docs/plans/` にある手順書が、
未完了の一覧です。**

- 手順書は git で管理します。承認するとき、同じ操作でコミットします
- 完了して取り込まれたら、作業ツリーから削除します（`git rm`）。過去は git の履歴で読めます
- 「いま対象」「保留」の印は持ちません。作業ツリーにあるかどうかだけです

一覧を別に持たないのは、それが現実とずれるからです。一覧は、手順書を承認する操作で
書かれ、実行が完了する操作では触られません。書く手順を飛ばしても作業は進むので、
飛ばされます（[workflow.md](workflow.md) の「記録は、現実を変える操作と同じ操作の中で
書く」）。

同じ理由で、`status.md` や `session-history.md` のような状態ファイルも作りません。
進み具合は implement が残した証拠と状態の写しから導きます。

生きている実行（実装が動いているブランチと作業ディレクトリ）は、`git worktree list` が
答えます。plan はそれを読むだけで、書きません。

## 複数の手順書があるとき

作業ツリーに未完了の手順書が複数あってもかまいません。plan はどれかを「いま対象」に
選びません。どれを実装するかは、cycle か implement を起動するときに決まります。

同じ範囲を扱う手順書が二重にできそうなときは、AI が既にある手順書を見せて、新しく作るか
既存の手順書を改訂するかを人に聞きます。黙って似た手順書を並べません。

## やらないこと

- 仕様書に無いことを決めない。設計しない
- 実装しない。テストを書かない。製品変更をコミットしない。承認された手順書のコミットだけは
  plan 自身の終端操作として行う
- ブランチや作業ディレクトリ（git worktree）を作らない、切り替えない
- 進捗を手順書や状態ファイルに書かない
- 未完了の手順書の一覧や、状態ファイルを作らない
- 止まった実装の再開を行わない（それは implement が受け持つ）
- cycle や implement を自動で始めない
- 仕様の内容を手順書に書き写さない
- 新しい外部依存を選ばない。必要なのに仕様で決まっていなければ brainstorm へ戻す

## 人が判断する場面

| 場面 | 人が決めること |
|---|---|
| 入力が足りない | brainstorm に戻って決める |
| 手順書の承認 | ステージ済みの差分を、その内容のままコミットしてよいか |
| 同じ範囲の手順書が既にある | 新しく作るか、既存の手順書を改訂するか |

## 失敗したときの動き

- ステージまたはコミットで失敗したら、どの段階で失敗したかを報告し、「承認された」とは
  言いません。書いたファイルはそのまま残します
- 書き方の検査や Git にある承認済み仕様との照合に通らなければ、どの箇所がどう読めないかを示します。
  人に見せる前に AI が直します

## skill の構成

```text
skills/ba0918-plan/
├── SKILL.md                 入口。責任の範囲と、どの補足をいつ読むか
├── references/
│   ├── creation.md          入力の確認、手順書の書き方、承認
│   ├── readability.md       手順書を人が読める形にするための確認項目
│   └── lifecycle.md         改訂、未完了の手順書の扱い
└── scripts/
    └── plan_artifact.py     参照する仕様書と予定する変更範囲の読み取り
```

機械が読む入口となる 2 つの top-level block（検証の対応、予定する変更範囲）は、この
`plan_artifact.py` が 1 か所で持ちます。implement はこの読み取りを使い、自分で別の解釈を
持ちません。検証 portfolio の意味と人が判断する場面は、implement が本文を読んで理解するので、
スクリプトの仕事ではありません。
