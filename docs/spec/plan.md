# plan の仕様

plan は、brainstorm で承認された仕様書を、実装の手順書に変えるステップです。
手順書は、人が読んで「何がどう変わるか」を判断できる文書であると同時に、次のステップ
（cycle と、その中の implement）がそのまま実行できる文書です。

全体の中での位置と、brainstorm から何を受け取り cycle へ何を渡すかは
[workflow.md](workflow.md) にあります。ここでは plan の中で何が起きるかを説明します。

## 何をするステップか

plan は「決まったことを、順番に並べる」だけのステップです。新しいことは決めません。
仕様書に書いていないことが手順を書く途中で必要になったら、自分で埋めずに brainstorm へ
戻します。これは、手順書が「2 回目の設計」になって、人が承認していない設計が実装に
流れ込むのを防ぐためです。

plan が終わったとき、次のものができています。

- 人が読んで承認した手順書（`.agents/artifacts/plans/` に置かれ、git で管理される）

未完了の手順書の索引は作りません。**作業ツリーにある手順書が、そのまま未完了の一覧です。**
手順書は git で管理し、完了して取り込まれたら作業ツリーから削除します。過去の手順書は
git の履歴から読めます。索引と現実がずれる余地を作らないための形です。

手順書ができても、cycle は自動では始まりません。人が「実装して」と言って初めて動きます。

## 受け取るもの

plan は、brainstorm または人が名前を挙げた仕様書だけを入力にします。リポジトリの中を
探して「これが関係ありそう」と仕様書を自分で選ぶことはしません。

手順書を書き始める前に、次がそろっているかを確かめます。

- 作る物が、1 回の実装と検証で終わる 1 つの単位になっている
- 参照する仕様書のパスと、その内容の指紋（SHA-256 のハッシュ値）が分かっている
- 仕様書に、完了を確かめる方法と、人が判断する場面が書いてある
- 配布の仕方、動かし方、保存する状態、外部サービスとの入出力が決まっているか、
  無いと確認されている
- 決まっていないこと（未決定）が残っていない

1 つでも欠けていたら、草稿を書かずに、何が足りなくてどう困るかを人の言葉で説明し、
brainstorm へ戻します。

## 手順書に書くこと

手順書は 1 つの Markdown ファイルです。人が読む部分と AI が読む部分を分けません。
全体を人の言葉で書いたうえで、implement が機械的に読む箇所だけ、決まった書き方をします。

### 仕様書を書き写さない

**手順書は仕様の内容を書き写しません。**仕様書へ参照を張り、その計画で何をどう作るかだけを
書きます。

写しを持つと二重管理になります。仕様書が改訂されるたびに写しが古くなり、手順書ごと
作り直しになります。実際に、写しを求めていた時期の手順書は 788 行あり、そのうち大半が
仕様の写しでした。そして 1 つの実装で 3 回の改訂が起き、3 回とも引き金は仕様の改訂でした。

手順書に書くのは次です。

- **仕様書への参照**: どの仕様書のどの節に基づくか。パスと指紋と節の名前
- **この計画で採る実装方針と、その根拠**: 仕様が許す範囲の中で、なぜこの作り方を選んだか
- **変更するファイル**: 手順書全体の範囲と、各手順で触る範囲
- **順序**: 手順の並びと、手順どうしの前提
- **各手順の完了の示し方**: 下の 4 種類から 1 つ
- **実装側に任せてよい選択**（あれば）
- **止まる条件**

仕様の詳細を知りたい読者は、参照から仕様書を読みます。承認する人は、その仕様書を既に
承認しているので、写しを読み直す必要はありません。

読んで分からないのは、**この計画に固有の判断**だけであってはいけません。「なぜこの順序か」
「なぜこのファイルを触るのか」「どこで止まるのか」は手順書だけで分かるように書きます。
それらは仕様書に書いていない、この計画の判断だからです。

### 機械が決まった書き方で読む箇所は 2 つだけ

implement が決まった書き方から読むのは、次の 2 つだけです。

| 箇所 | 書き方 | 何に使うか |
|---|---|---|
| 参照する仕様書 | `**Target specifications:**` の下に、パス・指紋・該当する節の一覧 | 実行前に、仕様書が承認時から変わっていないことを確かめる |
| 変更してよい範囲 | `## Scope` の下の、ファイルの木（`text` のコードブロック） | 範囲の外へのコミットを拒否する |

この 2 つだけが決まった書き方を持つのは、**どちらも外の世界と照らし合わせる値**だからです。
指紋は承認した内容と手元の内容を比べ、範囲はコミットの境界で守ります。機械が読めないと
成り立ちません。

手順、完了の示し方、人が判断する場面、手順書の ID と版は、本文を読んで理解します。
決まった書き方を求めません。読めない書き方だったとき、直せるのは AI であって、機械が
止まっても誰も助かりません。意味が変わる直しなら plan へ返します。

機械が読む印（見出しや太字のラベル）は、利用者の言語に関わらず同じ英語の固定語です。
手順書の本文や節の名前は利用者の言語で書きます。印の横や下に、利用者の言語で説明を添えて
かまいません。

草稿を保存するときと正本に移すときに、補助スクリプトはこの 2 つを検査します。読めなければ
草稿を保存せず、正本にもしません（「草稿と承認」の節）。人が読んで承認した手順書が、
実行の段になって初めて「読めない」と言われることを防ぐためです。

参照する仕様書の書き方の例です。

```markdown
**Target specifications:**

- `docs/spec/implement.md`
  - content identity: `sha256:0123…abcd`
  - sections: `残っている作業があるとき`, `証拠の残し方`
```

implement は、パスと指紋だけを機械的に読みます。該当する節（`sections`）は人のためのもので、
「この手順書が仕様書のどこに基づいているか」を人が辿れるようにします。節の名前は仕様書の
見出しそのもの（利用者の言語）を backquote で囲み、コンマで区切ります。

plan は、ここに書いた指紋が、そのパスにいま置かれている仕様書の指紋と一致することを、
草稿の保存時と正本への移動時に確かめます。一致しなければ、手順書が古い仕様書か存在しない
仕様書に基づいていることになるので、止まります。承認のあとで仕様書が変わっていないかを
確かめるのは implement の役目で、plan が確かめるのは「書いた時点で正しかったか」です。

変更してよい範囲の書き方の例です。字下げで階層を表し、ディレクトリは末尾に `/` を
付け、パスはリポジトリの先頭からの相対パスにします。コメントや注釈は書きません。
この書き方から外れると、plan の検査で止まります。

````markdown
## Scope

```text
skills/ba0918-implement/
  SKILL.md
  references/
    execution.md
  scripts/
    implement_runtime.py
```
````

### 完了の示し方

各手順は、完了をどう示すかを次の 4 種類から 1 つ選んで書きます。

| 書き方 | 意味 | 何に使うか | implement が要求する証拠 |
|---|---|---|---|
| `**Completion:** test` | テストで示す | 決まった入力に決まった出力を返すコード | 先に失敗するテストを書き、通ったこと |
| `**Completion:** check` | 検査で示す | 生成した物、道具が判定できる成果物 | 手順に書いた検査コマンドがすべて成功で終わったこと |
| `**Completion:** artifact` | 作った物で示す | 人や AI が読んで意味を判断する文章 | 決めた内容のファイルが存在し、形式の検査を通り、人が読んで OK と言ったこと |
| `**Completion:** external` | 外で確かめる | 実機での動作確認、人が頼んだ実測 | 実行した結果を人が見て OK と言ったこと |

この仕様書では、4 種類を「テストで示す」「検査で示す」「作った物で示す」「外で確かめる」と
呼びます。手順書に書く値は `test`、`check`、`artifact`、`external` です。

選ぶ基準は「何を作るか」ではなく、**誰が完了を判定できるか**です
（[workflow.md](workflow.md) の「plan → implement」と「承認を儀式にしない」）。

- 決まったコマンドが判定できる → `test`（先に失敗するテストが書けるとき）か `check`
- 人が読んで意味を判断しないと決まらない → `artifact` か `external`

「検査で示す」を選んだ手順には、**成功を判定する検査コマンドを 1 つ以上、手順に書きます**。
検査を書かずにこの種類は選べません。生成した複製の同期（`gen` と `verify`）、リポジトリ
全体の検査の通過、書式の検査だけで完了が決まる手順がこれにあたります。人の承認は求めません。

検査コマンドは、その手順の中に `**Checks:**` の宣言として書きます。1 行に 1 つ、コマンド
全体を逆引用符で囲んだ箇条書きです。

````markdown
**Completion:** check

**Checks:**

- `bunx agentic-skill-vendor gen`
- `bunx agentic-skill-vendor verify`
````

implement は、ここに挙げたコマンドだけを、書かれた順に走らせます（[implement.md](implement.md)
の「検査で示す」）。手順の本文に文章としてコマンドが出てきても、それは走りません。走らせる物を
一箇所に集めるのは、手順書が名前を挙げた検査と、実際に走った検査を同じにするためです。

`**Checks:**` が無い、または 1 つもコマンドを挙げていない `check` の手順は、手順書として
受け付けません。`check` 以外の種類の手順に `**Checks:**` は置きません。

**人や AI が読んで意味を判断する文章を `check` にしてはいけません。** 検査コマンドを 1 つ
書けば承認を省ける、という使い方は、承認を儀式にしないという約束に反します。仕様書、skill の
本文、手順書、利用者向けの文書は `artifact` です。この線引きは機械では判定できないので、
plan が書くときに守ります。

AI が実際に走らせる確認（実測）は、人が頼んだときだけ「外で確かめる」として手順に入れます。
頼まれていないのに AI が実測の手順を足すことはしません。

### 各手順に書くこと

手順ごとに次を書きます。

- 目的と、仕様書のどの節に基づくか（節の名前を挙げる。節の内容は写さない）
- 前提（先に終わっているべき手順、先に決まっているべきこと）
- 変更してよいファイルの範囲（手順書全体の範囲の中で、さらに絞る場合）
- 完了の示し方（上の 4 種類から 1 つ）と、具体的に何を確かめるか。`check` なら検査コマンドも
- 実装側に任せてよい選択（あれば）
- 止まる条件

「具体的に何を確かめるか」は、仕様の再記述にならない範囲で書きます。仕様に書いてある
振る舞いをもう一度書くのではなく、**この手順が終わったと言える条件**を書きます。

実装側に任せてよい選択は、どれを選んでも承認された振る舞いが変わらない範囲に限ります。
新しい入力の種類、受け入れの境界、エラーの扱い、許容する誤差、検証の例を手順書で
初めて決めることはしません。それらは brainstorm に戻します。

### 人が判断する場面の宣言

仕様書で「ここは人が判断する」と決まっている手順には、人向けの説明に加えて、
implement が読む宣言を同じ手順の中に置きます。

````markdown
**Human gates:**

```json
{
  "version": 1,
  "gates": [
    {
      "gate_id": "profile-wording",
      "sections": ["Review profile"],
      "criterion": "観点の文言が承認した仕様の意味と一致しているか",
      "target": { "kind": "files", "paths": ["skills/ba0918-review/references/profile/default.md"] },
      "timing": "before_commit",
      "allowed_results": ["approved", "rejected"]
    }
  ]
}
```
````

- `gate_id` は手順書の中で一意
- `sections` は、この手順が基づく仕様書の節の名前。手順書冒頭の `**Target specifications:**`
  の `sections` に列挙した名前のどれかと一致していなければなりません。比べるのは節の名前
  そのもので、backquote は含めません（上の例なら `"残っている作業があるとき"` と書きます）。
  一致しない名前があれば、plan の検査で止まります。節の名前を手で写すときの誤字や、
  仕様書側の改名に追従できていない手順書を、人が読む前に見つけるためです
- `criterion` は、人が「はい / いいえ」で答えられる 1 つの問い
- `target` は、判断の対象。リポジトリ内の相対パスの集合（`files`）か、変わらない証拠の
  指紋（`event` と `content_identity`）のどちらか
- `timing` は `before_edit`（編集の前）、`before_commit`（コミットの前）、
  `before_implementation_green`（全手順完了の前）のどれか
- `allowed_results` は `approved` と `rejected` だけ

答えによって作る物の意味が変わるような判断は、ここに書きません。それは brainstorm で
決めることです。人の判断が要らない手順には、この宣言を書きません。

## 草稿と承認

手順書は、brainstorm の仕様書と同じ手順で正本になります。

1. AI が草稿を `.agents/tmp/plans/<手順書 ID>_<名前>_r<版>_draft.md` に保存する。
   補助スクリプト（`scripts/plan_artifact.py draft`）が、implement が機械的に読む箇所の
   書き方と、参照する仕様書の指紋の一致を検査してから保存し、パスと指紋を返す。
   検査に通らなければ保存せず、どこが読めないかを返す。AI はそれを直して保存し直す
2. AI はチャットに、草稿のパス、指紋、正本の置き場所、人が判断すべき点だけを出す。
   草稿の全文をチャットに貼らない。要約を承認の対象にしない
3. 人が自分の道具で草稿を読み、「このパスのこのファイルを、この指紋のまま正本にして
   よい」と明示する
4. AI が補助スクリプト（`scripts/plan_artifact.py publish`）で正本の場所へ移し、git に
   追加してコミットする。移す前に、草稿の指紋が提示したものと同じであることと、草稿が 1 の
   検査にいまも通ることを確かめ、移したあと読み戻して一致したときだけコミットする

黙っていること、「もう少し話そう」と言うことは承認ではありません。直したいところがあれば
対話で受けて新しい草稿を出します。人にファイルを直接編集してもらうことはしません
（編集すると指紋が変わり、古い草稿として拒否されます）。

承認の前に、正本の手順書や状態ファイルを作ったり書き換えたりしません。草稿が触ってよいのは、
自分の一時ファイルだけです。

同じ名前の草稿がすでにあるとき（前の会話が途中で切れたときなど）は、置き換える対象の
指紋を明示したときだけ置き換えます。指紋が合わない古い草稿を黙って消すことはしません。

## 手順書の改訂

正本になった手順書は、その場で書き換えません。進捗の記録のために書き換えることも
しません。

- 作る物の意味、禁止、許容する差異、人が判断する場面を変える必要が出たら、手順書を
  直さずに brainstorm へ戻します。仕様書が改訂されたら、それに基づく手順書は新しい版として
  作り直します
- 意味を変えずに手順だけを直す場合（たとえば、implement が読めない書式を直す）は、
  新しい版を新しいパスに作り、全文を人に見せて同じ承認を取ります。古い版に結び付いた
  実装の証拠は古いものになります。古くなった証拠は捨てる物ではなく、implement が新しい版で
  束ね直して続けられます（[implement.md](implement.md) の「残っている作業があるとき」）

## 未完了の手順書をどう知るか

索引は作りません。**作業ツリーの `.agents/artifacts/plans/` にある手順書が、未完了の
一覧です。**

- 手順書は git で管理します。承認して正本にするとき、同じ操作でコミットします
- 完了して取り込まれたら、作業ツリーから削除します（`git rm`）。過去は git の履歴で読めます
- 「いま対象」「保留」の印は持ちません。作業ツリーにあるかどうかだけです

索引を置かないのは、索引と現実がずれるからです。索引は、手順書を公開する操作で書かれ、
実行が完了する操作では触られません。書く手順を飛ばしても作業は進むので、飛ばされます
（[workflow.md](workflow.md) の「記録は、現実を変える操作と同じ操作の中で書く」）。

同じ理由で、`status.md` や `session-history.md` のような状態ファイルも作りません。
進み具合は implement が残した証拠と状態の写しから導きます。

生きている実行（実装が動いているブランチと作業ディレクトリ）は、`git worktree list` が
答えます。plan はそれを読むだけで、書きません。

## 複数の手順書があるとき

作業ツリーに未完了の手順書が複数あってもかまいません。plan はどれかを「いま対象」に
選びません。どれを実装するかは、cycle か implement を起動するときに決まります。

同じ目的の手順書が二重にできそうなときは、AI が既にある手順書を見せて、新しく作るか
既存の版を改訂するかを人に聞きます。黙って似た手順書を並べません。

## やらないこと

- 仕様書に無いことを決めない。設計しない
- 実装しない。テストを書かない。コミットしない
- ブランチや作業ディレクトリ（git worktree）を作らない、切り替えない
- 進捗を手順書や状態ファイルに書かない
- 未完了の手順書の索引や、状態ファイルを作らない
- 止まった実装の再開を行わない（それは implement が受け持つ）
- cycle や implement を自動で始めない
- 仕様の内容を手順書に書き写さない

## 人が判断する場面

| 場面 | 人が決めること |
|---|---|
| 入力が足りない | brainstorm に戻って決める |
| 草稿の承認 | そのファイルを、その指紋のまま正本にしてよいか |
| 似た手順書が既にある | 新しく作るか、既存の版を改訂するか |
| 未コミットの変更がある | どう隔離するか（plan は行わない） |

## 失敗したときの動き

- 正本への移動、読み戻し、コミットのどこかで失敗したら、どの段階で失敗したかを
  報告し、「正本にした」とは言いません。草稿は再開用に残します
- 草稿が書き方の検査や指紋の一致に通らなければ、草稿を保存せず（または正本にせず）、
  どの箇所がどう読めないかを示します。人に見せる前に AI が直します

## skill の構成

```text
skills/ba0918-plan/
├── SKILL.md                 入口。責任の範囲と、どの補足をいつ読むか
├── references/
│   ├── creation.md          入力の確認、草稿の書き方、承認、正本への反映
│   ├── readability.md       手順書を人が読める形にするための確認項目
│   └── lifecycle.md         改訂、索引、いま対象の切り替え
└── scripts/
    └── plan_artifact.py     草稿の保存、正本への反映、参照する仕様書と変更してよい範囲の読み取り
```

機械が決まった書き方で読む 2 箇所（参照する仕様書、変更してよい範囲）は、この
`plan_artifact.py` が 1 か所で持ちます。implement はこの読み取りを使い、自分で別の解釈を
持ちません。手順、完了の示し方、人が判断する場面は、implement が本文を読んで理解するので、
スクリプトの仕事ではありません。
