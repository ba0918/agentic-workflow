# マージまで進める設定 仕様

この文書は、cycle と iterate が収束した後に、人を待たずに取り込み（マージ）まで進めるための設定の約束を、人が読んで判断できる形で書いたものである。
設定の無いリポジトリでは何も変わらず、cycle は終端報告で終わり、取り込みは人がする。
ループと終端報告の約束は[開発ワークフロー仕様](workflow.md)に、小さいタスクの約束は[小さいタスク skill 仕様](iterate.md)にある。
この文書の上位に理念（`docs/principles.md`）があり、食い違ったときは理念に従う。

## 設定

取り込みまで進めるのは、プロジェクトの指示にそう書いたリポジトリだけである。
プロジェクトの指示とは、そのリポジトリで agent が毎回読むファイル（`AGENTS.md`、`CLAUDE.md` など）を指す。
書く内容は「cycle は収束したらマージまで進める」という趣旨の 1 文で、決まった書式は持たない。

設定を置く場所をプロジェクトの指示に限るのは、取り込みの安全さがリポジトリごとに違うからである。
検査があるか、ブランチ保護があるか、取り込み先への push で公開が動くかは、リポジトリで決まる。
人の利用者スコープの指示ファイルに書かれていても、設定とは見なさない。

取り込みは取り消しにくい操作で、[人を止める場面](workflow.md#人が見るのは最終成果物だけ)の 1 に当たる。
設定は、人がその操作を先に頼んでおく手段である。
設定があれば、条件が揃った時点で聞かずに進めてよい。

その回だけ止めたいときは、人が実行の最初に「今回はマージしない」と言う。
そのとき cycle は設定が無いのと同じように動く。

設定が無いリポジトリで取り込んだら反例である。
設定があるのに、条件が揃った後で「マージしますか」と聞いたら反例である。

## 取り込む条件

設定があるリポジトリで、cycle は次の 4 つが全部揃ったときだけ取り込ませる。

1. 終端報告の「先に見てほしい所」が無い（[終端報告](workflow.md#終端報告)）
2. 未確認の成功条件が無い。つまり[終わり方](workflow.md#終わり方) 1 の収束で終えた
3. 検査が通る（「検査が無いとき」）
4. 変更が、人が必ず見るパスに触れていない（「人が必ず見るパス」）

1 つでも欠けたら、pull request を残して終端報告で終わる。
終端報告には、どの条件が欠けたかを書く。
「未確認あり」で終えたときは条件 2 が欠けるので、pull request を作って止まる。
収束以外の終わり方（上限、進捗が無い、差し戻し）では、push も pull request の作成もせず、設定が無いリポジトリと同じく終端報告だけで終わる。
途中で止まった作業をリモートに出さないためである。

1 と 2 は cycle 自身の判定で、3 は機械的に決まる。
4 は、CI の workflow ファイルのようにパスで決まる物と、cycle が差分を読んで判断する物を含む。迷ったら触れているとする。
1 と 2 の判定が甘かったときは、3 と 4 だけが残りの歯止めになる。
それでも判定のための agent は足さない。
根拠が弱い判断や未確認の物が 1 つでもあれば止まる形にしてあり、止まる側に倒れるからである。

条件が欠けているのに取り込ませたら反例である。
取り込むために、「先に見てほしい所」に載せるべき物を載せなかったら反例である。

## 人が必ず見るパス

次の 7 種類のどれかに触れる変更は、ほかの条件が揃っていても取り込まない。

- 公開、配布、版の宣言（package manifest の version、publish の設定、release workflow、tag）
- 資格情報や秘密
- 外部到達（ネットワーク、外部 API、deploy、DB migration）
- 消す変更のうち、消える物の利用者を列挙できない物
- CI の workflow ファイル
- プロジェクトの指示のファイルと、指示が設定や検査の一覧を任せた先のファイル
- プロジェクトの指示が名指しする検査の定義（検査の script、hook の設定）

上の 4 つは、入口 skill 仕様の[外に出る徴候](using-workflow.md#判断に任せない物)と同じ物である。
残りの 3 つを足すのは、取り込みを決める物そのものを書き換えられると、歯止めにならなくなるからである。
CI の workflow と検査の定義を書き換えれば、条件 3 が通る。
プロジェクトの指示を書き換えれば、設定を足すことも、検査の一覧から検査を外すこともできる。

同じ理由で、設定があるかどうかと、検査の一覧は、取り込み先のブランチ側の写しで読む。
作業ブランチ側の写しでは読まない。
作業ブランチが自分で設定を書き足して、自分を取り込ませたら反例である。

プロジェクトの指示で、人が必ず見るパスを足せる。
減らすことはできない。
歯止めを外す書き方を skill が持たないためである。

触れているかどうかは、pull request が取り込む差分の全体（取り込み先との差分）で判定する。
cycle や iterate の比較の基点は使わない。
同じブランチで iterate を回し直すと比較の基点が置き直され、前の実行の変更が判定から外れるからである。
同じ理由で、条件 1 と 2 も、そのブランチの指摘 JSON があるなら残る物の全体で見る。
レビューが 0 回で指摘 JSON が無い実行では、終端報告の「先に見てほしい所」と成功条件の確認結果だけで判定する。

## 検査が無いとき

検査は次の順で決める。

1. ホスティングサービス側の検査（pull request に付く CI）があれば、それが通るのを待つ
2. 無ければ、取り込み先のブランチ側のプロジェクトの指示にある検査を手元で通す
3. どちらも無ければ、取り込まない

検査が 1 つも無いリポジトリでは、設定があっても pull request を残して終端報告で終わる。
機械の検査が無いことを、レビューで代用しない。

## 手段

cycle は作業ブランチを push し、終端報告を本文にした pull request を作る。
条件 1、2、4 が揃っていれば、検査が通った時点でホスティングサービスが取り込む設定（自動マージ）にする。
検査が通るのを待つのはホスティングサービスである。
検査を手元で通す場合（「検査が無いとき」の 2）は、通してから pull request を作って取り込ませる。
取り込みの方式（merge、squash、rebase）は、リポジトリの設定に従う。
取り込み先は、pull request の既定の取り込み先（リポジトリの既定のブランチ）である。

手元で取り込み先にマージして push することはしない。
ブランチ保護とホスティングサービス側の検査を通らないからである。

push と pull request の作成は、設定があるリポジトリで、収束か「未確認あり」で終えたときだけ行う。
条件が欠けて止まったときも、pull request は残す。人はそこで終端報告を読み、自分で取り込める。

ただし、次のどれかに当たるときは、push も pull request の作成もせず、終端報告だけで終える。

- その実行で、秘密情報の露出による停止が起きた
- 差分が資格情報や秘密に触れている
- 「先に見てほしい所」に、重さが `security` の項目がある

pull request の本文は終端報告なので、未修正の `security` の指摘の内容がリモートへ出る。
秘密が履歴に残ったまま push すれば、秘密そのものが出る。
公開のリポジトリでは、どちらも外から読める。
プロジェクトの指示に「その場合も pull request を残す」と書いたリポジトリでは、この 3 つの場合も pull request を残す。
リモートが非公開で、止まった理由を必ず pull request で読みたいリポジトリのための切り替えである。
この切り替えも、取り込み先のブランチ側の写しで読む。
切り替えが無いリポジトリで、`security` の項目が残る終端報告を pull request の本文にしたら反例である。

自動マージを設定した時点で取り込みが済んでいれば、cycle はそれを終端報告に書いて終える。
検査や人の承認を待っている状態なら、取り込みを待たずに、自動マージを設定したことと、取り込みが検査待ちであることを書いて終える。
人の承認が必須のブランチ保護や長い検査では、待つと実行が終われないからである。
取り込んだ後の worktree とローカルのブランチは、cycle は消さず、メインセッションが片付ける。
ホスティングサービスが検査の失敗などで取り込まなかったときは、その理由を終端報告に書いて終える。
検査を通すために検査を書き換えたら反例である。

## iterate

iterate にも同じ設定と同じ条件が効く。
条件 2 は、iterate の収束の読み替え（[読み替える点](iterate.md#読み替える点)）に従う。
iterate が収まらないと判定して止まったとき、差し戻しで終わったときは、取り込まない。

## 作る物

- cycle の skill 本文に、収束の後の分岐（設定があるか、条件が揃うか）を足す。条件の中身は参照資料に置き、設定があるときだけ読む
- README の skill の説明に、設定の書き方を 1〜2 行で足す

## 作らない物

- 利用者スコープの指示ファイルでの設定
- 人が必ず見るパスを減らす書き方
- 取り込むかどうかを判定する専用の agent や分類器
- 取り込んだ後に戻す仕組み（フラグ、段階的な公開、自動の revert）
- 取り込みの方式や取り込み先を選ぶ設定
- 取り込みが済むまで待つこと

## 根拠

人の操作を減らす方向は利用者の要望による（2026-11-26）。
毎回の口頭の指示は忘れるので、設定を 1 回書く形にした。

次の 3 つは、Claude Code チームの記事を参考にした。
変更の中身で人が見るかどうかを分けること。CI の workflow ファイルを必ず人が見ること。取り込みを止める条件に未解決の指摘と検査の失敗を置くこと。
出典は <https://claude.dev/blog/solving-code-review-at-anthropic/> である（2026-10-15 公開、2026-11-26 に読んだ）。
記事のチームは、人が見るかどうかを決める分類器をレビューとは別に持ち、取り込んだ後に戻す仕組み（フラグ、段階的な公開、当番）も持つ。
この仕様はどちらも持たないので、条件を止まる側に倒してある。
記事は、人の承認なしで取り込まれる割合と、分類器の精度を述べていない。

## 却下した案

- 取り込みまで進めるかを、実行のたびに口頭で指示すること。毎回の指示は忘れる
- 利用者スコープの指示ファイルに書けば、どのリポジトリでも進めること。検査とブランチ保護が無いリポジトリまで取り込まれる
- 検査とパスの 2 条件だけで取り込むこと。根拠の弱い判断が、人の読む前に取り込み先へ入る
- 「人が見るべきか」を別の agent に判定させること。設定があるリポジトリで、実行ごとに agent が 1 体増える
- 人が必ず見るパスを、プロジェクトが減らせるようにすること。歯止めを外す書き方を skill が持つことになる
- 検査が無くても、ほかの条件が揃えば取り込むこと。何も検査されていない変更が取り込み先に入る
- 手元でマージして push すること。ホスティングサービス側の検査とブランチ保護を通らない
- iterate には設定を効かせないこと。小さいタスクは毎回、人が取り込むことになる
- 条件が欠けたら、どの場合も必ず pull request を残すこと。未修正の `security` の指摘の内容や、履歴に残った秘密がリモートへ出る
- `security` の項目が残る場合などに、どのリポジトリでも push しないこと。リモートが非公開のリポジトリでは、止まった理由を pull request で読めたほうがよい
- 設定と検査の一覧を作業ブランチ側の写しで読むこと。ブランチが自分で書き換えて、自分を取り込ませられる

## 未決定

- このリポジトリ自身のプロジェクトの指示へ設定を書くかどうか。決めるのは利用者で、時期はこの仕様が skill へ入った後である

## 委任

- pull request の題名と、終端報告を本文に収める形は、cycle の実行者に任せる。どの形でも取り込む条件は変わらない
- 取り込み先は pull request の既定の取り込み先に固定し、選ぶ設定を持たない。壁打ちでは聞かずに決めた。別のブランチへ取り込みたい実例が出たら見直す
- 取り込みが済んだことの確かめ方（どのコマンドで見るか）は、cycle の実行者に任せる。ホスティングサービスごとに違う
