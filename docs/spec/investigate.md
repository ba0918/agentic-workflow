# 調査 skill 仕様

この文書は、読むだけで原因を調べる skill（investigate）の約束を、人が読んで判断できる形で書いたものである。
skill は `skills/ba0918-investigate/` に置き、本文と参照資料は LLM 向けの英語で、この文書の内容を実行者への指示として写したものである。
両者の意味が食い違ったときは、この文書を正とする。
この文書の上位に理念（`docs/principles.md`）があり、食い違ったときは理念に従う。
用語集はリポジトリ直下の `CONTEXT.md` にある。

investigate は、開発ワークフロー仕様（`docs/spec/workflow.md`）が定める 5 つの skill の流れの外にある独立した skill である。
5 つの流れには加わらず、その仕様書も変えない。
実行環境、状態を保存する仕組み、状態を読み書きする script を持たないという縛りは、5 つの skill と同じ形で効く。
skill 本文と参照資料の行数の上限は合計で 163 である。
値は作り直し前の本文 200 行から、持ち越さない「実装後の検証」の節 37 行を引いた実測から取った。
超えたら肥大化と見なし、減らす。

## 責務

責務は、人が述べた症状や疑問を受け取り、読むだけで原因と影響を調べることである。
修正せずに報告し、次の行動を提案する。
調べる物は、問題の確認、原因（直接と根本）、影響範囲、テストの有無の 4 つである。
用語集ではこれを「調査」と呼び、review の直接呼び出しである「診断」と区別する。
調査の出発点は症状や疑問であり、診断の出発点は差分や文書などの対象である。
調査は指摘の形（重さ、対応、確かめ方）を持たない。

調べる範囲は人の問いに釣り合わせる。
1 つの module で答えが出る問いにリポジトリ全体を読むのは範囲の広げすぎであり、逆に問いが 3 つのディレクトリにまたがるのに 1 つだけ読んで結論を出すのは不足である。

人が単独で呼ぶだけで、cycle の中からは呼ばない。
cycle の中で問題を見つける役は review が持つ。

## 読むだけの保証

ファイルを編集、作成、上書き、削除、移動しない。名前も変えない。
notebook も含む。
リポジトリとファイルシステムの状態を変えない。
例外は 1 つだけで、人が出力先を明示して報告のファイルを頼んだときに、その場所へ報告を書くことである。
出力先を言わずにファイルを頼まれたら、自分で場所を選ばずに人へ聞く。

許す操作は次の 6 つである。

- ファイルを読む
- パスを列挙する
- 文字列や記号を検索する
- 読むだけと分かっているコマンドを走らせる
- コードの参照を辿る
- 広い探索を subagent に委譲する

テストは、snapshot、キャッシュ、生成物などリポジトリの状態を更新しないと分かっているときだけ走らせる。

禁じる操作は次のとおりである。

- `rm` `rmdir` `mv` `cp` `chmod` `chown` `touch` `mkdir` `tee`
- 出力のリダイレクトと、その場での書き換え
- `commit` `push` `reset` `checkout --` などの状態を変える git 操作

この列挙は例示であり、状態を変えるおそれのある他のコマンドも同じく拒む。

保証の手段は skill 本文の指示であり、道具を絞った別文脈の agent には任せない。
道具を Read / Grep / Glob に絞ると、安全と分かっているテストの実行ができなくなるためである。
保証は skill 本文の指示で担い、調査の前と後に `git status` を取って比べる。
成功条件は、頼まれた出力先を除いて、前後の `git status` の出力が変わらないことである。
頼まれた出力先を除き、追跡外の場所（キャッシュ、`.agents/`、一時ディレクトリ）への書き込みも禁止だが、`git status` には現れない。
こちらは、走らせたコマンドがすべて読むだけと分かっている物であることで担保し、疑わしいコマンドは走らせない。
git 管理下でない対象では前後の比較が取れないので、この担保だけで保証を満たしたとする。
前後の比較か、走らせた操作の結果から、頼まれた出力先以外に差が出たと分かったら、この保証は破れている。

調べた先に認証情報などの秘密があったら、存在だけを報告し、値は書かない。
subagent へ渡すプロンプトにも写さない。
報告に鍵の値が 1 文字でも現れたら反例である。

## 進め方

### 文脈を掴む

人の述べた問題を受け取り、プロジェクトの指示書と関係するディレクトリの構造を見る。
使えるエラー、ログ、スタックトレース、変更されたファイル、仕様の記述を探す。

### 4 つを調べる

問いに関係する範囲で、次の 4 つを調べる。

1. **問題の確認**：観測された振る舞いと、それが起きる条件を具体にする
2. **原因の特定**：証拠を辿って直接の原因（コードの箇所）を見つけ、当てはまるなら設計の階層の根本原因まで辿る
3. **影響の分析**：影響を受ける利用側、依存、同じパターンの他の出現を探す
4. **テストの確認**：既存のテストが問題を通しているかを見る。該当するテストが無ければ影響の節に `no tests` と明記する

原因を「たぶんここ」で止めず、直接の原因には観測した箇所（ファイルと、当てはまるなら行）を付ける。

### 探索を委譲する

次のどれかに当たるときは、探索を別文脈の subagent に委譲する。

- 調査が 3 つ以上のディレクトリにまたがる
- 3 つ以上の見る角度を並列に探すべきである
- 1 つの角度で 5 ファイル以上の横断検索が要る

どれにも当たらなければ委譲せず、自分で読む。
当たっていても、次のどちらかで対象が狭く縛られているときは自分で読んでよい。

- 文書の調査で、1 つの検索式で対象の中核ファイルを列挙し切れる
- 既知のパス 10 個以内で対象が収まる

委譲先のプロンプトには、「読むだけの保証」の節のうち委譲先の行動を縛る部分をそのまま書く。
それは次の 5 つである。

- 編集・作成・上書き・削除・移動・改名の禁止
- 許す操作。ただし「広い探索を subagent に委譲する」は写さず、委譲先はさらに委譲しない
- 読むだけと分かっているコマンドだけを走らせること
- 禁じる操作と、それが例示であること
- 秘密の扱い

報告のファイル出力の例外と、前後の `git status` の比較は、呼び出した側の物なので委譲先には書かない。
代わりに「委譲先はファイルを一切書かない」と明記する。
複数の subagent は同時に起動する。
失敗した subagent はやり直さず、自分で読んで続ける。
委譲先が状態を変えたら、それは調査側の保証の破れとして扱う。

## 報告

報告は会話に返し、ファイルには書かない。
人が出力先を明示してファイルを頼んだときだけ、その場所に書く。
読むのは目の前の人だけで、後工程が機械で読むことはないためである。
診断の報告が `.agents/tmp/` に置かれるのは reviewer の JSON を書き起こす都合であり、調査には書き起こす元が無い。

報告は次の 6 節からなり、見出しの語は固定で英語、中身は会話の言語で書く。

```text
══════════════════════════════════════
INVESTIGATION REPORT
══════════════════════════════════════

## 1. Problem overview
## 2. Cause analysis
## 3. Impact
## 4. Confidence
## 5. Fix options
## 6. Recommended action
```

1 は何が起きているか、2 はなぜ起きるかで、直接の原因と（当てはまるなら）根本の原因を分けて書く。
3 は影響を受けるファイル、機能、同じパターンの他の出現で、テストが無ければ `no tests` を書く。
4 は確信度と 2〜4 個の根拠、5 は修正案、6 は推奨する次の行動である。
6 節のどれかが欠けた報告は不完全である。

### 確信度

- **high**：ファイルの中身、検索、コマンド出力で機械的に確かめた。もっともらしい反例は述べた範囲の外にある
- **medium**：推論で支えられているが、反例や範囲外の不確かさが残る
- **low**：限られた証拠だけに基づき、追加の情報か調査が要る

不確かさは正直に書く。
読んでいないファイルを根拠に high を付けるのは反例である。

### 修正案

修正が要るときは 1〜3 案を出し、何もしないことが正当なら `keep as-is` を含める。
各案は「変える場所（ファイルと箇所）」「概要」「長所と短所」の 3 点で書く。
見つけた欠陥は、人が述べた症状、または疑問が指す対象の壊れを引き起こすかどうかで分ける。
引き起こす欠陥は問題であり、案にする。
同じパターンの他の出現は、述べられた症状と同じ壊れ方をするなら問題として扱う。
引き起こさない欠陥は将来の改善である。
問題はあるのに放置を正当と見るときは、案の 1 つとして `keep as-is` を出す。
問題が 1 つも無ければ修正は要らず、5 節を `no fix needed` で始める。
将来の改善は、案の有無によらず 5 節の末尾に 1〜2 点まで添えてよく、案の形式には押し込まない。
6 節の推奨には将来の改善を出さない。
retry の問いで「間隔が無い」を見つけても、述べられた症状（500 が retry されない）を引き起こさないなら将来の改善である。
案を出すだけで、実行は始めない。
修正案の文中に「直しておいた」が現れたら、この責務の外に出ている。

### 推奨する次の行動

6 節では主となる推奨を 1 つ選び、複数が当てはまるときは軽い物から重い物へ代替を並べる。
表示する呼び出しはそのまま使える形にする。

| 状況 | 推奨 | すぐ使える形 |
|---|---|---|
| 小さい修正 | 人が直すか、メインセッションに頼む | 直す場所と内容 |
| 仕様書が無い、判断の根拠が無い、または二通りに読める | brainstorm | `/ba0918-brainstorm <題材>` |
| 仕様書があり、中くらい以上の変更 | plan、続けて cycle | `/ba0918-plan <仕様書のパス>` |
| 後回しにする | 人が控える | 控える内容の 1 行 |
| 直す必要なし | そう言う | `no further action needed` |
| 証拠が足りない | 調査を続ける | 続けて調べる範囲 |

小さい修正とは、1 つのまとまり（skill や module）の中で 3 ファイルまでの変更である。
それを越えるか、複数のまとまりを横断する変更は中くらい以上とする。
4 ファイルに触る変更を「小さい」と呼んで人に直させるのは反例である。

issue の管理は持たないので、後回しの行は人が控えることに留める。
iterate は現時点で存在しないため表に書かず、できたときに足す。

## 事故のとき

頼まれた出力先以外に差が出たと分かったら（例：走らせたテストが snapshot を書き換えた）、理念の「続けると被害が広がる事故」として止まる。
`git status` の差か、差が出たと分かった元の出力を人に示し、判断を仰ぐ。
自分では元に戻さない。
戻す操作も編集であり、保証を二重に破るためである。
このとき報告は出さない。
snapshot を書き換えたまま 6 節の報告を返したら反例である。

## 起動する言葉と診断との境界

起動する言葉は「調べて」「原因を調査して」「なぜ〜が起きる」「影響範囲を見たい」と、英語の同等の語である。
「検証して」「動作確認して」「実装確認」では起動しない。
これらは完成した変更を見る仕事で、review の直接呼び出しである診断が受け持つ。
突き合わせる相手があればそれとも突き合わせ、無ければ品質の指摘だけが返る。
診断の振る舞いは開発ワークフロー仕様の review の節に従い、この文書では定めない。
この文書が決めるのは、診断がこれらの言葉で起動するように review skill の description に足す語だけである。

人が「この変更、動作確認して」と言ったとき、investigate が動いて 6 節の報告を返したら、境界の破れである。

## 作る物

1 つのブランチで作る物は次のとおりで、ブランチと worktree はこのリポジトリに立てる。

- `skills/ba0918-investigate/`（`SKILL.md` と、要るなら `references/`）
- `PROJECT.md` の 3 か所
  - 冒頭の数を「開発を進める 5 つと、読むだけの調査 1 つ」に直す
  - 正本の表に `docs/spec/investigate.md` の行を足す。review の description に足す起動語の根拠もこの文書だと書く
  - 縛りの「5 つの責務を越える物は」を、数を持たない「skill の責務を越える物は」に直す
- `evals/cases/ba0918-investigate/` に scenario 2 本と、`evals/inputs/ba0918-investigate/` にその入力
  - 原因の調査が読むだけで完走する
  - 修正不要の判定で `no fix needed` を返す
- review skill の description の日本語キーワードに「検証 動作確認 実装確認」を足す。診断が「動作確認して」を受け取れるようにするためで、開発ワークフロー仕様は変えない
- `regression-lock.json` の review のエントリ
  - description だけの変更で、scenario は明示の呼び出しなので結果に影響しないと note に書く
  - `accepted-without-run` でハッシュを取り直す
- 用語集の冒頭の数と「調査」「診断」の 2 語（この仕様書と一緒に承認する）

scenario は作り直し前の fixtures（原因の調査と修正不要の 2 本）を、この文書の対応表に合わせて書き直したものである。
走らせるかどうかは人が頼んだときだけ決める。

## 作らない物

- 実装後の検証モード（変更ファイルと 1 段先の依存だけを見る範囲の縛りと、差の 3 分類）
- cycle からの呼び出し
- 「検証して」「動作確認して」「実装確認」での起動
- 報告のファイル出力（人が出力先を明示して頼んだとき以外）
- script、状態の保存、issue の管理
- iterate を指す対応表の行
- 道具を絞った別文脈の agent による保証
- `regression-lock.json` の investigate のエントリ（scenario を実走したときに skill-regression が書く）

## 却下した案

- 実装後の検証モードの持ち越し。診断と重なる。仕様書の無い変更の検証に隙間ができることと、実測済みの scenario を 1 本捨てることは承知の上
- 道具を Read / Grep / Glob に絞った別文脈の agent で読むだけを機械的に保証すること。安全なテストの実行ができなくなり、配る skill の本体に環境固有の agent 名を書けない
- 報告を `.agents/tmp/` の Markdown に置くこと。読むのは目の前の人だけで、後工程が機械で読まない
- 対応表に iterate と issue-create の行を残すこと。どちらも今のワークフローに無い
- 検証モードの scenario の持ち越し。モードと一緒に捨てる
- 直接呼び出しの語を「診断」以外にすること。開発ワークフロー仕様がすでに「コードベースの診断」と呼んでいる。理念の「診断して方法を変える」は一般語で、文脈で読み分ける
- 足した要求のぶん行数上限を 163 から引き上げること。上限は超えたときに必要性を疑う合図であり、超えたら減らす物を選ぶ
- 一度も実走していない skill の lock エントリを新しく置くこと。lock は何を走らせて確かめたかの記録であり、走らせていない物を載せると嘘になる
- 委譲先に写す範囲を「読むだけの保証」の禁止リストだけにすること。禁止リストはシェルコマンドの列挙で、編集禁止の本体と秘密の扱いが伝わらない
