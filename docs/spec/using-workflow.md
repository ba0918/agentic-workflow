# 入口 skill 仕様

この文書は、新しい依頼をどの skill から入れるかを決める skill（using-workflow）の約束を、人が読んで判断できる形で書いたものである。
skill は `skills/ba0918-using-workflow/` に置き、本文は LLM 向けの英語で、この文書の内容を実行者への指示として写したものである。
元にした claude-skills の同名 skill の写しではなく、この repo の skill 構成に合わせて書き直したものである。
両者の意味が食い違ったときは、この文書を正とする。
この文書の上位に理念（`docs/principles.md`）があり、食い違ったときは理念に従う。
用語集はリポジトリ直下の `CONTEXT.md` にある。

using-workflow は、開発ワークフロー仕様（`docs/spec/workflow.md`）が定める 5 つの skill の流れの外にある独立した skill である。
5 つの流れには加わらず、その仕様書も変えない。
実行環境、状態を保存する仕組み、状態を読み書きする script を持たないという縛りは、他の skill と同じ形で効く。
skill 本文の行数の上限は 73 である。
元の値は 60 で、claude-skills の同名 skill の実測 44 行（2026-09-01 に数えた）に例外の余地を載せた物だった。
工程を足す理由、床、外に出る徴候の 3 つを本文に入れたぶんを 10 行足した（2026-09-19）。
この 3 つは毎ターン読まれてはじめて効く。参照資料へ追い出すと、読まずに既定の全部入りへ戻る。
入口の例 3 つ（裸の「直して」、文言の無い「分かりやすく」、investigate の報告からの続き）のぶんを 3 行足した（2026-09-20）。
例は境界の判定にその場で要り、仕様書にだけ残すと本文は境界を失う。
行数は frontmatter とその直後の空行を除いて数える。
常駐して毎ターン読まれる前提の skill なので、上限は 5 つの skill の上限（110〜242）の半分未満に保つ。
参照資料は持たない。
上限は目安で、超えるときは、足した行が実行者にその場で要ることを、その変更のレビューで示す。
すぐに陳腐化する事は書かない。

## 責務

責務は、新しい依頼を受けたとき、どの skill から入るかと、ワークフローのどの工程を回すかを決めることである。
決めるのはこの 2 つだけで、作業そのものは始めない。
判定の対象は、作る・変える依頼と、原因の分からない不具合の報告と、読み調べないと答えられない疑問である。
質問と雑談はルーティングの対象外であり、skill へ送らずそのまま応える。
境界は読み調べの要否で引く。会話で答えられる質問は対象外で、ファイルを読む・検索しないと答えられない疑問は調査の依頼である。
作る・変える依頼でない操作（コミット、リリース、PR の段取りなど）も対象外であり、環境の手段と規則に従う。
対象外を明記するのは、軽い依頼が brainstorm に吸い込まれて質問攻めが始まる過剰発火を防ぐためである。
質問への応答が brainstorm の起動提案で始まったら、対象外の破れである。

## 工程は既定で足さない

工程（壁打ち、計画、計画のレビュー、実装の委譲、小ささの判定、レビュー、ループ）は、
どれも別文脈の agent 1 体ぶんの費用を持つ。
その agent はリポジトリと仕様を読み直すので、費用は変更の大きさにほとんど関係なく掛かる。
よって既定はどの工程も足さないことであり、足すには 1 行の理由が要る。
理由が書けない工程は足さない。
宣言してから動き、人の承認は待たない。人は宣言を覆せる。

宣言は次の 3 つのスロットを埋める 1 行である。

```
外に出るか ・ 依存し合う変更箇所の数 ・ 間違いに気づく手段 → 足す工程
```

3 つ目を埋められないこと自体が合図になる。
「気づく手段が無い」と書けたときにはじめて、検査を足すか工程を足すかの判断に進む。
道具の名前は書かせない。この skill は任意のリポジトリで動くので、textlint や特定の検査系の存在を前提にできない。

| 工程 | 足す理由 |
|---|---|
| 壁打ち | 依頼が二通り以上に読め、1〜2 往復で潰せない |
| 計画 | 実装役が一度に持てない量、または途中で人に引き継ぐ |
| 実装の委譲 | メインセッションの文脈を汚したくない量 |
| レビュー | 依存し合う変更箇所が複数あり、実装が自分の中で矛盾しうる |
| ループ | 修正が別の場所へ波及しうる |

レビューを足す理由はこの 1 つだけである。
機械の検査にも差分の一読にも映らないのは、実装が自分の中で矛盾することだけだからである。
1 箇所で閉じる変更、互いに独立した変更、既存の検査が捕まえる間違いには足さない。
reviewer の体数は観点の数で決める。既定は 1 体で、突き合わせる仕様書があり、
機械の検査がその整合を捕まえられないなら、2 体にする。

## 判断に任せない物

次の 3 つは宣言の判断に任せない。
どれも機械の検査か既存の「人を止める 4 つ」で受けるので、工程は増えない。

- 秘密や資格情報に触れる変更は、プロジェクトの検査を通す
- 公開、配布、版に触れる変更は、プロジェクトの検査を通す
- 不可逆な操作、人の権限が要る操作、危険な対象は、「人を止める 4 つ」で止める

レビューはこの 3 つに入れない。
レビューが必ず走る条件は 1 つも無い。
これは、レビューを増やしても正しさは保証されず、抜けはそのまますり抜けるという判断による。
安心感のために体数を増やすことはしない。

抜けたレビューは、人が後から頼める。
宣言の 1 行は、人が「レビューが走っていない」と気づくための材料でもある。
後から頼む道は既にある。review を直接呼ぶ（診断）か、同じブランチで iterate を回し直すかである。
足りなかったと分かった時点で足せるので、先回りして足す必要は無い。

機械の検査が無いリポジトリでは、検査を足せるなら足す。
変更そのものより検査を書くほうが大きくなるなら足さず、宣言の 3 つ目に「気づく手段が無い」と書いて進む。
レビューを機械の検査の代わりにはしない。

「外に出るか」は、リポジトリ固有の文書に頼らず次の 4 つの徴候で見る。

- 公開、配布、版の宣言（package manifest の version、publish の設定、release workflow、tag）
- 資格情報や秘密
- 外部到達（ネットワーク、外部 API、deploy、DB migration）
- 消す変更のうち、消える物の利用者を列挙できない物

5 つ目を足すには、それで事故った実例が要る。

## 入口の規則

既定の入口は次の表で決める。

| 依頼 | 入口 |
|---|---|
| 宣言でどの工程も足さなかった | メインセッションが直接編集する |
| 小さいタスク | iterate |
| 仕様書の無い中くらい以上の変更、判断の根拠が無い、または二通りに読める | brainstorm |
| 仕様書があり、中くらい以上の変更 | plan、続けて cycle |
| 原因の分からない不具合の報告、読み調べないと答えられない疑問 | investigate |

1 行目が既定であり、2 行目以降は宣言が足した工程の分だけ発火する。
小さいタスクの定義は用語集にあり、小さいタスク skill 仕様（`docs/spec/iterate.md`）が決める。
iterate を起動する語も iterate 仕様に従う。裸の「直して」では、人がメインセッションに直接直させる道が残る。
影響が読めない変更、または仕様の判断が要る変更は中くらい以上とする。
文言の指定が無い「エラーメッセージを分かりやすくして」は一通りに読めないので、小さいタスクではなく brainstorm に入る。
仕様書そのものを直す依頼は、plan の行ではなく brainstorm に入る。既存の仕様書のパスを持つ改訂である。
不具合を investigate に入れた先は、investigate の報告の「推奨する次の行動」が次の入口へ繋ぐ。
不具合でも、直す場所と内容が最初から明確で小さいタスクの定義を満たすなら iterate に入れる。
この表は investigate 仕様の「推奨する次の行動」の表と行が重なる。
重なる行は内容を揃え、食い違ったときはこの文書を正とする。
今回の変更では investigate 仕様に触れない。

## 例外

承認済みの手順書や進行中の記録を持つ作業は、brainstorm へ巻き戻さず、続きから入る。
承認済みの手順書がある「実装して」は cycle であり、手実装ではない。
承認済みの手順書がある「実装して」に、メインセッションが手で実装を始めたら反例である。
進行中の brainstorm、cycle、iterate の記録が残る作業は、その記録を使う skill の再開規則に従う。
この表に無い skill は、それ自身の description で発火し、既定の表には落ちない。
このリポジトリに新しい skill を実装したときに入口の規則へ行を足すのは、この文書とリポジトリの維持の決まりであり、skill 本文には写さない。

## 常駐と発火

本文は、毎ターン読まれる常駐を前提とした書き方にする。
常駐のさせ方は環境側の判断であり、skill には hook と script を同梱しない。
README の「常駐のさせ方」節で、AGENTS.md へのポインタ行を主として案内する。

```markdown
## 重要

- 最初に `ba0918-using-workflow` を必ず読み込むこと
```

README は全文が英語なので、節の例示は英語の同等文で書く。
上の日本語の行は、このリポジトリの AGENTS.md に入れる dogfood の文言である。
ポインタ行が効かない環境では本文のインライン展開が確実である、と代替を添える。
ポインタ行の効きは未検証の仮説である。
実測で棄却済みなのは読む時機を書かない「Always」のポインタであり、この文言は時機（最初に）と強制（必ず）を持つ。
その実測は 2026-09-01 の、このリポジトリの 31 本の session ログによる。
AGENTS.md の「Always」行に挙がる skill を読み込んだ session は、4 skill いずれも 31 本のうち 0〜9 本だった。
description には明示起動の語（「どこから始めるか」「入口を決めて」と、英語の同等の語）を置く。

## 作る物

1 つのブランチで作る物は次のとおりで、ブランチと worktree はこのリポジトリに立てる。

- `skills/ba0918-using-workflow/`（`SKILL.md` 単体）と、開発中の skill を読むための `.claude/skills/` の symlink
- `PROJECT.md` の正本の表に `docs/spec/using-workflow.md` の行を足す
- README の「常駐のさせ方」節。ポインタ行を主とし、インライン展開を代替として 1〜2 行で添える
- README の skill の数え上げと Skills の表を、新しい skill を含む形に更新する。plugin manifest の 2 ファイルも同じく更新する。対象は `.claude-plugin/plugin.json` の description と keywords、marketplace.json の description である
- `CHANGELOG.md` の `Unreleased` に `Added` の項目を書く
- `ROADMAP.md` の検討中に setup-workflow の行を足す。形は対話式で、常駐の 3 方式（ポインタ行、インライン展開、hook）から選ばせ、推奨はポインタ行である。再開の条件は、設置や案内が繰り返し面倒だった、または設置で事故った実例が出たときである
- `ROADMAP.md` の検討中に、入口の規則の表と investigate の表の整合を機械化する案を控える。名前参照化と、共有文書にして vendor で配ること（agentic-skill-vendor）の 2 案である。動かす条件は、表を参照する skill が 3 つ以上になったとき、または手動の整合で食い違いの事故が起きたときである
- `ROADMAP.md` に dogfood の控えを足す。控えるのは、main 取り込み後にこのリポジトリの `AGENTS.md` へポインタ行を足すことと、その後の session 群で skill の読み込み率を測ることの 2 つである。前者は行う作業の控えで、後者はやるかをそのとき決める。計測の中身は ROADMAP 側に書き、この文書では定めない
- `evals/cases/ba0918-using-workflow/` に scenario 2 本と、`evals/inputs/ba0918-using-workflow/` にその入力
  - 作る・変える依頼の種別から、表のとおりの入口を答える
  - 質問を対象外と判定し、skill へ送らずそのまま応える

scenario を走らせるかどうかは、人が頼んだときだけ決める。

## 作らない物

- SessionStart hook の同梱
- 本文のインライン展開を配布の前提にすること
- 質問と雑談を brainstorm へ送る既定
- investigate 仕様の変更（表の整合の機械化は ROADMAP の検討中に控える）
- 参照資料（`references/`）
- 用語集の変更（新しい語を導入しない）
- setup-workflow（ROADMAP の検討中に控える）
- `regression-lock.json` のエントリ（scenario を実走したときに skill-regression が書く）
- 読み込み率の計測そのもの（ROADMAP の控えに留め、やるかはそのとき決める）

## 却下した案

- 常駐を description の発火だけに頼ること。ルーティングは skill の発動前の判断であり、description の照合に乗らない。AGENTS.md の「Always」行の遵守は 31 session のうち読み込みが 0〜9 本だった
- hook を skill に同梱して常駐させること。script を持たない縛りと衝突し、Codex での hook 運用には過剰発火の観測がある
- 本文を CLAUDE.md / AGENTS.md へインライン展開して常駐させること。skill に分解した良さが失われる。ポインタ行が効かなかったときの代替としては残す
- 「迷ったら brainstorm」の単一既定（claude-skills 版の写し）。小さいタスクの入口である iterate が死に、質問まで brainstorm に吸い込む
- 用語「漏斗」を仕様と本文で使うこと。「入口の規則」「ルーティング」で足りる
- 入口の規則の表を共有文書にして、vendor で using-workflow と investigate の両方へ配ること。重なりが 3 行と定義の参照だけで、共有文書という新しい成果物の種類の導入に釣り合わない。案は ROADMAP の検討中に条件付きで控える
