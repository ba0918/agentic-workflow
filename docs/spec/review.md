# review の仕様

review は、implement が仕上げた実装を、独立した目で確かめるステップです。
問題を指摘として挙げ、修正のあとは「その指摘が消えたか」だけを確かめ直します。

全体の中での位置と、implement から何を受け取るかは [workflow.md](workflow.md) にあります。
ここでは review の中で何が起きるかを説明します。

この skill は実装済みです。この文書は、その振る舞いについての合意です。

## 何をするステップか

AI にレビューを任せると、レビューのたびに新しい指摘が出てきて、いつまでも終わらない
ことがあります。以前の仕組みでは、7 つの観点ごとに別の AI を並列に走らせ、さらに
2 人目の AI にも毎回意見を求めていたため、同じ入力を最大 8 回読み、修正のたびに指摘が
増え続けて、無人のまま 22 往復した事例がありました。

review は、次の 2 つだけを受け持ちます。

1. **最初のレビュー**: 実装全体を 1 回見て、指摘の集合を作り、固定する
2. **差分の再レビュー**: 修正のあと、未解決の指摘と、それを直した変更だけを見直す

直すこと、直す往復を回すこと、最終的に「取り込んでよい」と判断することは、review の
仕事ではありません。それらは別のステップと人の判断です。

## 受け取るもの

review が読むのは**差分**です。差分を特定できる入力があれば動きます。

| 入力 | 何を見るか |
|---|---|
| ブランチ | そのブランチと、分岐元との差分 |
| 2 つのコミット | その間の差分 |
| implement の実行 ID | その実行のブランチと、始めたコミットからの差分 |

**実行 ID は必須ではありません。**review は、このワークフローを通っていない変更
（人が手で書いたブランチ、外から来た pull request）もレビューできます。実行 ID を渡された
ときだけ、次の追加の確認をします。

- 証拠の最後の出来事が「全手順完了」であること
- 手順書と仕様書の指紋（内容から計算した SHA-256 のハッシュ値。1 バイトでも違えば別の値に
  なります）が、証拠に書かれたものと一致すること。implement が実行を新しい内容へ張り替えて
  いれば（束ね直し）、最後の `rebound` の出来事に書かれた指紋と比べます
- 作業ディレクトリがあり、そのブランチを指していること

食い違えば、指摘を作る前に止まります。実行 ID の無い入力では、これらの確認はしません。
比べる相手が無いからです。その場合、指摘が依拠する仕様書は、人が名前を挙げるか、
リポジトリの `docs/spec/` を既定にします。

会話の記憶で「たぶんこの変更」と決めることはしません。

## 指摘（finding）

指摘 1 件が持つ情報と、「同じ指摘かどうか」の決め方です。核は「指摘の ID は、確かめ方から
作る」です。修正で行番号がずれても、同じ確かめ方なら同じ指摘として扱えます。

| 項目 | 意味 |
|---|---|
| ID | 確かめ方から機械的に導いた、変わらない ID |
| 重さ（severity） | `security`（安全上の問題）、`critical`（致命的）、`warn`（直したほうがよい）、`info`（記録のみ） |
| 対応（action） | `auto_fix`（人に聞かず直す）、`fix_and_verify`（直して確かめる）、`human_judgment`（人が決める）、`record_only`（記録だけ） |
| 根拠となる仕様 | 影響する仕様書のパスと節 |
| 証拠 | 観測したファイル、行の範囲、出力の要約 |
| 確かめ方 | 直ったかを機械的に判定する手段（テスト名やコマンド）。人が決める指摘の場合は、なぜ機械で確かめられないかの理由 |
| 根本原因のキー | 同じ原因の指摘をまとめて示すための分類 |
| 状態 | `open`（未解決）、`closed`（解決した、または人が直さないと決めた）、`stale`（前提が古くなった）、`deferred`（後回しの候補へ送った） |
| 依拠した仕様の指紋 | どの版の仕様書で判断したか |
| 観点 | どの観点の一覧から出た指摘か |

### 重さと対応は別

重さから対応を自動で決めることも、その逆もしません。`info` の対応は `record_only` だけです。

`info` は記録だけで終わる観察なので、直ったことを確かめる手段を求めません。確かめ方も、
なぜ確かめられないかの理由も要りません。直す対象でないものに「直ったかを判定する方法」は
存在しないからです。`info` の指摘は、集合を固定した時点で `closed` になります。

### 確かめ方を先に書く

レビュアーは、全部の指摘について、まず機械的な確かめ方を書こうとします。書けない理由を
記録したときだけ `human_judgment`（人が決める）にできます。「書くのが面倒」は理由に
なりません。`warn` の確かめ方は、既存のテストの再実行や静的検査でかまいません。新しいテストを
書くことは求めません。

人が決める指摘以外は、指摘を作った時点で、その確かめ方が「いまは失敗する」ことを確認して
記録します。最初から通る確かめ方を持つ指摘は、「直した」ことにならないまま素通りしてしまう
ので、固定する集合に入れません。

### 人が決める指摘

人が決める指摘も固定する集合に入れますが、機械的には閉じません。人の判断を記録したときだけ
`closed` になります。人が決める指摘は 1 往復ごとにまとめて示し、1 件ずつ質問はしません。

機械で確かめる指摘についても、人は「直さない」と決められます。決めた結果と理由を記録した
ときだけ、その指摘は `closed` になります。この判断は、指摘の集合を固定したあと、開いている
指摘にだけ使えます。固定する前に不都合な指摘を消す抜け道にしないためです。却下した指摘は、
そのあと確かめ方が通っても状態を変えません。人の判断を機械が上書きしないためです。

### 同じ原因はまとめる

同じ根本原因の指摘は、1 つの修正単位としてまとめて示します。まとめるのは見せ方だけで、
各指摘の ID と確かめ方は個別に持ちます。

## 誰がレビューするか（モデル）

レビューの深さは、レビューする AI のモデルの能力で決まります。能力の低いモデルでは、
安全上の問題や設計の矛盾のような深い指摘は出ません。また、作業全体を回している AI
（オーケストレータ）と同じモデルでそのままレビューすると、同じ見落としを繰り返す可能性が
あります。レビューは、上位のモデルで行うのが望ましいです。強制はしませんが、どのモデルが
レビューしたかは必ず記録します。

### 指定の仕方

| 指定 | 意味 |
|---|---|
| `--model=<モデル ID>` | 最初のレビューを行うモデル |
| `--second-reviewer=<実行先>` | 2 人目のレビュアーの実行先（Codex など） |
| `--second-model=<モデル ID>` | 2 人目のレビュアーのモデル |

モデル ID は完全な ID（例: `claude-fable-5`）で書きます。`opus` のような別名は、世代が
複数あるとどれを指すか決まらないので使いません。

いまの会話と違うモデルを指定したときは、review はそのモデルで新しい会話（サブエージェント）を
立て、そこでレビューを行わせます。いまの会話の AI がそのまま行うのは、指定が無いときだけです。

### 自走時にモデルを決める順序

review を起動するのは、人ではなく、作業全体を回している AI であることがほとんどです。
そのとき人に毎回聞かなくて済むように、モデルは次の順で決めます。

1. 起動時の明示の指定（`--model` など）
2. プロジェクトの指示（AGENTS.md や PROJECT.md に「レビューに使うモデル」が書いてあれば、それ）
3. 利用者の規則（たとえば、役割ごとのモデルを決めた利用者の常駐規則）
4. どれにも無ければ、いまの会話の AI

どの段階で決まったかと、実際にレビューしたモデルを、指摘の集合の記録に残します。
skill の本体に特定のモデル名は書きません。モデルの選び方は利用者とプロジェクトの側で
決めるものだからです。

## 最初のレビュー

上で決まったモデルのレビュアー 1 人が、選ばれた観点の一覧を 1 回だけ回します。
観点ごとに別の AI を立てたり、観点ごとに入力を読み直したりしません。

### 読む範囲は重さの候補で変える

- `security` と `critical` の候補: 変更の差分に加えて、差分が触った関数などを直接呼んでいる
  場所（1 段だけ、作業ディレクトリの中）と、影響する仕様書の節まで読む。呼んでいる場所は
  候補が立ってから読み、先読みしない
- `warn` の候補: 差分だけ
- `info`: 記録だけ。追加で読まない

入力が大きすぎるとき（閾値は運用で決める）は、自動で分割せずに止まって人に返します。
分割は手順書の粒度の問題で、review が解くことではありません。

### 安全上の確認は必須

安全上の確認は、観点の一覧の中の必須項目として同じレビュアーが行います。終えられないときは、
review 全体を「未完了で再開できる」状態で止め、成功とは言いません。

### 強さは 2 段階、人が選ぶ

`--level=light|standard` で強さを指定できます。既定は `standard`。`light` は `security` と
`critical` の候補だけを探し、`warn` と `info` は集めません。確かめ方が必須であること、
安全上の確認が必須であること、差分の再レビューの約束は、強さで変わりません。

変更の行数から強さを自動で選ぶことはしません。認可の判定を 1 行変えるのがいちばん危ない、
というように、行数は影響の大きさの代わりにならないからです。レビュアーは「`light` で
足りそう」と提案してよいですが、決めるのは人です。

### 指摘の集合を固定する

最初のレビューが終わったら、指摘の集合を 1 つの出来事として記録し、その指紋を以後の
差分の再レビューの入力にします。

## 観点の一覧（profile）

何を見るかの一覧は、skill の本体から切り離した文章ファイル（`references/profile/`）に
置きます。

| ファイル | 対象 | 観点 |
|---|---|---|
| `default.md` | 一般のコード | 正確性、安全、性能とメモリ、設計、網羅性、仕様との一致、画面がある場合の使い勝手 |
| `skill.md` | skill の文書（SKILL.md、補足、補助スクリプト） | 以前の skill-reviewer の観点に加えて、**ステップ間の受け渡し**（各ステップが workflow.md の「受け渡す物」の約束を守っているか） |
| `document.md` | 説明の文書（README、仕様書、利用者向けの文書） | 変更したコードの振る舞いと、それを説明している文書が食い違っていないか。消えた関数やコマンドを指したままの記述、変わった既定値の書き残し、増えた選択肢の書き漏れ |

- 各ファイルは、担当するファイルの種類、観点の一覧、重さの判定基準、許される確かめ方の
  種類、`light` でも回す項目を、自分で宣言します
- skill の本体は、選ばれた観点の一覧だけを読みます。全部を先読みしません
- 観点の一覧は、差分のファイルの種類から自動で選び、`--profile` で上書きできます。種類が
  混ざった差分では、該当する一覧をファイルの集合ごとに当て、指摘の集合は 1 つに保ちます
- 観点の一覧を足しても、本体と補助スクリプトは変えません
- 観点の一覧は文章だけで副作用が無いので、専用のテストや実測は要求しません。過不足は
  使いながら見つけて、そのファイルだけ直します

`skill.md` に「ステップ間の受け渡し」の観点を入れるのは、skill を 1 つずつ見ても継ぎ目の
ズレは見つからなかった、という経験からです。

実装と文書のずれを見つけることを、独立したステップにはしません。その出力（ずれの一覧）は
review の出力（指摘の集合）と同じ形なので、ステップを分けても新しい情報が増えず、継ぎ目が
1 つ増えるだけだからです。観点の一覧に 1 つ足せば済みます。

## 差分の再レビューと収束

修正のあとは、全部を読み直しません。

- 入力は、未解決の指摘、その指摘の ID をコミットメッセージの末尾（trailer。`Key: value` 形式の
  行）に書いた修正コミットの差分、影響する証拠、修正が新たに持ち込んだリスク、だけ
- 修正した側の「直しました」という報告は読みません。各指摘の確かめ方を自分で走らせて、
  通ったら `closed`、まだ失敗するなら `open` のまま
- 再レビュー中に見つけた別の問題（`warn` を含む）は、今回の合否に混ぜず、`deferred`（後回しの
  候補）として分けます。修正が新たに持ち込んだリスクだけは、新しい指摘として集合に足せます
- 指摘の ID を trailer に持たないコミットが修正に混ざっていたら、関連する差分を推測で補わず、
  範囲外として拒否します
- 承認された範囲の外を触らないと閉じられない指摘は、人が決める指摘（`human_judgment`）に
  します。指摘のテキストは AI が書いた物なので、それを根拠に範囲を広げません。範囲を広げて
  よいか、別の作業に送るかは人が決めます。指摘そのものを落とすことはしません
- 固定した集合が依拠した仕様書が、その後に改訂されていたら、指摘を閉じずに `findings_stale`
  （指摘の前提が古くなった）として止め、人に返します。これは終端ではありません。人が改訂後の
  仕様書で束ね直す（`rebound` の出来事を記録する）と、`stale` になった指摘は全部 `open` に
  戻り、要らない物は理由つきの却下か保留で人が閉じます。参照する節の文面で選り分けることは
  しません。新しく始めることもできます
- 作業ディレクトリに、最初のレビューで見た範囲の未コミット変更があれば、再レビューを拒否
  します（修正はコミットで渡す約束です）。その範囲の外の未コミット変更は事実として記録する
  だけで、拒否の理由にしません

### 収束の仕組み

指摘の集合は有限で、再レビューでは新しい指摘を足さないので、往復は必ず終わります。
同じ指摘の確かめ方が何度直しても通らないときは、「収束しない」ではなく「直せていない」
として人が決める指摘に格上げし、人に返します。人が理由を記録して「直さない」と決めた指摘も
閉じます。

**review の側は、往復の回数で打ち切りません。**収束は構造で保証されているので、回数は
review が判定に使う値ではないからです。往復を回す側（[cycle.md](cycle.md)）は上限を
持ちますが、それは収束の手段ではなく「そこまで直して閉じないなら、どこかが壊れている」
という診断のシグナルです。

最初のレビューをもう一度全部やり直す候補になるのは、修正コミットが最初のレビューで見た
ファイルの外を触ったときだけです。候補になっても自動では再実行せず、人に上げて理由を
記録します。

## 仕上げのレビューと 2 人目のレビュアー

- **仕上げのレビュー**: 新しい目で全部を見直したいとき、人がその場で頼んだときだけ、
  新しい会話の AI による全体レビューを 1 回追加できます。結果は固定した集合に合流させ、
  そこからは差分の再レビューで閉じます。自動で繰り返しません
- **2 人目のレビュアー**: 別の AI（Codex など）の意見は、`--second-reviewer`（と
  `--second-model`）の明示の指定があるときだけ、最初のレビューに 1 回だけ並走させます。許可を持ち越さず、自動で
  やり直しません。使えないときは警告を記録して、1 人のレビューだけで続けます。渡すのは
  手順書の内容と差分だけで、ソースファイル全体は渡しません。渡す前に秘密情報が無いか
  走査し、自分のレビュー結果や結論は渡しません。実行先は差し替え可能にし、特定の
  サービスを仕様で固定しません

## 直す側との約束

直す側は、往復を回す [cycle.md](cycle.md) が委譲した会話です。人が直接直すこともあります。
指摘の集合の形と次の約束は、直す側が誰でも同じです。review 自身が直すことだけはしません。
指摘を出した本人が直して本人が確認すると、独立した目という review の存在意義が消えるからです。

- 指摘の集合は review だけが書く、変えないファイルです。直す側は読むだけで、状態を書き換えません
- 直す側は、修正コミットの trailer に対象の指摘の ID を書きます。review はコミット履歴の
  trailer から、関連する差分を機械的に計算します
- 直す側が修正中に見つけた別の問題は、指摘の集合ではなく、後回しの候補として別ファイルに書きます
- 直す側が修正中に仕様の不足を見つけたら、仕様書の改訂は brainstorm に戻し、review は
  `findings_stale` で止まります。改訂後に束ね直せば、そこから続きます

## 記録の置き場所

review の記録は、implement の証拠と同じ実行の下に、同じ「1 件 1 ファイル、追記のみ」の
方式で置きます。実行 ID を持たない入力（ブランチや差分だけ）をレビューしたときは、
`.agents/evidence/reviews/<レビュー ID>/` に同じ形で置きます。記録の形は同じで、
implement の証拠を参照する部分だけがありません。

- `.agents/evidence/<手順書 ID>/<実行 ID>/review/`: 指摘の集合と、往復ごとの判定
- implement の出来事の列には書き足しません。review は自分の連番を持ち、最初の出来事で
  implement の最後の出来事の指紋を参照します
- 指摘の開閉は追記で表し、固定した集合のファイルは上書きしません
- 束ね直し（`rebound`）も review の記録に追記します。以降の指紋の検査は、その出来事に書いた
  指紋で行います。`findings_stale` は終端の出来事ではなく、そのあとに `rebound` を追記できます
- review の完了は、固定した集合の全指摘が `closed`、`stale`、`deferred` のどれかになったこと
  から導きます。完了を表す出来事は書きません。完了した review がある実行に対して review を
  始めようとしたときは、「進行中」ではなく「完了済み」として扱います
- 同じ実行に対して、2 つの review を同時に走らせません。review の記録ディレクトリが
  すでにあって終わっていなければ、人に見せて確認します。リポジトリ全体に 1 つの「使用中」の
  印は置きません
- `.agents/evidence/reviews/` は人向けの報告の置き場で、機械が読む記録ではありません
- 実行の全出力や外部サービスのログは記録に複製しません。秘密情報、個人情報、内部の
  ホスト名も記録しません

## 人が判断する場面

| 場面 | 人が決めること |
|---|---|
| 人が決める指摘 | 1 往復ごとにまとめて、それぞれを受け入れるか |
| 機械で確かめる指摘を直さないと決める | 理由を記録して閉じるか |
| 指摘の前提が古くなった（`findings_stale`） | 仕様書を改訂して束ね直すか、新しく始めるか。束ね直しで `open` に戻った指摘の却下・保留 |
| 安全上の確認が終えられない | どうするか（review は未完了のまま止まる） |
| 何度直しても通らない指摘 | 受け入れるか、別の方法を取るか |
| 全体レビューのやり直しの候補 | やり直すか |
| 強さ（`light` / `standard`）と 2 人目のレビュアー | 使うか（その場で、1 回だけ） |
| レビューのモデル | プロジェクトの指示や利用者の規則で決めておくか、起動時に指定するか |

## 失敗したときの動き

- 必要な人、証拠、作業ディレクトリ、確かめ方を実行する環境が無いときは、成功と言わず、
  未完了で再開できる状態を残します
- 拒否や停止のあとも、指摘の集合のファイルは消しません
- 確かめ方のコマンドは作業ディレクトリの中で実行し、絶対パス、作業ディレクトリの外への
  書き込み、認証情報を含むコマンドは拒否します

## やらないこと

- 直さない。直す往復を回さない。直す役を呼ばない
- 最終判断、メインのブランチへの取り込み、公開、作業ディレクトリの掃除をしない
- 手順書の本文、状態ファイル、セッションの履歴を更新しない
- `info` の指摘を自動で直さない
- 頼まれていない 2 人目のレビュアーを動かさない
- Claude Code 組み込みの `/code-review` や公式プラグインに最初のレビューを委ねない
  （AI の種類によって存在せず、品質がぶれ、指摘の ID と限定した再レビューを持たないため）
