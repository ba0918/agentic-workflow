# review の仕様

review は、implement が仕上げた実装を、独立した目で確かめるステップです。
最初と最後に実装全体を見て、その間の修正後は未解決の指摘と修正差分へ範囲を絞ります。

全体の中での位置と、implement から何を受け取るかは [workflow.md](workflow.md) にあります。
ここでは review の中で何が起きるかを説明します。

この文書は、review が満たす振る舞いについての合意です。実装が追従中の箇所も含みます。

## 何をするステップか

AI にレビューを任せると、レビューのたびに新しい指摘が出てきて、いつまでも終わらない
ことがあります。以前の仕組みでは、7 つの観点ごとに別の AI を並列に走らせていました。
さらに 2 人目の AI にも毎回意見を求めたため、同じ入力を最大 8 回読んでいました。その結果、
修正のたびに指摘が増え続け、無人のまま 22 往復した事例があります。

review は、次の 3 つを受け持ちます。

1. 最初の全体レビューでは、実装全体を 1 回見て、指摘の集合を作ります
2. 差分の再レビューでは、修正のあと、未解決の指摘と、それを直した変更だけを見直します
3. 最終全体レビューでは、未解決の指摘が無くなったあと、新しい目で実装全体をもう 1 回だけ見ます

直すこと、直す往復を回すこと、最終的に「取り込んでよい」と判断することは、review の
仕事ではありません。それらは別のステップと人の判断です。

## 受け取るもの

review が読むのは**差分**です。差分を特定できる入力があれば動きます。

| 入力 | 何を見るか |
|---|---|
| ブランチ | そのブランチと、分岐元との差分 |
| 2 つのコミット | その間の差分 |
| implement の実行 ID | その実行のブランチと、始めたコミットからの差分 |

**実行 ID を必須としません。** このワークフローを通っていない変更
（人が手で書いたブランチ、外から来た pull request）もレビューできます。実行 ID を渡された
ときだけ、次の追加の確認をします。

- 証拠の最後の出来事が「全手順完了」であること
- 手順書と仕様書の現在の内容が、実行を束ねた Git コミットにある内容とどう違うか。implement が
  新しい内容へ追従（`recovering`）または束ね直し（`rebound`）していれば、その最後の出来事が
  指すコミットを使います
- 作業ディレクトリがあり、そのブランチを指していること

実行 ID を渡した review では、実際に走らせた操作として記録できるものの出所も 1 つ増えます
（下の「確かめ方の出所」）。

食い違えば、指摘を作る前に止まります。実行 ID の無い入力では、これらの確認はしません。
比べる相手が無いからです。その場合、指摘が依拠する仕様書は、人が名前を挙げるか、
リポジトリの `docs/spec/` を既定にします。

会話の記憶で「たぶんこの変更」と決めることはしません。

ブランチだけを渡された場合、分岐元は明示された比較先、pull request の取り込み先、
リポジトリの既定ブランチとの merge-base の順で決めます。既定ブランチを一意に決められない
ときは、誤った差分をレビューしないため、比較先を人に聞いてから始めます。

## 指摘（finding）

指摘 1 件が持つ情報と、「同じ指摘かどうか」の決め方です。核は「指摘の ID は、確かめ方から
作る」です。修正で行番号がずれても、同じ確かめ方なら同じ指摘として扱えます。

| 項目 | 意味 |
|---|---|
| ID | 確かめ方から機械的に導いた、変わらない ID |
| 重さ（severity） | `security`（安全上の問題）、`critical`（致命的）、`warn`（直したほうがよい）、`info`（記録のみ） |
| 対応（action） | `auto_fix`（人に聞かず直す）、`fix_and_verify`（直して確かめる）、`human_judgment`（人が決める）、`record_only`（記録だけ） |
| 根拠となる仕様 | 影響する仕様書のパスと節 |
| 証拠 | 観測したファイル、行の範囲、出力の要約 |
| 確かめ方 | 直ったかを機械的に判定する手段（テスト名やコマンド）。人が決める指摘の場合は、なぜ機械で確かめられないかの理由 |
| 根本原因のキー | 同じ原因の指摘をまとめて示すための分類 |
| 状態 | `open`（未解決）、`closed`（解決した、または人が直さないと決めた） |
| 依拠した仕様の版 | どの Git コミットにある仕様書で判断したか |
| 観点 | どの観点の一覧から出た指摘か |

### 重さと対応は別

重さから対応を自動で決めることも、その逆もしません。`info` の対応は `record_only` だけです。

`info` は記録だけで終わる観察なので、直ったことを確かめる手段を求めません。確かめ方も、
なぜ確かめられないかの理由も要りません。直す対象でないものに「直ったかを判定する方法」は
存在しないからです。`info` の指摘は、集合を固定した時点で `closed` になります。

### 確かめ方を先に書く

指摘に記録する確かめ方は、直ったことを判定するための**提案**です。文字列をそのまま実行してよい
命令ではありません。後のレビュアーは、指摘の意図と現在の作業ディレクトリを読み、自分で安全な
操作へ組み立て直してから実行します。ローカルなテスト、読み取りだけの検査、静的検査は人へ
聞かずに走らせます。絶対パスや作業ディレクトリ外への書き込みを含む提案は、そのまま実行しません。
不可逆な操作、外部公開、認証情報を使う操作も同様です。同じ判定を安全に行える方法へ置き換えます。安全な
代替がなく、人の権限や判断が本当に必要なときだけ `human_judgment` にします。

レビュアーは、全部の指摘について、まず機械的な確かめ方を提案します。書けない理由を記録した
ときだけ `human_judgment`（人が決める）にできます。「書くのが面倒」は理由になりません。
`warn` の確かめ方は、既存のテストの再実行や静的検査でかまいません。新しいテストを書くことは
求めません。

人が決める指摘以外は、指摘を作った時点で、その確かめ方が「いまは失敗する」ことを確認して
記録します。最初から通る確かめ方を持つ指摘は、「直した」ことにならないまま素通りしてしまう
ので、固定する集合に入れません。

### 確かめ方の出所

レビュアーは差分の再レビューで、指摘を閉じたときも、まだ失敗したときも、「実際に走らせた
操作」を記録します。補助スクリプト（この文書では runtime と呼びます）は、その操作が次の 2 つの
出所のどちらかに当てはまることを確かめます。どちらにも当てはまらない操作は記録できません。

1. runtime が持つ固定の一覧。作業ディレクトリの中で完結するテストの実行、読み取りだけの Git
   操作、静的検査など、対象を書き換えない操作だけを含みます
2. implement の実行 ID を渡された review に限り、承認コミットにある手順書の `**Checks:**`
   （[plan.md](plan.md) の「完了の示し方」）に書かれたコマンド。承認コミットは、review が実行を
   束ねたときに使う物です（追従や束ね直しがあれば、その最後の出来事が指すコミット。「受け取る
   もの」と同じ）。手順書のどの手順に書かれたものでもかまいません。指摘と手順の対応は求めません。書かれた文字列と、
   前後の空白を除いて 1 文字も違わず一致するものだけです。引用符の付け方や語間の空白が違えば、
   同じ意味でも一致しません

2 を加えるのは、手順書が選んだ検査（このリポジトリなら品質ゲート）と同じ判定で指摘を閉じられる
ようにするためです。固定の一覧に無い検査を確かめ方にした指摘は、別の判定へすり替えるか、理由の
無いまま人が決める指摘にするしかなく、どちらも「確かめ方を先に書く」に反します。

手順書の検査を信頼する根拠は、implement と同じです。手順書は人が承認し Git に固定した文書で、
implement もその `**Checks:**` をそのまま走らせます。照合に使うのは承認コミットの内容であって、
作業ディレクトリにある手順書ではありません。作業ディレクトリの手順書を書き換えれば記録できる操作が
広がる、という抜け道を作らないためです。指摘に書かれた確かめ方の文字列も、この出所には含めません。
指摘は信頼しない入力だからです。

手順書の `**Checks:**` には、生成した複製を同期し直すコマンドのように、作業ディレクトリを
書き換えるものも書けます。review はレビュー対象を編集しないので、そうしたコマンドは選びません。
どのコマンドが対象を書き換えるかは runtime では判定できないため、選ばない責任はレビュアーの
「安全な操作へ組み立て直す」義務に含めます。runtime は、記録する操作が上の 2 つの出所のどちらかに
あることを確かめます。絶対パス、作業ディレクトリの外、シェルの連結や書き出しを含む文字列を
拒否する検査は、出所にかかわらずこれまでどおり掛かります。手順書の `**Checks:**` にそうした
文字列があっても、review では記録できません。それを選ばない責任も、書き換えを伴う検査と同じく
レビュアーの義務です。

実行 ID の無い入力（ブランチ、2 つのコミット）には手順書が無いので、固定の一覧だけを使います。
`PROJECT.md` の検査コマンドの一覧は、人の承認記録ではないため出所にしません。固定の一覧に、
そのリポジトリにしか無い検査（このリポジトリの品質ゲートのように、リポジトリ内のパスを名指しする
検査）を書くこともしません。runtime は複数のプロジェクトへ配布するものだからです。

この節が守られているかは、次で判定できます。

- 実行 ID を渡した review で、承認コミットの手順書の `**Checks:**` にあるコマンドを、閉じた
  ときの操作としても、まだ失敗したときの操作としても記録できる
- 固定の一覧に無いコマンドは、作業ディレクトリの手順書にだけ書き足しても、指摘の確かめ方に
  だけ書いても、実行 ID の無い review でも記録できない
- 固定の一覧にある操作は、これまでどおり記録できる
- 絶対パスやシェルの連結を含む文字列は、手順書の `**Checks:**` にあっても記録できない

### 人が決める指摘

人が決める指摘も集合に入れますが、機械的には閉じません。重要な設計判断、不可逆な操作、
人の権限、安全上または致命的な問題で人の判断が必要な場合だけ途中で人へ返します。それ以外の
主観的な改善案は `info` として終端報告へ送り、往復の途中で人を止めません。

機械で確かめる指摘についても、人は「直さない」と決められます。決めた結果と理由を記録した
ときだけ、その指摘は `closed` になります。この判断は、指摘の集合を固定したあと、開いている
指摘にだけ使えます。固定する前に不都合な指摘を消す抜け道にしないためです。却下した指摘は、
そのあと確かめ方が通っても状態を変えません。人の判断を機械が上書きしないためです。

### 同じ原因はまとめる

同じ根本原因の指摘は、1 つの修正単位としてまとめて示します。まとめるのは見せ方だけで、
各指摘の ID と確かめ方は個別に持ちます。

## 誰がレビューするか（モデル）

レビューの深さは、レビューする AI のモデルの能力で決まります。能力の低いモデルでは、
安全上の問題や設計の矛盾のような深い指摘は出ません。また、作業全体を回している AI
（オーケストレータ）と同じモデルでそのままレビューすると、同じ見落としを繰り返す可能性が
あります。レビューは、上位のモデルで行うのが望ましいです。強制はしませんが、どのモデルが
レビューしたかは必ず記録します。

### 指定の仕方

| 指定 | 意味 |
|---|---|
| `--model=<モデル ID>` | 最初のレビューを行うモデル |
| `--second-reviewer=<実行先>` | 2 人目のレビュアーの実行先（Codex など） |
| `--second-model=<モデル ID>` | 2 人目のレビュアーのモデル |

モデル ID は完全な ID（例: `claude-fable-5`）で書きます。`opus` のような別名は、世代が
複数あるとどれを指すか決まらないので使いません。

いまの会話と違うモデルを指定したときは、review はそのモデルで新しい会話（サブエージェント）を
立て、そこでレビューさせます。いまの会話の AI がそのまま行うのは、指定が無いときだけです。

### 自走時にモデルを決める順序

review を起動するのは、人ではなく、作業全体を回している AI であることがほとんどです。
そのとき人に毎回聞かなくて済むように、モデルは次の順で決めます。

1. 起動時の明示の指定（`--model` など）
2. プロジェクトの指示（AGENTS.md や PROJECT.md に「レビューに使うモデル」が書いてあれば、それ）
3. 利用者の規則（たとえば、役割ごとのモデルを決めた利用者の常駐規則）
4. どれにも無ければ、いまの会話の AI

どの段階で決まったかと、実際にレビューしたモデルを、指摘の集合の記録に残します。
skill の本体に特定のモデル名は書きません。モデルの選び方は利用者とプロジェクトの側で
決めるものだからです。

## 最初のレビュー

上で決まったモデルのレビュアー 1 人が、選ばれた観点の一覧を 1 回だけ回します。
観点ごとに別の AI を立てたり、観点ごとに入力を読み直したりしません。

### 仕様要求と検証の対応を確かめる

planを伴うreviewでは、承認済み仕様節、planの`Verification coverage`、各Stepの検証portfolioを
順に辿ります。続いてimplementのevidenceと実装差分を確認します。runtimeによる
「対応の存在と実行の成功」という保証だけで、仕様適合を結論にしません。

reviewは次を意味として判断します。

- 関連する仕様書や要求節がcoverageから漏れていない
- 節の中にある各要求がいずれかのStepと直接検証で覆われている
- 直接検証は、仕様に書かれた反例が実装にあれば失敗する
- unit、integration、E2E、PBT、静的検査、artifact、externalの選択が対象に合う
- 補助検証だけを仕様適合の証拠にしていない
- planに宣言した検証portfolioをexisting evidenceが覆い、実装がtestをすり抜けていない

不足は通常のfindingとして固定し、仕様の意味を変えず既存の依存、環境、承認範囲で直せるtestや
checkの不足はcycleの修正へ渡します。要求の意味、判定基準、新しい依存、外部環境、権限が必要な
不足はhuman judgmentとしてbrainstormへ返します。

### 読む範囲は重さの候補で変える

- `security` と `critical` の候補: 変更の差分に加えて、差分が触った関数などを直接呼んでいる
  場所（1 段だけ、作業ディレクトリの中）と、影響する仕様書の節まで読む。呼んでいる場所は
  候補が立ってから読み、先読みしない
- `warn` の候補: 差分だけ
- `info`: 記録だけ。追加で読まない

入力が大きいこと自体は、人へ返す理由にしません。まず、候補が立った箇所だけ直接の呼び出し元を
読む、仕様節を対象ごとに読むなど、意味を失わない安全な方法で入力を絞ります。それでもレビュー
できなければ、原因を診断して別の安全な読み方を 1 回試します。その方法でも判断できないときだけ、
読めなかった範囲と理由を添えて人へ返します。保存した記録を削ることで入力を小さくはしません。

### 安全上の確認は必須

安全上の確認は、観点の一覧の中の必須項目として同じレビュアーが行います。終えられないときは、
review 全体を「未完了で再開できる」状態で止め、成功とは言いません。

### 強さは 2 段階、人が選ぶ

`--level=light|standard` で強さを指定できます。既定は `standard`。`light` は `security` と
`critical` の候補だけを探し、`warn` と `info` は集めません。確かめ方が必須であること、
安全上の確認が必須であること、差分の再レビューの約束は、強さで変わりません。

変更の行数から強さを自動で選ぶことはしません。認可の判定を 1 行変えるのがいちばん危ない、
というように、行数は影響の大きさの代わりにならないからです。レビュアーは「`light` で
足りそう」と提案してよいですが、決めるのは人です。

### 最初の指摘の集合を記録する

最初のレビューが終わったら、指摘の集合を 1 つの出来事として記録します。集合は上書きしません。
修正が新しい問題を持ち込んだ場合は、追加の出来事として新しい指摘を足します。出来事や集合を
独自の指紋でつなぎません。

## 観点の一覧（profile）

何を見るかの一覧は、skill の本体から切り離した文章ファイル（`references/profile/`）に
置きます。

| ファイル | 対象 | 観点 |
|---|---|---|
| `default.md` | 一般のコード | 正確性、安全、性能とメモリ、設計、網羅性、仕様との一致、画面がある場合の使い勝手 |
| `skill.md` | skill の文書（SKILL.md、補足、補助スクリプト） | 以前の skill-reviewer の観点に加えて、**ステップ間の受け渡し**（各ステップが workflow.md の「受け渡す物」の約束を守っているか） |
| `document.md` | 説明の文書（README、仕様書、利用者向けの文書） | 変更したコードの振る舞いと、それを説明している文書が食い違っていないか。消えた関数やコマンドを指したままの記述、変わった既定値の書き残し、増えた選択肢の書き漏れ |

- 各ファイルは、担当するファイルの種類、観点の一覧、重さの判定基準を宣言します。許される
  確かめ方の種類と、`light` でも回す項目も自分で宣言します
- skill の本体は、選ばれた観点の一覧だけを読みます。全部を先読みしません
- 観点の一覧は、差分のファイルの種類から自動で選び、`--profile` で上書きできます。種類が
  混ざった差分では、該当する一覧をファイルの集合ごとに当て、指摘の集合は 1 つに保ちます
- 観点の一覧を足しても、本体と補助スクリプトは変えません
- 観点の一覧は文章だけで副作用が無いので、専用のテストや実測は要求しません。過不足は
  使いながら見つけて、そのファイルだけ直します

`skill.md` に「ステップ間の受け渡し」の観点を入れるのは、skill を 1 つずつ見ても継ぎ目の
ズレは見つからなかった、という経験からです。

実装と文書のずれを見つけることを、独立したステップにはしません。その出力（ずれの一覧）は
review の出力（指摘の集合）と同じ形なので、ステップを分けても新しい情報が増えず、継ぎ目が
1 つ増えるだけだからです。観点の一覧に 1 つ足せば済みます。

## 差分の再レビューと収束

修正のあとは、全部を読み直しません。

- 入力は、未解決の指摘、その指摘の ID をコミットメッセージの末尾（trailer。`Key: value` 形式の
  行）に書いた修正コミットの差分、影響する証拠、修正が新たに持ち込んだリスク、だけ
- 修正した側の「直しました」という報告は読みません。各指摘の確かめ方を自分で走らせて、
  通ったら `closed`、まだ失敗するなら `open` のまま
- 修正が新たに持ち込んだ問題は、新しい指摘として集合へ足します。偶然見つけた無関係な
  `warn` と `info` は、今回の合否に混ぜず、終端報告へ送る観察として分けます。安全上または
  致命的な問題は、既存か新規かに関係なく今回の指摘へ含めます
- 指摘の ID を trailer に持たないコミットが修正に混ざっていたら、関連する差分を推測で補わず、
  範囲外として拒否します
- 手順書の予定範囲の外を触らないと閉じられない場合も、範囲外という理由だけで人へ返しません。
  大筋を変えない通常の補完なら、理由を記録して修正できます。重要な設計判断、新しい外部依存、
  本番設定やデータ移行など危険な対象が必要なら、人が決める指摘にします
- 指摘の依拠する仕様書が改訂されていたら、AI が新旧の内容を読みます。重要な設計判断が動いて
  いなければ、新しい Git の版へ自動で追従して続け、変更内容を終端で報告します。重要な判断が
  動いていた場合だけ `findings_stale`（指摘の前提が古くなった）として止め、人へ返します。
  `findings_stale` は完了ではありません。束ね直すと未解決の指摘を `open` のまま再開します
- 作業ディレクトリに、最初のレビューで見た範囲の未コミット変更があれば、再レビューを拒否
  します（修正はコミットで渡す約束です）。その範囲の外の未コミット変更は事実として記録する
  だけで、拒否の理由にしません

### 収束の仕組み

未解決の指摘を、重さごとに `security`、`critical`、`warn` の順で数えます。修正前後の件数を
この順で比べ、最初に違う件数が小さくなることを進捗とします。たとえば、`security` が 1 件
減れば `warn` が増えても進捗ですが、同じ重さの問題へ置き換わっただけなら進捗ではありません。

**往復の回数では打ち切りません。** この件数の組は無限に小さくなれないので、進捗が続く限り
往復は終わります。小さくならなかった場合は、編集を続けず、指摘、実装、仕様、道具のどこで
詰まったかを診断します。診断で選んだ方法による次の修正でも小さくならなければ、人の判断が
必要な状態として返します。

修正が最初のレビューで見たファイルの外へ広がっても、それだけでは止めません。対象範囲の
構造、前提、依存、手順の順序、完了条件、または依拠する仕様が動いたなら、差分だけでは影響を
判断できないため全体レビューへ戻ります。通常の補完なら、関連する指摘と差分の再レビューを
続け、最終全体レビューで全体への影響を確かめます。

## 最終全体レビューと 2 人目のレビュアー

- 最終全体レビューでは、最初のレビューで作った未解決の指摘が無くなったら、新しい会話の AI が
  実装全体を 1 回だけ見直します。これは必須です。見つけた指摘は集合へ追加し、そこからは
  差分の再レビューで閉じます。この追加された集合を、以降の進捗比較の新しい起点にします。
  追加で件数がゼロから増えたこと自体は非進捗と判定せず、その後の修正前後を比較します。
  最終全体レビューをもう一度繰り返しません
- 2 人目のレビュアーとして別の AI（Codex など）を使うのは、`--second-reviewer` と
  `--second-model` の明示の指定があるときだけです。最初のレビューに 1 回だけ並走させます。許可を持ち越さず、自動で
  やり直しません。使えないときは警告を記録して、1 人のレビューだけで続けます。渡すのは
  手順書の内容と差分だけで、ソースファイル全体は渡しません。渡す前に秘密情報が無いか
  走査し、自分のレビュー結果や結論は渡しません。実行先は差し替え可能にし、特定の
  サービスを仕様で固定しません

## 直す側との約束

直す側は、往復を回す [cycle.md](cycle.md) が委譲した会話です。人が直接直すこともあります。
指摘の集合の形と次の約束は、直す側が誰でも同じです。review 自身が直すことだけはしません。
指摘を出した本人が直して本人が確認すると、独立した目という review の存在意義が消えるからです。

- 指摘の集合は review だけが書く、変えないファイルです。直す側は読むだけで、状態を書き換えません
- 直す側は、修正コミットの trailer に対象の指摘の ID を書きます。review はコミット履歴の
  trailer から、関連する差分を機械的に計算します
- 直す側が修正中に見つけた別の問題のうち、その修正が生んだ回帰、安全上の問題、致命的な問題は
  review に観測として返し、指摘の集合へ追加します。関係のない軽微な問題は後回しの候補として
  別ファイルに書き、往復の途中では扱いません
- 直す側が修正中に仕様の不足を見つけたら、仕様書の改訂は brainstorm に戻し、review は
  `findings_stale` で止まります。改訂後に束ね直せば、そこから続きます

## 記録の置き場所

review の記録は、implement の証拠と同じ実行の下に、同じ「1 件 1 ファイル、追記のみ」の
方式で置きます。実行 ID を持たない入力（ブランチや差分だけ）をレビューしたときは、
`.agents/evidence/reviews/<レビュー ID>/` に同じ形で置きます。記録の形は同じで、
implement の証拠を参照する部分だけがありません。

指摘と判定の記録に、件数や経過時間による保存上限は設けません。上限で古い指摘を落とすと、
過去に何を見つけ、どう閉じたかを復元できなくなるためです。件数が増えた場合は未解決の指摘と
関連差分だけを読むことで処理量を抑え、記録そのものは残します。また、この記録は単一作業者の
ローカルデータなので、本人による偽造を想定した署名、真正性、改変検出、同一性確認は作りません。
途中書き込みや壊れた形式を拒否する入力検査とは別の話です。

- `.agents/evidence/<手順書 ID>/<実行 ID>/review/`: 指摘の集合と、往復ごとの判定
- implement の出来事の列には書き足しません。review は自分の連番を持ち、最初の出来事で
  implement の最後の出来事の番号と、実行を束ねた Git コミットを参照します。独自の指紋は
  持ちません
- 指摘の追加と開閉は追記で表し、最初の集合のファイルは上書きしません
- 束ね直し（`rebound`）も review の記録に追記します。以降は、その出来事が指す Git コミットの
  内容を使います。`findings_stale` は終端ではなく、そのあとに `rebound` を追記できます
- review の完了は、最終全体レビューが済み、今回の対象にした全指摘が `closed` になったことから
  導きます。`findings_stale` の間は完了ではありません。完了を表す出来事は書きません
- 同じ実行に対して、2 つの review を同時に走らせません。review の記録ディレクトリが
  すでにあって終わっていなければ、人に見せて確認します。リポジトリ全体に 1 つの「使用中」の
  印は置きません
- 実行の全出力や外部サービスのログは記録に複製しません。秘密情報、個人情報、内部の
  ホスト名も記録しません

## 人が判断する場面

| 場面 | 人が決めること |
|---|---|
| 重要な設計判断、不可逆な操作、人の権限が必要な指摘 | どの判断または操作を採るか |
| 機械で確かめる指摘を直さないと決める | 理由を記録して閉じるか |
| 仕様書の重要な判断が動き、指摘の前提が古くなった（`findings_stale`） | 改訂後の内容で束ね直すか、新しく始めるか |
| 安全上の確認が終えられない | どうするか（review は未完了のまま止まる） |
| 進捗が止まり、原因診断後の修正でも回復しない | 仕様・設計・指摘のどこを見直すか |
| 強さ（`light` / `standard`）と追加の 2 人目のレビュアー | 使うか（その場で、1 回だけ） |
| レビューのモデル | プロジェクトの指示や利用者の規則で決めておくか、起動時に指定するか |

## 失敗したときの動き

- 必要な人、証拠、作業ディレクトリ、確かめ方を実行する環境が無いときは、成功と言わず、
  未完了で再開できる状態を残します
- 拒否や停止のあとも、指摘の集合のファイルは消しません
- 確かめ方は作業ディレクトリの中で安全な操作へ組み立て直して実行します。絶対パス、作業
  ディレクトリの外への書き込み、不可逆・外部公開・認証情報を含む提案はそのまま実行しません。
  同じ結果を安全に確かめる方法が無い場合だけ、人の判断が必要な指摘として残します

## やらないこと

- 直さない。直す往復を回さない。直す役を呼ばない
- 最終判断、メインのブランチへの取り込み、公開、作業ディレクトリの掃除をしない
- 手順書の本文、状態ファイル、セッションの履歴を更新しない
- `info` の指摘を自動で直さない
- 頼まれていない 2 人目のレビュアーを動かさない
- Claude Code 組み込みの `/code-review` や公式プラグインに最初のレビューを委ねない
  （AI の種類によっては存在しないため）。品質がぶれ、指摘の ID と限定した再レビューを
  持たないことも理由です
