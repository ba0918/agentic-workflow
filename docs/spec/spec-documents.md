# 仕様書の分け方 仕様

この文書は、brainstorm が書く仕様書の粒度と分け方と参照のさせ方を、人が読んで判断できる形で書いたものである。
この約束に従って動くのは主に brainstorm である。
plan、cycle、review は、分けた仕様書を受け渡す側として関わる。
各工程がこの約束をどこで使うかは、[開発ワークフロー仕様](workflow.md)の各工程の節にある。
skill の本文は LLM 向けの英語で、この文書の内容を実行者への指示として写したものである。
両者の意味が食い違ったときは、この文書を正とする。
この文書の上位に[理念](../principles.md)があり、食い違ったときは理念に従う。
用語集はリポジトリ直下の [CONTEXT.md](../../CONTEXT.md) にある。

## 目的と限界

仕様書は、改訂のたびに同じ 1 本へ書き足されて大きくなる。
大きな仕様書は自分の中で矛盾しやすく、しかもその矛盾に気づきにくい。
LLM も人と同じで、大きな文脈を一度に渡されると矛盾を見落とす。
kakoi では 1 本の仕様書が約 1,700 行になり、レビューのたびに新しい矛盾が見つかり、直すたびに別の矛盾が出て終わらなかった。

この文書の目的は、矛盾を減らして見つけやすくすることである。
手段は、仕様書の粒度を小さく保つことと、事実の置き場を 1 つにすることである。
矛盾を無くすことは約束しない。
機械の検査を持つ仕組み（kotowari）であっても保証まではできず、確率を下げているだけである。
このワークフローは機械の検査を持たないので、その範囲で確率を下げる。

## 責務ごとに 1 本

仕様書は責務ごとに分け、1 つの責務を 1 本で書く。
責務とは、同じ理由で変わる物のまとまりである。
仕様書では要求のまとまりを、skill では指示のまとまりを指す。
たとえば「review の指摘の形」と「cycle の終わり方」は変わる理由が違うので、別の責務である。

brainstorm は仕様書を書くとき、既存の仕様書に足すか、新しい仕様書を作るかを、この責務で判断する。
足そうとしている要求の変わる理由が既存の要求と違うなら、新しい仕様書にする。
1 回の brainstorm で複数の仕様書を変えてよい。
それでも成果物は [plan に進める条件](workflow.md#仕上げ)の 1 単位のままである。

ディレクトリの形やファイル名は、このワークフローでは決めない。
小さいプロジェクトなら仕様書の置き場の直下に並べるだけで足りる。
大きいプロジェクトなら、ドメインごとのディレクトリに分けることもある。
どちらが合うかはプロジェクト次第で、brainstorm がそのプロジェクトの形に合わせる。

- 成功の条件: 改訂の後、どの仕様書も、中の要求が同じ理由で変わる物だけでできている
- 反例: 「review の指摘の形」を直す改訂で、cycle の終わり方の仕様書に節を足す
- 確かめ方: brainstorm が書く前の見直しで確かめ、人が承認のときに見る

## 1 つの事実は 1 か所

1 つの事実は、1 つの仕様書の 1 か所にだけ書く。
ほかの仕様書でその事実が要るときは、書き写さずにリンクで参照する。
写しは、片方だけが直されたときに食い違う。

brainstorm は新しい要求を書く前に、その要求の中心の言葉で、プロジェクトの指示が示す仕様書の置き場（このリポジトリでは `docs/spec/`）をテキスト検索する。
同じ事実が既に書かれていれば、書かずにそこへリンクする。

- 成功の条件: 同じ事実を述べた文が、2 つ以上の仕様書に無い
- 反例: 「フルレビューは 2 回目で最後」を、cycle の仕様書と review の仕様書の両方に書く
- 確かめ方: brainstorm が書く前の見直しで確かめ、人が承認のときに見る

## 参照はリンクで書く

ほかの仕様書への参照は、Markdown のリンクで書く。
見出しへの参照は、アンカーでその見出しへ飛べるようにする（例: `[指摘 1 件の項目](review.md#指摘-1-件の項目)`）。
リンクになっていない参照は、人が辿りにくく、LLM もどの文書とつながっているかを拾えない。

節番号や「上記」「前述」での参照は書かない。
この約束が効くのは、その改訂で書いた参照と、分けたときに張り直す参照である。
今ある文書に残っているリンクでない参照を、まとめて直すことはしない。
仕様書を分ける brainstorm は、分けたときに残る古い参照（節番号、「上記」など）を、同じ変更の中で全部リンクに張り直す。
kakoi は分けたときに張り直さず、節番号での参照が 12 か所残った文書と、委任を集めた文書のあいだで、規則と裁量が食い違った。
2 つの文書はリンクでつながっておらず、どちらを読んでも相手に辿り着けなかった。

見出しの名前を変えたり文書を動かしたりした brainstorm は、同じ変更の中で古いリンクをテキスト検索して直す。
リンク切れを機械で検査する仕組みは持たない。

- 成功の条件: その改訂で書いた参照と張り直した参照が全部リンクで、リンク先の文書と見出しが存在する
- 反例: 仕様書を分けたのに「第 6.1 節の上限に当たる」という参照を残す
- 確かめ方: brainstorm が書く前の見直しで確かめ、人が承認のときに見る。リンク先の存在はテキスト検索で確かめられる

## 分ける目安

仕様書 1 本の行数の目安は 300 行である。
この数に根拠は無く、仮に置いた値である。
実績が出たら変える。
変えるときは、この節を改訂し、同じ改訂の中で brainstorm の skill 本文の写しも直す。
仕様書は人が承認してコミットし、skill 本文は成果物として cycle の終端で受け入れる。

brainstorm は仕様書を改訂するとき、改訂後の行数が目安を超えるなら、その仕様書に責務が混ざっていないかを確かめる。
混ざっていれば、今回の改訂が触る責務だけを切り出して別の仕様書にする。
ほかの責務はそのまま残す。
混ざっていなければ、そのままでよい。
行数は、ファイルの行数をそのまま数える。
混ざっているかの結論と切り出した範囲は、承認を頼むときの判断点として人に見せる。
数に合わせて文を削ったり、責務の境目でない所で分けたりするのは反例である。
依存し合う約束が別々の文書に割れると、かえって矛盾に気づきにくくなる。

既に大きくなっている仕様書を、まとめて整理し直すことはしない。
その仕様書を改訂する brainstorm が目安に当たった時点で、その場で確かめる。
この約束は、この文書が承認された後の改訂から効く。

- 成功の条件: 目安を超えた仕様書を改訂した brainstorm が、責務が混ざっているかを確かめ、その結論を人に見せている
- 反例: 目安を超えないように、要求の説明や反例を削る
- 確かめ方: brainstorm が書く前の見直しで確かめ、人が承認のときに見る

## 分けたときの形

### 索引

1 本の仕様書を複数に分けたときは、索引を 1 本置く。
索引は、分けた仕様書へのリンクと、それぞれの 1 行の説明だけを持つ仕様書で、本文を持たない。
人が読み始める場所であり、brainstorm がその範囲の改訂を始める場所である。
[plan の起点ではない](workflow.md#plan)。

- 成功の条件: 分けた仕様書が、どれも索引からリンクで辿れる。索引に要求が書かれていない
- 反例: 索引に「共通の約束」の節を置いて本文を書く
- 確かめ方: brainstorm が書く前の見直しで確かめ、人が承認のときに見る

### 却下・未決定・委任の置き場

仕様書を分けたとき、却下した案、未決定、委任の節は、それが関わる責務の仕様書に置く。
1 つの仕様書に集めない。
kakoi は委任を 1 つの文書に集めたので、ある規則と「それを実装に任せる」という記述が別の文書に離れ、食い違った。
同じ文書にあれば、書く時点で両方が目に入る。

- 成功の条件: 却下・未決定・委任のどの項目も、それが関わる要求と同じ仕様書にある
- 反例: 分けた仕様書の委任を `delegation.md` にまとめる
- 確かめ方: brainstorm が書く前の見直しで確かめ、人が承認のときに見る

### 用語集

用語集は、既定ではリポジトリ直下の [CONTEXT.md](../../CONTEXT.md) 1 本である。
同じ語の意味がドメインごとに割れたときだけ、そのドメインのディレクトリへ用語集を分ける。

- 成功の条件: 用語集が複数あるとき、どの 2 つを比べても、同じ語に違う定義を与えている理由がドメインの違いで説明できる
- 反例: 意味が割れていないのに、ドメインごとに `CONTEXT.md` を置く
- 確かめ方: brainstorm が書く前の見直しで確かめ、人が承認のときに見る

## 作る物

- `skills/ba0918-brainstorm/` の本文への写し。この文書の約束のうち brainstorm が実行する物と、書く前にリンク元を読み直すこと、仕上げのレビューに渡す範囲
- `skills/ba0918-plan/` と `skills/ba0918-cycle/` の本文への写し。[開発ワークフロー仕様](workflow.md)の plan と cycle の節で変えた受け渡し
- `skills/ba0918-using-workflow/`、`skills/ba0918-iterate/`、`skills/ba0918-investigate/` の本文の直し。仕様書のパスを 1 本と決めている箇所
- `PROJECT.md` の正本の表に、この文書の行を足す。縛りの行数の書き方を「目安」に直す

## 作らない物

- ディレクトリの形の雛形（小規模ならこう、大規模ならこう）
- 行数で機械的に仕様書を切る仕組み
- リンク切れの検査
- 既存の仕様書の棚卸し
- 分けた仕様書の組全体を指す言葉

## 却下した案

- ディレクトリの形をワークフローで決めること。合う形はプロジェクト次第で、決めるのは責務の線と事実の置き場で足りる
- 分ける合図を「上限」と呼ぶこと。LLM が上限を死守しようとして、無理に圧縮したり無理に分けたりし始める
- 1 回の brainstorm で変える仕様書を 1 本に限ること。責務をまたぐ変更で brainstorm が何回も要り、境目をまたぐ矛盾をどの回も一緒に見なくなる
- plan に索引から辿らせること。関係ない文書まで読ませる
- 却下・未決定・委任を 1 つの仕様書に集めること。規則と、それを任せる記述が離れる
- リンク切れの検査を足すこと。切れて困った実績がまだ無い
- 既存の仕様書をまとめて整理し直すこと。改訂のときに確かめれば足りる
- kotowari のような機械の検査をこのワークフローに持たせること。実行環境を持つとフレームワークになり、このワークフローは kotowari に依存しない
- 「入口」と呼ぶこと。using-workflow の「入口」と同じ語が 2 つの意味になる
- ドメインごとの用語集を既定にすること。意味が割れていないうちは 1 本で足りる
