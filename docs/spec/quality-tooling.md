# 品質検査ツール

## 目的

品質検査ツールは、ソースコードと仕様書にある機械判定可能な違反を検出します。特定のAIエージェントに依存せず、同じ検査を手動実行、Gitのコミット前処理、継続的インテグレーションから利用できなければなりません。

ここでいう品質検査には、Pythonコードの構造検査と型検査、日本語仕様書の文章検査を含みます。

## 配置

共通実装は`tools/quality`に配置します。このディレクトリには、検査をまとめて実行するコマンド、個別検査、設定、追加規則、テストを置きます。

AIエージェントの終了時フック用の変換処理は`tools/quality/agents/stop_hook.py`に配置します。この処理は共通検査の結果を、終了時フックが要求するJSONへ変換するだけにします。Claude CodeとCodexの終了時フックは同じ形式のJSONを受け取るため、変換処理はエージェントごとに分けず1つだけ置きます。

`.claude`にはClaude Codeが読み込むプロジェクト設定`settings.json`だけを、`.codex`にはCodexが読み込む`hooks.json`だけを追跡します。品質検査の実装、設定、テストは置きません。両方の設定は、同じ変換処理を同じ引数で終了時フックとして登録します。

## 依存方向

エージェント用の変換処理は共通品質検査に依存できます。共通品質検査は、エージェント用の変換処理、各エージェントの設定、エージェント固有の入力形式に依存してはいけません。

LefthookはGitのコミット前にコマンドを実行するツールです。Lefthookと継続的インテグレーションは、エージェント用の変換処理を経由せず、共通品質検査を直接呼びます。

## 共通コマンドの契約

共通コマンドは、検査対象の範囲として作業ツリー、Gitのステージ済み内容、または全追跡対象を受け取ります。違反がなければ終了コード0を返します。違反があれば非0を返し、原因を診断として出力します。

共通コマンドは、起動時のカレントディレクトリや暗黙の`PYTHONPATH`に依存してはいけません。リポジトリ直下以外から起動した場合も、同じ対象を検査して同じ結果を返します。

## Pythonの検査対象

Pythonの構造検査と型検査は、手書きの正本である`tools/quality`と`tools/workflow-runtime`を対象にします。各ディレクトリのテストも対象です。次節で定めるPylint規則と追加規則、strict mypyの全違反を解消し、行単位の抑制、型検査の回避、対象除外、別名の検査入口による迂回を認めません。

`skills/*/scripts`にあるPythonは`tools/workflow-runtime`から生成された配布用の複製です。同じ内容を二重にlintせず、agentic-skill-vendorの一致検査で正本からの乖離を拒否します。

Python検査は、作業ツリー、ステージ済み、全追跡対象のどの範囲でも正本全体を検査します。変更ファイルだけに限定すると、型や重複コードなど複数ファイルにまたがる違反を見逃すためです。

ステージ済み範囲では、Gitのindexから一時的なcheckoutを構築し、その中にあるPythonの正本全体を検査します。作業ツリーの内容で代用せず、部分ステージングを含めて実際にコミットされる内容を検査します。一時checkoutを安全に構築できない場合は、検査を失敗させます。

Pythonの正本として検査するのは通常ファイルだけです。対象パスがsymlinkなどの非通常ファイルになっている場合は、検査対象から黙って除外せず、検査を失敗させます。

## Pythonの構造規則

Pylintは、重大度がfatal、error、warningの規則をすべて適用します。これに加えて、次の規則を適用します。

- 命名規則の`invalid-name`と`disallowed-name`
- 引数、ローカル変数、return、分岐、文、真偽式、ネストの複雑度規則
- `duplicate-code`
- `too-many-public-methods`
- `too-many-ancestors`
- `tools/quality/plugins`にあるプロジェクト固有の設計規則

命名はPylintの既定規則に従います。クラスの公開メソッド数と祖先クラス数もPylintの既定上限を使い、責務肥大化の粗い兆候として検出します。

業務ロジックの再利用と責務分割には、継承より移譲と合成を優先します。ただし、例外階層、テスト基底、フレームワークの拡張点、データ表現など、外部契約や種類の関係を表す境界用途の継承は禁止しません。継承自体を一律に禁止する独自規則は設けません。

一律のdocstring、行長、クラスの最小公開メソッド数、インスタンス属性数は強制しません。これらを満たすためだけの説明、分割、名前変更は、可読性や責務を改善するとは限らないためです。その他のconvention、refactor規則は、ここで列挙したものだけを選択して適用します。

テストの目的と期待する振る舞いはテスト名で表します。前提、反例、fixtureの理由など、コードと名前だけでは意図を誤解するテストにはコメントまたはdocstringを残しますが、全テストへの説明文は強制しません。

## 仕様書の検査対象

文章検査は`docs/spec`にあるMarkdown候補のうち、通常ファイルだけを対象にします。作業ツリー範囲では変更済みと未追跡の対象、ステージ済み範囲ではindexにある変更対象、全追跡範囲ではGitが追跡する全対象を検査します。

仕様書の本文と箇条書きは、どちらもです・ます調に統一します。textlintの文体規則は、本文と箇条書きの双方でです・ます調を優先し、文末にある文体の混在を拒否します。

ステージ済み範囲では、作業ツリーではなくindexの本文を検査します。部分ステージングされた内容、削除、file-type changeを正しく扱い、symlinkなどの非通常ファイルを通常ファイルとして検査したことにしてはいけません。

クリーンなcheckoutで差分がなくても、全追跡範囲は対象を空にしません。全追跡範囲は継続的インテグレーションがリポジトリ全体の現在値を証明するために使います。

## 編集直後のファイル単位検査

AIエージェントがファイルを書き換えた直後に、そのファイルだけを検査する経路を置きます。目的は、違反をターン終了まで溜めずに、書いた直後に同じファイルで直させることです。

対象は、Pythonの正本にある`.py`と`docs/spec`にあるMarkdownだけです。Pythonの正本にはPylintとmypyを、Markdownにはtextlintを、全体検査と同じ設定ファイルで実行します。規則を緩めた別設定を使ってはいけません。それ以外のファイルと、リポジトリの外にあるファイルは何もせずに成功として扱います。

この経路は即時の助言であり、合否の権威ではありません。1ファイルだけの検査では、重複コードのようにファイルをまたぐ違反を検出できないためです。合否は、終了時フック、コミット前処理、継続的インテグレーションの全体検査が決めます。ファイル単位検査が通っても、全体検査の対象や規則は変わりません。

Claude Codeはフックへ書き換えたファイルのパスを渡し、Codexの編集ツールはパッチ本文を渡します。変換処理はどちらも受け取り、パッチからは追加、更新、移動先のパスを取り出して、フックが報告する作業ディレクトリを基準に解決します。削除されたファイルは検査しません。

## runtimeリファクタリング

`tools/workflow-runtime`のlint適合は、振る舞いを変更しないリファクタリングとして行います。既存の137件のruntimeテストを維持し、型、責務分割、依存方向、重複、複雑度を規則に適合させます。検査を通すために公開契約、保存形式、イベントの意味、人の判断境界を変更してはいけません。

既存テストが失敗する変更、証拠形式や保存方式の変更、新しい外部依存が必要になった場合は、lint違反を理由に自動決定せず、仕様判断へ戻します。

## 実行経路

次の実行経路は、同じ検査設定を使います。

- 共通コマンドを直接実行する経路
- Claude CodeとCodexの終了時フックから変換処理を経由する経路
- AIエージェントがファイルを書き換えた直後に、そのファイルだけを検査する経路
- Lefthookのコミット前処理から共通コマンドを呼ぶ経路
- GitHub Actionsから全追跡対象を検査する経路

入口ごとに異なるのは、検査に使うsnapshot、文章検査の対象範囲、結果の表現だけです。Pythonの対象集合とPylint、mypy、textlintの規則は、入口によって変えてはいけません。

## 失敗時の扱い

検査器を取得できない、設定が壊れている、対象を安全に確定できない場合は成功として扱いません。診断を返し、検査を失敗させます。違反を回避するためのlint抑制、設定緩和、hookの迂回は禁止します。

runtime全体の適合が一度に完了しない場合も、通っていない検査を成功扱いにする暫定除外は追加しません。リファクタリングを独立した実装単位として完了させてから、v0.1.0の配布CIを有効にします。
