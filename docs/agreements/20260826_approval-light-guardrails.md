# 承認を減らし、設計段階のガードレールを強化する

## 目的

人の確認を、本当に人の判断が必要な場所へ集約する。確認を増やすことで安全を作ろうとすると、
確認が儀式になり、重要な判断まで中身を読まずに通すようになる。代わりに、作る物を決める段階へ
LLM の検討と独立レビューの費用を寄せ、実装中は大筋を変えない判断を自走させる。

## 合意

### 人が判断する境界

- 通常の人の確認は、仕様書、手順書、最終成果物の 3 つの境界へ集約する
- cycle の途中では、重要な設計判断が未決定、不可逆な操作の直前、人の権限が必要、または
  放置すると被害が広がる事故が起きた場合だけ人へ返す
- 仕様や手順の大筋を変えない補完、通常の変更ファイルの漏れ、道具の選択、回復可能な失敗は
  LLM が処理し、必要な事実だけを終端で報告する
- 仕様が扱うべき重要な判断について、書かれていないことを LLM への委任とは扱わない。委任は
  仕様書に明記する。合意済みの結果を実現する内部的な選択は LLM が行ってよい

### 設計段階のレビュー

- brainstorm の仕上げでは、別コンテキストのアーキテクトが目的そのものを含めて全体を疑う
- アーキテクトは「作らない」という案、暗黙の未決定、既存構造との衝突も指摘できる。人との
  合意を自動で上書きせず、再検討する材料として返す
- 仕様の意味が変わったら、アーキテクトは全体をもう一度レビューする。問題が無くなってから
  人へ仕様書の承認を求める
- plan は最初に手順書全体を独立レビューする。局所的な修正後は指摘と影響範囲だけを見直し、
  前提、順序、依存、完了条件、参照仕様が動いたら全体レビューへ戻る
- plan のレビューで仕様不足を見つけたら、plan の中で設計せず brainstorm へ戻す

### 依存と危険な対象

- 新しい外部依存の採用は brainstorm で人と決める。plan や implement は新しく決めない
- 標準ライブラリ、実行環境の標準機能、導入済みの依存は、実装側が選んで使ってよい
- plan の Scope は予定した変更範囲であって、絶対的な許可リストではない。大筋を変えない
  ファイル漏れは実装側が補い、理由を終端で報告する
- 本番設定、データ移行、アクセス制御、秘密情報など、誤ると被害が大きい対象は、パスの一覧だけ
  ではなく内容と操作の影響から判断する。AGENTS.md などの明示的な規則も判断材料にする
- 秘密情報、危険なパス、一時ファイル、ログ、生成物の検査は、予定範囲の内外にかかわらず
  全コミットで通す。範囲外変更のために安全検査を迂回しない

### Git と記録

- 仕様書、手順書、出来事のために独自の SHA-256 指紋を持たない
- 承認対象は Git のステージ領域に固定し、人はステージ済みの差分を読んで承認する。承認した
  内容をそのままコミットする
- 承認済み文書は、コミット済みで作業ツリーの内容がそのコミットと一致する文書に限る
- RED で失敗したテストと GREEN で通ったテストの同一性は、Git で代替できないため確認を残す
- cycle が実行 ID と記録場所を作り、委譲の開始と終了を書く。委譲中は implement だけが
  手順の証拠を書く。出来事を指紋の鎖にはしない
- 旧形式の実行記録を新形式へ変換する移行処理は作らない。新仕様は完成後に始める実行から使う

### review の収束

- 最初に全体レビューを行い、修正中は未解決の指摘と修正差分だけを見る
- 修正が新しく持ち込んだ問題は指摘へ追加する。偶然見つけた無関係な軽微事項は終端報告へ送り、
  安全上または致命的な問題は今回の対象へ含める
- 未解決の指摘が閉じたら、新しい目で最終全体レビューを 1 回行う。その指摘は限定レビューで
  閉じ、全体レビューをもう一度繰り返さない
- 往復回数に根拠のない上限を置かない。未解決の指摘を `security`、`critical`、`warn` の順で
  数えた組が、辞書順で小さくなることを進捗とする
- 進捗が無ければ編集を続けず原因を診断する。診断後の修正でも進捗が無ければ、仕様、設計、
  指摘のどこかに人の判断が必要な問題があるとして人へ返す
- `stale` は完了ではなく一時停止である。参照仕様が変わっても重要な判断が動かなければ、LLM が
  新しい版へ追従して終端で報告する

### 最終報告

- 最終報告は、成果物、検証結果、確認する差分への案内を基本とする
- LLM が補った判断、予定外の変更、未解決事項は、実際に存在するときだけ追加する。空の定型欄を
  毎回並べない

## 却下した案

- 人を頻繁に止めることで安全を作る案。確認が儀式になり、重要な判断の質を下げるため
- 指摘の集合を固定して新しい問題を無視する案。修正が持ち込んだ不具合を見逃すため
- 根拠のない往復回数で review を打ち切る案。進捗の有無を見ずに止まるため
- Git と別に仕様書・手順書・出来事の指紋を持つ案。同じ役割の仕組みを重ねるため
- 旧形式の途中実行を新形式へ移行する案。完成前の仕組みで、移行対象となる実運用が無いため
