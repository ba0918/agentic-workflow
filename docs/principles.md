# ワークフローの理念

開発を円滑に進めるためのワークフローを構築する。
これは本質的な理念のみを抽出したものである。

## 共通

- 各 skill の責務をシンプルにする。依存を極力持ち込まない
- 人が見るのは最終成果物だけ。改善ループは自律で回る
- 人を止めるのは次の 4 つだけ。それ以外の躓きは LLM が自分で立て直す
  - 製品や設計の意味が足りない、または承認済みの内容から動いた
  - 不可逆な操作、人の権限が要る操作、危険な対象に触れる直前
  - 続けると被害が広がる事故
  - 診断して方法を変えても進捗が無い

## brainstorm

ユーザとの対話で共通理解を得られるまでインタビューし、要件や仕様を抽出する。
これは実質的なドメインモデリングである。

- ユーザと LLM の共通理解を得る。認識のズレを無くす
- 暗黙の了解を 0 にする
- 共通理解を得て、完全な合意を得る。少しでも曖昧であればそれは合意ではない
- 一切の妥協を許さず、徹底的に行う
- 勝手に終わらない

## plan

抽出された要件や仕様を元に、詳細な実装計画を立てる。
文脈を一切知らない LLM が、実装計画を見て作業を円滑に進められる粒度を要求する。
仕様書があるなら参照パスを書いて読ませる。仕様の中身を実装計画に写さない。
足りない文脈は実装側がリポジトリを読んで補う。

完了後に subagent を使って敵対的にレビューする。
意思決定が必要ない指摘はそのまま対応し、意思決定が必要な指摘（設計変更など）はユーザに確認する。
ユーザ確認に回すのは、共通の「人を止める 4 つ」に当たる指摘だけ。

## implement

与えられた実装計画を元に、実装を進める。

- コードベースの場合は TDD で進める
- それ以外の文書や、小さいスクリプトなどはそのまま進めても良い

## review

与えられた文脈を元に、複数観点でレビューする。

少なくとも次の 2 つを行う。

- コードベース観点の評価
- 仕様観点の評価

評価は敵対的に行い、反証を探し、徹底的に厳しく行う。

## cycle

小さいオーケストレータとしての振る舞いを求める。
与えられた実装計画を元にサイクルを回す。

```
implement ──▶ review ──▶ fix
                ▲          │
                └──────────┘
```
