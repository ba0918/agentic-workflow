# ワークフローの理念

開発を円滑に進めるためのワークフローを構築する。
これは本質的な理念のみを抽出したものである。

## 共通

- 各 skill の責務をシンプルにする。依存を極力持ち込まない
- 工程は既定で足さない。足すのに 1 行の理由が要る。理由が書けないなら足さない
- 足すか足さないかは動く前に 1 行で宣言する。人はそれを覆せる。承認を待たない
- 人が見るのは最終成果物だけ。改善ループは自律で回る
- 人を止めるのは次の 4 つだけ。それ以外の躓きは LLM が自分で立て直す
  - 製品や設計の意味が足りない、または承認済みの内容から動いた
  - 不可逆な操作、人の権限が要る操作、危険な対象に触れる直前
  - 続けると被害が広がる事故
  - 診断して方法を変えても進捗が無い
- 判断に任せない物は次の 3 つだけである。どれも機械の検査か上の 4 つで受けるので、工程は増えない
  - 秘密や資格情報に触れる変更は、プロジェクトの検査を通す
  - 公開、配布、版に触れる変更は、プロジェクトの検査を通す
  - 不可逆な操作、人の権限が要る操作、危険な対象は、上の 4 つで止める
- 機械の検査が無いなら、足せるときは足す。足せないなら気づく手段が無いと宣言して進む。レビューで代用しない

## brainstorm

ユーザとの対話で共通理解を得られるまでインタビューし、要件や仕様を抽出する。
これは実質的なドメインモデリングである。

- ユーザと LLM の共通理解を得る。認識のズレを無くす
- 暗黙の了解を 0 にする
- 共通理解を得て、完全な合意を得る。少しでも曖昧であればそれは合意ではない
- 一切の妥協を許さず、徹底的に行う
- 勝手に終わらない

## plan

抽出された要件や仕様を元に、詳細な実装計画を立てる。
文脈を一切知らない LLM が、実装計画を見て作業を円滑に進められる粒度を要求する。
仕様書があるなら参照パスを書いて読ませる。仕様の中身を実装計画に写さない。
足りない文脈は実装側がリポジトリを読んで補う。

完了後のレビューは既定では行わない。
手順書の中で決めたことが互いに矛盾しうるとき、その理由を宣言して subagent に敵対的にレビューさせる。
意思決定が必要ない指摘はそのまま対応し、意思決定が必要な指摘（設計変更など）はユーザに確認する。
ユーザ確認に回すのは、共通の「人を止める 4 つ」に当たる指摘だけ。

## implement

与えられた実装計画を元に、実装を進める。

- コードベースの場合は TDD で進める
- それ以外の文書や、小さいスクリプトなどはそのまま進めても良い

## review

与えられた文脈を元にレビューする。

レビューを足す理由は 1 つである。
依存し合う変更箇所が複数あり、実装が自分の中で矛盾しうることである。
1 箇所で閉じる変更、互いに独立した変更、機械の検査が捕まえる間違いには足さない。

体数は観点の数で決める。既定は 1 つ（コードベース観点）で、突き合わせる仕様書があり、
機械の検査がその整合を捕まえられないなら、仕様観点も足して 2 つにする。

評価は敵対的に行い、反証を探し、徹底的に厳しく行う。

## cycle

小さいオーケストレータとしての振る舞いを求める。
与えられた実装計画を元にサイクルを回す。

フルレビューは既定で 1 回である。
修正が別の場所へ波及しうるときだけ、その理由を宣言して 2 回目を回す。

```
implement ──▶ review ──▶ fix
                ▲          │
                └──────────┘
```
